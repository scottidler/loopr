# Design Document: Coordinator Phase Gating and Work Dispatch Fixes

**Author:** Scott A. Idler
**Date:** 2026-04-08
**Status:** Implemented
**Review Passes Completed:** 5/5

## Summary

Three bugs combine to prevent any work from executing in a Full-mode E2E run. The coordinator
declares `GoalComplete` immediately after decomposition, which leaves `current_phase_id` as
`None`, which causes workers to claim work out-of-phase and without atomic exclusion. A fourth
issue prevents implementers from reading their phase context docs inside isolated worktrees. All
four are discrete, non-overlapping fixes.

## Problem Statement

### Background

Loopr decomposes a goal into a Plan -> Spec -> Phase -> Work hierarchy. The coordinator FSM
drives phase activation and completion. Pull-based workers pick up `Ready` work items and run
implementers in isolated git worktrees. The decomposer creates all records as `Active`/`Ready`
immediately so the coordinator can begin executing without a second activation step.

### Problem

In every Full-mode run, the coordinator signals `GoalComplete` within seconds of decomposition
finishing. Workers then pull work items from any phase because `current_phase_id` is `None`, and
two workers can claim the same work item. Implementers that do start fail immediately because
`docs/loopr/` hierarchy documents are not accessible from inside the worktree.

Root cause trace (confirmed against source + E2E log 20260408T131053):

1. `coordinator.rs:879` - `find_next_phase_to_activate` looks for `HierarchyStatus::Draft`
   phases. The decomposer (`decomposer.rs:925`) creates all phases as `HierarchyStatus::Active`.
   Function returns `None` on first call. `apply_fsm_transition` treats `None` as "no phases
   remain" and transitions to `GoalComplete`.

2. With the coordinator at `GoalComplete`, `current_phase_id` is never set. Worker dispatch
   (`work_queue.rs:35`) has `unwrap_or(true)` on the phase filter, so all 37 `Ready` works are
   eligible simultaneously.

3. `next_assignable_work` returns a work ID under a read lock without marking it claimed.
   `run_single_work` then calls `work.transition` (Ready -> InProgress) over IPC. If two workers
   read concurrently, both see the same work as `Ready`. The second worker's `Ready -> InProgress`
   transition hits `Transition::Unchanged`, which returns `DaemonResponse::ok(null)` - not an
   error - so the second worker proceeds as if it won the claim.

4. Implementers run inside `git worktree add`-created directories. `docs/loopr/` files (phase and
   work markdown) are generated by the daemon into `repo_path/docs/loopr/` and are never committed
   to git. The worktree checkout does not contain them. `read_file 'docs/loopr/ph-xyz.md'` fails.

### Goals

- Fix the coordinator FSM to correctly activate phases when phases start as `Active`
- Fix work dispatch to be atomic so no work item can be claimed by two workers
- Fix worktree creation to make `docs/loopr/` readable from inside each worktree

### Non-Goals

- Changing the decomposer's status choices (phases-as-Active is intentional design)
- Adding dependency ordering to work dispatch (dependencies are already filtered in `work_queue.rs`)
- Changing how work priority scoring works

## Proposed Solution

### Fix 1 - coordinator.rs: Return first non-terminal phase

**File:** `src/agents/coordinator.rs`
**Location:** `find_next_phase_to_activate`, inner loop (~line 879)

Change the phase selection from Draft-only to any non-terminal status:

```rust
// Before
for (phase_id, _, title, _, status) in &phases {
    if *status == HierarchyStatus::Draft {
        return Some((phase_id.clone(), title.clone()));
    }
}
// No Draft phases but some are still Active/in-progress - wait
return None;

// After
for (phase_id, _, title, _, status) in &phases {
    if !matches!(*status, HierarchyStatus::Complete | HierarchyStatus::Abandoned) {
        return Some((phase_id.clone(), title.clone()));
    }
}
// has_non_terminal was true but no matching phase found - should be unreachable
warn!("find_next_phase_to_activate: has_non_terminal=true for spec {} but no matching phase", spec_id);
return None;
```

The outer `has_non_terminal` check already confirmed a non-terminal phase exists, so the new
`warn!` + `None` branch is structurally unreachable with valid data.

Update the function comment block to reflect that phases start as `Active` (not `Draft`).

**Why not fix the decomposer instead:** The decomposer comment at line 872 explicitly states
"All records start Active/Ready immediately (coordinator begins executing after decomposition)".
This is intentional. The coordinator should match the decomposer's contract, not the other way
around.

**Side effect:** Once `current_phase_id` is populated (by this fix), the existing
`work_queue.rs:35` phase filter works correctly with no additional changes.

### Fix 2 - work_queue.rs: Atomic work claiming

**File:** `src/daemon/work_queue.rs`
**Change:** Atomically claim work inside `next_assignable_work` using a double-check lock pattern.

The function currently reads all works under a read lock, scores candidates, returns the winning
ID, and releases the lock. The caller (`run_single_work`) then claims the work via a separate IPC
call (`work.transition Ready -> InProgress`). Between the read and that IPC call, another worker
can read the same work as `Ready`, score it, and also call `work.transition`.

The race is confirmed: `handle_work_transition` returns `DaemonResponse::ok(null)` on
`Transition::Unchanged` (work already InProgress), so `transition_resp.is_error()` is `false`.
Both workers proceed to run an implementer on the same work item.

**Chosen approach (double-check):** Score candidates under a read lock (as today), then re-verify
and mark `InProgress` under a write lock before returning. No signature change.

```rust
pub fn next_assignable_work(stores: &Arc<Stores>, current_phase_id: Option<&str>) -> Option<String> {
    // Phase 1: score candidates under read lock (no change from today)
    let candidate_id = {
        let works = stores.read_works().ok()?;
        // ... existing filter + scoring logic ...
        candidates.first().map(|c| c.work_id.clone())
    }?;

    // Phase 2: atomically claim under write lock
    let mut works = stores.write_works().ok()?;
    let work = works.get_mut(&candidate_id)?;
    if work.status() != WorkStatus::Ready {
        return None; // Lost the race between phases - caller retries next tick
    }
    work.force_status(WorkStatus::InProgress);
    // Persist to TaskStore while still holding the write lock
    if let Some(ref store_arc) = stores.store {
        if let Ok(mut s) = store_arc.lock() {
            let _ = s.update(work.clone());
        }
    }
    Some(candidate_id)
}
```

Because `next_assignable_work` now marks `InProgress`, `run_single_work` must skip or remove
the `work.transition` call at step 1 (`executor.rs:167-187`). The work is already claimed
when the function returns.

One production caller: `worker.rs:56`. All test call sites in `work_queue.rs` use `Arc<Stores>`
with no state mutation expected after the call — tests verify return value only. Tests for the
existing `InProgress` filter case (line 287: `assert!(next_assignable_work(&stores, None).is_none())`)
remain correct because an already-InProgress work is not in `Ready` state and is filtered before
the write phase.

### Fix 3 - context.rs: Resolve docs/loopr paths from canonical repo root

**File:** `src/agents/context.rs`
**Location:** Parent context link emission (~lines 622-654)

The context builder emits parent context links as relative paths (`docs/loopr/{id}.md`). When
an implementer runs inside a git worktree, these relative paths resolve against the worktree
directory, which does not contain `docs/loopr/` (those files are generated by the daemon into
the canonical repo root and are never committed to git).

**Fix:** Emit absolute paths computed at prompt-render time from `repo_path`:

```rust
let docs_dir = repo_path.join("docs").join("loopr");
// Before: format!("- [Plan: {}](docs/loopr/{}.md)\n", title, id)
// After:
format!("- [Plan: {}]({}/{}.md)\n", title, docs_dir.display(), id)
```

The work doc read (line 578-582) already resolves against `repo_path` correctly. Only the
parent context links (Plan, Spec, Phase) need updating.

**Why not symlinks:** Symlinks require mutating `.git/info/exclude` in the target repo,
leave permanent artifacts, and add filesystem complexity for a problem that is entirely
solvable at the prompt layer. The data is already available via `repo_path` in the config.

**Why not path interception in read_file:** Adds orchestration-specific routing logic to a
generic filesystem tool. The tool layer should stay dumb.

**Why not store absolute paths in JSONL:** Absolute paths are environment-specific and would
break portability across machines. The JSONL records store record IDs; the absolute path is
computed at render time from the config.

### Implementation Plan

Each fix is independent and can be committed separately. Apply in order so each can be validated
before the next.

1. **`coordinator.rs`** (`find_next_phase_to_activate`) - one-line change at line 879, comment
   block update. Run `otto ci`. This unblocks all execution.
2. **`work_queue.rs`** (`next_assignable_work`) + **`executor.rs`** (remove stale
   `work.transition` step) - atomic claim. Run `otto ci`.
3. **`context.rs`** (parent context links) - emit absolute `docs/loopr/` paths.
   Run `otto ci`.
4. Run `bin/e2e python-api` to validate all three fixes together end-to-end.

## Alternatives Considered

### Alternative: Decomposer creates phases as Draft

- **Description:** Change `decomposer.rs:925` from `force_status(Active)` to leave phases in
  their default `Draft` state.
- **Pros:** Matches the original coordinator design where Draft = not yet activated.
- **Cons:** Requires Works to also start as Draft (blocked until phase activates), adds an
  activation step, contradicts the decomposer's stated design intent ("coordinator begins
  executing after decomposition"), and requires a cascade of changes.
- **Why not chosen:** The decomposer comment is explicit. The coordinator should adapt to the
  decomposer's contract.

### Alternative: work_queue filter-only fix (no atomic claim)

- **Description:** Fix only coordinator Bug #1; rely on the phase filter to prevent cross-phase
  dispatch; accept occasional double-assignment as a transient.
- **Pros:** Smaller change.
- **Cons:** Double-assignment causes two implementers to run the same work, producing conflicting
  commits, double spending on LLM calls, and unpredictable state.
- **Why not chosen:** Double-assignment is a correctness violation, not a transient.

## Technical Considerations

### Dependencies

- Fix 2 (`work_queue.rs`) does not change the function signature but adds a write-lock phase.
  One production caller (`worker.rs:56`). The `work.transition` claim step in `executor.rs:167`
  must be removed since the work is already `InProgress` when returned.
- Fix 3 (`context.rs`) requires `repo_path` to be available in the context builder, which it
  already is via `self.stores.config.project.repo_path`.

### Testing Strategy

- Fix 1: Existing FSM tests in `src/tests/fsm/` cover phase activation transitions. Add a test
  that creates phases as Active (not Draft) and verifies `find_next_phase_to_activate` returns
  the first one.
- Fix 2: Existing `work_queue.rs` tests exercise the function. Add a concurrent test that calls
  `next_assignable_work` from two threads simultaneously and verifies only one returns the work
  ID.
- Fix 3: Existing context builder tests cover prompt rendering. Add a test that verifies
  parent context links contain the absolute `repo_path` prefix, not relative `docs/loopr/`.

### Rollout Plan

Single commit per fix, `otto ci` gate between each. Run full E2E after all three land.

## Risks and Mitigations

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| Atomic claim write lock contends with high-frequency reads | Low | Med | Read-then-write pattern (read lock for scoring, write lock only for claim) keeps write lock held briefly |
| Absolute paths in prompts leak filesystem layout | Low | Low | Agent already sees worktree path; repo root is not secret; paths are computed at render time, not stored |
| Scoring phase races with claim phase in Fix 2 (candidate becomes non-Ready between read and write lock) | Low | Low | Write-lock phase re-checks status; returns None on mismatch, caller retries next worker tick |
