# Design Document: `#[derive(Fsm)]` Proc Macro

**Author:** Scott A. Idler
**Date:** 2026-04-20
**Status:** Draft
**Review Passes Completed:** 5/5

**Scope note:** this design touches two crates (`derive` + `domain`), which is why it lives in `docs/design/` at the repo root rather than in `crates/derive/docs/design/` per `crates/derive/docs/CLAUDE.md`. The roadmap entry at §Stage 5 that pointed to `crates/derive/docs/design/fsm-macro.md` was written before this cross-crate shape was understood; update the roadmap when this ships.

## Summary

`#[derive(Fsm)]` turns a Rust enum of status states into a compile-time state machine: it generates const transition tables, role-authorization checks, and the canonical `validate_transition` / `validate_override` / `is_terminal` trio that every `domain` record FSM consumer will call. The macro replaces v4's YAML-loaded `FsmInterpreter` (runtime HashMap lookups over strings) with a pure-codegen design where an unknown transition is a compile-time mismatch, not a runtime "unknown state" lookup.

**Where this fits in the roadmap:** Stage 5 (daemon persists Plan via TaskStore) is the first consumer. `Plan`'s status enum carries `#[derive(Fsm)]` with the transitions listed in the Stage 5 records design. Stage 6 extends the pattern to `Work` and the hierarchy enum. Stages 7 and 8 add `Bundle` and `Tick`. Every v4 FSM in `resources/engine/fsm/*.yml` lands as a `#[fsm(...)]` annotation on its v5 status enum; that port is Phase 4 of this design (reference appendix only, no code).

## Problem Statement

### Background

v4 owned FSM state machines through `FsmInterpreter` (`crates/loopr-v4/src/fsm/runtime.rs`) driven by five YAML files at `resources/engine/fsm/{agent,bundle,hierarchy,tick,work}.yml`. Each YAML declares states, terminal states, transitions keyed `from -> to` with a `by: [role]` authorization list, and override edges for coordinator-only unsticks. At startup `FsmInterpreter::new(repo_path)` loaded every YAML via `rust-embed`, parsed to `HashMap<String, FsmDefinition>`, and served `validate_transition(fsm_name, from, to, role) -> Transition`. Every runtime call stringified a state, traversed two HashMap layers, and returned `eyre::Result<Transition>`.

v5 deliberately collapses that runtime layer. `docs/vision.md` §domain states: "`FsmTransition<T>` — const transition tables with role guards. A transition that isn't in the table is a compile-time mismatch, not a runtime YAML lookup." `docs/vision.md` §Open Questions closes the open issue: "**Fsm derive:** port `#[derive(Fsm)]` from v4's `loopr-derive`. Rehomed in `crates/derive` under v5's single-word naming convention." `crates/derive/CLAUDE.md` constrains scope: "`#[derive(Fsm)]` — const transition tables with role guards; generates `validate_transition`, `validate_override`, `is_terminal`."

Stage 5 of the roadmap (daemon persists Plan via TaskStore) needs this derive in place so `domain::Plan`'s status enum can carry its own transition table. Stages 6 - 9 extend the pattern to `Work`, `Spec`, `Phase`, `Bundle`, `Tick`, and the reactive-execution FSM that coordinator-pool transitions run on.

### Problem

- Today `crates/derive/src/lib.rs` is literally two newlines. Every `domain` record in Stage 5+ is blocked on `#[derive(Fsm)]` existing.
- v4's "port" framing is misleading: the `loopr-derive` crate shipped `#[derive(FlexibleEnum)]` only. `Fsm` logic lives in the YAML interpreter, not in a macro. The Stage 5 derive is **net-new codegen**, informed by v4's runtime shape but not a straight port of a prior macro.
- v4's model has several runtime hazards that the derive needs to eliminate, not reproduce:
    - A typo in a transition (`intergrated` for `integrated`) passes YAML load, fires at runtime, fails with `unknown FSM transition`. Moving to an enum makes that a `no variant named Intergrated on Status` compile error.
    - `fsm_name` dispatch ("work", "plan", "bundle") was a string. Per-enum codegen scopes the table to the enum itself; no registry keyed on strings.
    - Role authorization was a `Vec<String>` matched against a caller-supplied `&str`. Codegen uses the `Role` enum end-to-end. "decomposr" as a typo is a compile error at the annotation site.
- v4's guard system (`guards: deps-ready: condition: deps-satisfied`) evaluated named conditions at runtime against ambient state. That is genuinely runtime logic — the derive must NOT try to encode it. Guards stay as a separate, per-record hook that the derive's consumers layer on top.

### Goals

- **A `#[derive(Fsm)]` macro** that attaches to a `Copy + Clone + PartialEq + Eq + Debug` status enum and generates the canonical trio (`validate_transition`, `validate_override`, `is_terminal`) as inherent methods, plus a few auxiliaries the daemon and UI need (`valid_targets`, `all_states`).
- **Helper attribute `#[fsm(...)]`** on the enum that declares `terminal`, `transitions`, and `overrides` inline. Every reference is an enum variant path, not a string. This is a derive helper attribute (scoped to the derive invocation), not a freestanding attribute macro - the derive crate's CLAUDE.md-forbidden "attribute macros" are attribute macros that rewrite function bodies, not derive helpers.
- **Compile-time dispatch tables** at the codegen-output level. The generated `validate_transition` body is a single `match (from, to) { (Self::A, Self::B) => &[Role::X], ... }`. Rust's match codegen produces a jump-table or binary-search dispatch depending on enum density; no HashMap allocation, no slice scan. For every v4 FSM in `resources/engine/fsm/` the table size is under 30 edges, well below any density threshold where the compiler's choice matters. Auxiliary const slices (the `valid_normal` / `valid_override` values embedded in error objects) are the only `&'static [...]` data the expansion emits.
- **Typed error output.** `validate_transition` returns `Result<Transition, FsmError>`. `Transition` is `Changed | Unchanged`; `FsmError` carries `from: Self`, `to: Self`, `role: Role`, and a `kind: FsmErrorKind` (`NoTransition`, `RoleNotAuthorized`, `NotOverridable`). Error messages include the same rich hints v4 produced (valid targets from this state, with and without overrides), now generated at macro-expansion from the known table.
- **`validate_override`** performs the two-stage check v4 codified: try the normal transition table first; on failure, try the override table. Both failure contexts are chained into a single error.
- **Role enum** lives in the consumer crate (`domain`), NOT in `derive`. `derive` only knows "Role: some enum in the consumer's scope; the macro takes a path to it in `#[fsm(role = ...)]`" and generates code that calls `Role::*`. This preserves the "`derive` has no runtime deps, no domain types" rule.
- **Compile-time validation.** During expansion the macro emits a spanned `compile_error!` (NOT `panic!` — spanned errors point at the offending source) if any of the following hold:
    - The attached item is not an enum (struct, union, fn, etc.).
    - The enum has zero variants (a FSM with no states is meaningless; reject rather than generate a method that can only ever return `Err(NoTransition)`).
    - The enum is generic (`enum Status<T> { ... }`). Generic FSMs would require threading type parameters through every generated method and the `::domain::FsmError<Self>` path; Stage 5+ records are all non-generic. Earn this later if a use case shows up.
    - Any variant is non-unit (`Variant { field: T }` or `Variant(T)`). Transitions over associated data are a Stage 5+ concept we are deliberately deferring.
    - More than one `#[fsm(...)]` attribute appears on the enum. Every config key must be inside a single attribute so the parse is deterministic. Reject with "merge into a single `#[fsm(...)]`."
    - A state listed in `terminal = [...]` has outgoing entries in `transitions(...)` (terminal states cannot transition out).
    - A transition names a `from` or `to` that isn't a variant of the enum.
    - A `from => to` pair appears more than once inside `transitions(...)`; ditto inside `overrides(...)`. Role unions belong inside a single edge's `by (...)` list, not as repeated edges.
    - The same `from => to` pair appears in both `transitions(...)` and `overrides(...)`. Overrides exist precisely for edges the normal table does NOT authorize; the duplication is always a mistake.
    - A self-loop (`from == to`) appears anywhere. The `from == to` early return handles idempotency; a literal self-loop edge would never fire. Reject with "remove this entry; self-transitions are implicit."
    - `by (Any)` appears alongside a concrete role (`by (Any, Coordinator)`). Ambiguous: `Any` and "this specific role" are not composable.
    - `role = <path>` is missing or malformed (not a Rust path).
- **Round-trip compatibility with v4's YAML** (reference only, not required at runtime). A short conversion note in the design describes how `work.yml` becomes the `#[fsm(transitions(...))]` block, so the v4 definitions port mechanically. The YAML is not loaded at runtime; it just informs the new annotation.
- **Exhaustive unit tests** in a consumer test crate (`crates/derive/tests/` - integration tests, because proc-macro crates can't unit-test their own macros). Tests cover every generated method against `work`-like and `plan`-like fixtures, plus the failure cases that v4's `fsm/tests.rs` already pins.

### Non-Goals

- **Runtime guards.** v4's `guards: { condition: deps-satisfied }` pattern is strictly out of scope. Guards are domain state that the derive cannot see (a `Work`'s deps live in TaskStore, not in the enum). Consumers layer guards on top of `validate_transition` by writing a hand-rolled `fn check_deps_ready(&self) -> Result<(), GuardError>` that runs BEFORE the FSM call. The derive guarantees "this transition is legal" (structural + role), not "this transition is safe right now" (guard).
- **YAML loading at runtime.** v5 has no `resources/engine/fsm/` directory. There is no `FsmInterpreter`. The derive reads annotations at macro expansion only. If someone needs to edit an FSM after release, they edit Rust source and rebuild.
- **Dynamic registry / cross-FSM dispatch.** v4's `validate_transition(fsm_name, ...)` dispatch is gone. Each enum has its own inherent methods; callers that need polymorphic FSM access (e.g., a generic "transition any record" function) implement a trait manually over the concrete types. v5's taskstore-traits already supplies `Record`; a `Fsm` trait is left as a Stage 5+ addition if it earns one.
- **Attribute macros** (`#[fsm] fn foo(...) { ... }`). The derive crate's CLAUDE.md forbids them. The `#[fsm(...)]` helper attribute used INSIDE a `#[derive(Fsm)]` invocation is a derive helper, registered via `#[proc_macro_derive(Fsm, attributes(fsm))]`; it only exists during expansion and never applies to a free item.
- **Function-like macros.** Same rule. No `fsm_table!(...)` or `transition!(...)`.
- **Persistence of state history.** How a record's status history gets serialized to TaskStore is the `#[derive(Record)]` design's concern. This derive only validates transitions.
- **Graph visualization / dot export.** v4 had a `loopr fsm graph` subcommand that emitted DOT. v5 may want it later; not Stage 5 scope.
- **Per-transition side-effects (`on_enter`, `on_exit`).** Lifecycle hooks are consumer-side code. The derive does not generate any transition-handler dispatch.

## Proposed Solution

### Overview

`#[derive(Fsm)]` is a standard proc-macro derive with a single helper attribute `#[fsm(...)]`. It attaches only to unit-variant enums. Every piece of the FSM (states, terminal states, transitions, overrides, role enum path) lives inside the single `#[fsm(...)]` attribute on the enum itself; the macro sees the enum + the attribute and has no awareness of subsequent `impl` blocks. §Data Model shows the full input shape.

The macro output for WorkStatus is a single `impl` block with the methods in §API Design and two private `const` slices inlined into the method bodies (the derive does not expose the raw edge tables). There is no free-standing `FsmEdge` slice at the item level; the edges show up as `match (from, to) { (Self::A, Self::B) => &[Role::X, Role::Y], ... }` arms inside `validate_transition`. §API Design walks through the exact generated body.

The runtime support types (`Transition`, `FsmError<S>`, `FsmErrorKind`, `TargetKind`) are declared in `crates/domain/src/fsm.rs`. Since `derive` itself cannot export runtime types (it is a `proc-macro = true` crate), generated code references them through fully-qualified `::domain::...` paths so consumers don't need to add a `use` statement.

### Architecture

```
crates/derive/
├── Cargo.toml              + proc-macro2, syn, quote
├── CLAUDE.md               (unchanged)
├── src/
│   ├── lib.rs              proc-macro entry, `#[proc_macro_derive(Fsm, attributes(fsm))]`
│   ├── fsm/
│   │   ├── mod.rs          parse + validate + emit
│   │   ├── parse.rs        parse the enum + helper attribute into an IR
│   │   ├── validate.rs     compile-time checks (terminal-has-no-out-edges, etc.)
│   │   └── emit.rs         quote!-driven codegen
└── tests/
    └── fsm.rs              integration tests: derives a test enum, exercises every method

crates/domain/
├── src/
│   ├── lib.rs              + mod fsm; pub use fsm::*;
│   ├── fsm.rs              runtime types: FsmEdge<S>, Transition, FsmError<S>, FsmErrorKind, TargetKind
│   └── role.rs             pub enum Role { Coordinator, Integrator, ... } (shared by all derive-consuming enums)
```

`crates/derive` gains `[dependencies]`: `proc-macro2 = "1"`, `syn = { version = "2", features = ["full", "extra-traits"] }`, `quote = "1"`. Added via `cargo add` at implementation time.

`crates/domain` hosts the runtime support types. This is the only runtime surface — the derive's output references `::domain::*` paths.

The derive crate does NOT depend on `domain` (it can't — `domain` wants to use the derive, forming a cycle). The paths emitted in generated code are textually qualified at `::domain::...` and resolved at the consumer's compile time, where `domain` is on the path.

### Data Model

**Required derives on the enum.** The generated code matches on `Self` values, uses `[T]::contains`, passes `Self` by value, and `{:?}`-formats it in error messages. The derive therefore requires `Debug + Clone + Copy + PartialEq + Eq` on the attached enum, and the expansion does NOT auto-emit them. Missing derives surface as a rustc native "trait bound not satisfied" error at the consumer's compile (the derive intentionally does not pre-check, because rustc's error already points at the exact method call that needs the missing trait). No `Hash` is needed.

**Mini-grammar for the `#[fsm(...)]` helper attribute:**

```
fsm_attr    := "#[fsm(" fsm_arg ("," fsm_arg)* ","? ")]"

fsm_arg     := "role"        "=" path
             | "terminal"    "=" "[" ident ("," ident)* ","? "]"
             | "transitions" "(" transition ("," transition)* ","? ")"
             | "overrides"   "(" transition ("," transition)* ","? ")"

transition  := ident "=>" ident "by" "(" role_list ")"

role_list   := "Any"
             | ident ("," ident)*

ident       := a variant name of the attached enum
             | (inside by-lists) a variant name of the `role = ...` enum
path        := a full Rust path expression, e.g. `Role` or `::domain::Role`
```

Argument order inside `#[fsm(...)]` is free; the macro parses each top-level `fsm_arg` by name. Every concrete edge must be listed; there is no wildcard syntax.

**Input (what the user writes):**

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq, Fsm)]
#[fsm(
    role = ::domain::Role,
    terminal = [Done, Superseded, Abandoned],
    transitions(
        Draft      => Pending     by (Coordinator),
        Draft      => Ready       by (Coordinator),
        Draft      => Superseded  by (Coordinator, Director),
        Draft      => Abandoned   by (Coordinator, Director),
        Pending    => Ready       by (Coordinator),
        Pending    => Superseded  by (Coordinator, Director),
        Pending    => Abandoned   by (Coordinator, Director),
        Ready      => InProgress  by (Coordinator),
        Ready      => Blocked     by (Coordinator),
        Ready      => Superseded  by (Coordinator, Director),
        Ready      => Abandoned   by (Coordinator, Director),
        Ready      => Done        by (Coordinator),
        InProgress => Blocked     by (Any),
        InProgress => InReview    by (Implementer),
        InProgress => Superseded  by (Coordinator, Director),
        InProgress => Abandoned   by (Coordinator, Director),
        Blocked    => Ready       by (Coordinator),
        Blocked    => Superseded  by (Coordinator, Director),
        Blocked    => Abandoned   by (Coordinator, Director),
        InReview   => InProgress  by (Coordinator),
        InReview   => Integrated  by (Integrator),
        InReview   => Superseded  by (Coordinator, Director),
        InReview   => Abandoned   by (Coordinator, Director),
        Integrated => Done        by (Coordinator, Integrator),
        Integrated => Abandoned   by (Coordinator, Director),
    ),
    overrides(
        InProgress => Ready     by (Coordinator),
        InProgress => InReview  by (Coordinator),
        InReview   => Ready     by (Coordinator),
    ),
)]
pub enum WorkStatus { /* variants as above */ }
```

Syntax highlights:

- `terminal = [...]`: comma-separated variant idents in brackets. The macro checks each is a variant of the enum.
- `transitions(...)` / `overrides(...)`: parenthesized list of `From => To by (Roles...)` entries.
- `by (Any)`: sugar for "no authorization required"; expands to an empty role slice.
- `by (Coordinator, Director)`: each entry is a `::` path relative to the `role = ...` root; the macro emits `Role::Coordinator`, `Role::Director`.
- Each transition entry ends with a comma. Trailing commas allowed.

**IR during macro expansion:**

```rust
struct FsmIr {
    enum_ident: syn::Ident,
    variants: Vec<syn::Ident>,
    role_path: syn::Path,
    terminal: Vec<syn::Ident>,
    transitions: Vec<EdgeIr>,
    overrides: Vec<EdgeIr>,
}

struct EdgeIr {
    from: syn::Ident,
    to: syn::Ident,
    by: Vec<syn::Ident>, // empty vec means "Any"
}
```

**Parser-level keywords** (NOT enum variants):

- `Any` — inside a `by (...)` list, means "no role restriction." Expands to an empty role slice; callers with any role are authorized. The macro rejects `Any` if it appears alongside a concrete role (`by (Any, Coordinator)` is ambiguous; compile error).

**Runtime support types (in `crates/domain/src/fsm.rs`):**

```rust
/// Outcome of a successful validate_transition / validate_override call.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum Transition {
    /// from == to; idempotent, no change recorded.
    Unchanged,
    /// Normal-table transition accepted.
    Changed,
    /// Override-table transition accepted (only validate_override returns this).
    Override,
}

/// What `valid_targets` reports per returned target.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum TargetKind {
    Normal,
    Override,
}

/// Error type emitted by validate_transition / validate_override.
/// Carries full context for a rich Display impl; constructed only on rejection paths.
#[derive(Debug)]
pub struct FsmError<S: 'static + std::fmt::Debug + Copy> {
    pub from: S,
    pub to: S,
    /// The role value rendered once as a string at error construction.
    /// We use `strum::Display` (derived on Role) so the kebab-case wire form
    /// appears in error messages: `"coordinator"`, not `"Coordinator"`.
    /// Storing a String here instead of `Role` lets `FsmError<S>` stay
    /// generic only over the status enum - records with different role
    /// enums (if that ever matters) stay compatible.
    pub role: String,
    pub kind: FsmErrorKind,
    /// Valid normal-table targets reachable from `from`. Each entry is
    /// `(target_state, &[authorized_role_names])`: the inner slice holds
    /// role names as static strings in the strum::Display form, exactly
    /// the way they should appear in Display output. `&'static` because
    /// the macro emits the whole thing as a const, one slice per `from`.
    /// Empty inner slice means "any role" (came from `by (Any)`).
    pub valid_normal: &'static [(S, &'static [&'static str])],
    /// Same shape as `valid_normal`, populated from the `overrides(...)` table.
    pub valid_override: &'static [(S, &'static [&'static str])],
    /// Populated only by validate_override when BOTH normal and override
    /// paths fail: holds the normal-path error so Display can chain the two
    /// rejection reasons in a single message. validate_transition always
    /// leaves this as None. Depth is at most 1 (never chained deeper) -
    /// callers that pattern-match on FsmError only need to handle one level.
    pub context: Option<Box<FsmError<S>>>,
}

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum FsmErrorKind {
    /// No edge (normal or override) from `from` to `to`.
    NoTransition,
    /// Edge exists, but `role` is not in the `by` list.
    RoleNotAuthorized,
}

impl<S> std::error::Error for FsmError<S> where S: 'static + std::fmt::Debug + Copy {}
impl<S> std::fmt::Display for FsmError<S> where S: 'static + std::fmt::Debug + Copy { /* see §API Design */ }
```

Design choices pinned in Pass 2:

- `FsmError::role` is `String`, not `&'static str`. The generated code calls `role.to_string()` (via `strum::Display`) once at construction, avoiding a `Role` type parameter on `FsmError<S>`. The one-allocation cost is negligible because errors are rare.
- The authorizing-roles slice stored in `valid_normal` / `valid_override` is `&'static [&'static str]` — the strings are emitted as const literals at macro expansion (`"coordinator"`, `"director"`, etc.). This is separate from the runtime-passed `role: Role` value; the two never need to share a type.
- `FsmErrorKind::NotOverridable` was removed in Pass 2 as speculative — no Stage 5 caller needs it. Add back only when a strict/lax caller split exists.

### API Design

**Generated inherent methods on the enum:**

```rust
impl WorkStatus {
    /// All variants of this enum, declaration order.
    pub const fn all_states() -> &'static [Self] { &[Self::Draft, Self::Pending, /* ... */] }

    /// Variants declared terminal in `#[fsm(terminal = [...])]`.
    pub const fn terminal_states() -> &'static [Self] { &[Self::Done, Self::Superseded, Self::Abandoned] }

    /// `true` if `self` is one of the terminal states.
    pub fn is_terminal(self) -> bool { Self::terminal_states().contains(&self) }

    /// Normal transition check: `from` -> `to` must be in the normal table, and
    /// `role` must be in the edge's `by` list (or the list must be empty).
    ///
    /// Returns `Transition::Unchanged` if `from == to` (idempotent);
    /// `Transition::Changed` on a normal-table hit; `Err` otherwise with rich context.
    pub fn validate_transition(from: Self, to: Self, role: Role) -> Result<Transition, FsmError<Self>>;

    /// Try `validate_transition` first; on failure, check the override table.
    /// Returns `Transition::Override` on override-table hit.
    pub fn validate_override(from: Self, to: Self, role: Role) -> Result<Transition, FsmError<Self>>;

    /// Every state reachable from `from` by the given role, normal + override.
    /// Used by `loopr fsm describe work` and test fixtures.
    ///
    /// **Ordering contract:** normal-table targets first, then override-table
    /// targets. Within each group, order matches the source-order of the
    /// corresponding `transitions(...)` / `overrides(...)` block as written
    /// in the `#[fsm(...)]` attribute. Tests may depend on this; the derive
    /// emits `match` arms in source order, which is deterministic.
    pub fn valid_targets(from: Self, role: Role) -> Vec<(Self, TargetKind)>;
}
```

**Method-name collisions.** The derive generates a fixed set of inherent method names on the target enum: `all_states`, `terminal_states`, `is_terminal`, `validate_transition`, `validate_override`, `valid_targets`, plus two underscore-prefixed `#[doc(hidden)]` helpers (`_normal_targets_from`, `_override_targets_from`). A consumer who writes their own `impl Status { fn validate_transition() { ... } }` gets a duplicate-definition error. That error is rustc-native and points at the user's impl block (good enough); the derive does not try to pre-check. These method names are reserved by the derive on any type that carries `#[derive(Fsm)]`.

**Lookup implementation (all const-time-generated inside the derive):**

The generated `validate_transition` is a `match` over `(from, to)` tuples (generated from the `transitions(...)` block), checking role membership inline:

```rust
pub fn validate_transition(from: Self, to: Self, role: Role) -> Result<Transition, ::domain::FsmError<Self>> {
    if from == to {
        return Ok(::domain::Transition::Unchanged);
    }
    // One `match` arm per normal-table edge. The role slice holds real Role values.
    let authorized: &[Role] = match (from, to) {
        (Self::Draft,      Self::Pending)    => &[Role::Coordinator],
        (Self::Draft,      Self::Ready)      => &[Role::Coordinator],
        (Self::InProgress, Self::Blocked)    => &[],                              // `by (Any)` expands to empty slice
        (Self::InProgress, Self::InReview)   => &[Role::Implementer],
        // ... one arm per normal-table edge ...
        _ => return Err(::domain::FsmError {
            from, to,
            role: role.to_string(),                                               // strum::Display
            kind: ::domain::FsmErrorKind::NoTransition,
            valid_normal: Self::_normal_targets_from(from),
            valid_override: Self::_override_targets_from(from),
            context: None,
        }),
    };
    if authorized.is_empty() || authorized.contains(&role) {
        Ok(::domain::Transition::Changed)
    } else {
        Err(::domain::FsmError {
            from, to,
            role: role.to_string(),
            kind: ::domain::FsmErrorKind::RoleNotAuthorized,
            valid_normal: Self::_normal_targets_from(from),
            valid_override: Self::_override_targets_from(from),
            context: None,
        })
    }
}

// Private helper, also generated. One arm per `from` state; each returns a
// `&'static [(Self, &'static [&'static str])]` that the macro constructed at
// expansion from the `transitions(...)` block.
#[doc(hidden)]
const fn _normal_targets_from(from: Self) -> &'static [(Self, &'static [&'static str])] {
    match from {
        Self::Draft      => &[(Self::Pending, &["coordinator"]), (Self::Ready, &["coordinator"]), /* ... */],
        Self::InProgress => &[(Self::Blocked, &[]), (Self::InReview, &["implementer"]), /* ... */],
        // ... one arm per from-state that has outgoing edges; every other arm returns &[]
        _ => &[],
    }
}
```

`role.to_string()` calls `strum::Display` which emits the kebab-case form (`"coordinator"`, `"director"`). The `Role` enum in `crates/domain/src/role.rs` derives `strum::Display` with `#[strum(serialize_all = "kebab-case")]` so every error message shows canonical role names.

The `match` over `(from, to)` lets the compiler generate the tightest dispatch it knows how (jump-table or binary search, depending on enum density). No HashMap allocation, no linear scan of a slice.

`validate_override`:

```rust
pub fn validate_override(from: Self, to: Self, role: Role) -> Result<Transition, ::domain::FsmError<Self>> {
    match Self::validate_transition(from, to, role) {
        Ok(t) => Ok(t),
        Err(normal_err) => {
            // Generated from the `overrides(...)` block, identical structure to the normal-table match.
            let authorized: &[Role] = match (from, to) {
                (Self::InProgress, Self::Ready)    => &[Role::Coordinator],
                (Self::InProgress, Self::InReview) => &[Role::Coordinator],
                (Self::InReview,   Self::Ready)    => &[Role::Coordinator],
                _ => return Err(::domain::FsmError {
                    from, to,
                    role: role.to_string(),
                    kind: ::domain::FsmErrorKind::NoTransition,
                    valid_normal: Self::_normal_targets_from(from),
                    valid_override: Self::_override_targets_from(from),
                    context: Some(Box::new(normal_err)),
                }),
            };
            if authorized.is_empty() || authorized.contains(&role) {
                Ok(::domain::Transition::Override)
            } else {
                Err(::domain::FsmError {
                    from, to,
                    role: role.to_string(),
                    kind: ::domain::FsmErrorKind::RoleNotAuthorized,
                    valid_normal: Self::_normal_targets_from(from),
                    valid_override: Self::_override_targets_from(from),
                    context: Some(Box::new(normal_err)),
                })
            }
        }
    }
}
```

**`Display` impl on `FsmError`:**

```
invalid transition: InProgress -> Done (role: implementer)
  valid from InProgress (normal): Blocked (any), InReview (implementer), Superseded (coordinator, director), Abandoned (coordinator, director)
  valid from InProgress (override): Ready (coordinator), InReview (coordinator)
```

The state names use `{:?}` (PascalCase from the enum) and the role names use strum's kebab-case form. This splits the difference between v4's all-kebab-case output and the natural Rust typing; the design rationale is that state values ARE the typed enum and should read as such, while roles are deliberately symbolic strings in the wire-protocol sense. See §Technical Considerations - Testing for the snapshot test that pins the format.

## Alternatives Considered

### Alternative 1: Keep v4's YAML-interpreter model (no derive at all)

- **Description:** `resources/engine/fsm/*.yml` loaded by `crates/domain::FsmInterpreter` at startup. Every `Status` enum has a sibling `&str` name and `validate_transition(fsm_name, ...)` does HashMap lookups.
- **Pros:** Zero-cost to port v4's FSM definitions; already working in v4; no proc-macro debt; editing an FSM post-release is an edit-deploy rather than rebuild.
- **Cons:** The whole v5 thesis in `docs/vision.md` is that seam-drift bugs come from string-keyed runtime dispatch. Keeping `FsmInterpreter` preserves exactly the failure class v5 was built to eliminate. `fsm_name` typos, state typos, role typos, and edge typos all survive compile.
- **Why not chosen:** vision.md §domain pins "compile-time mismatch, not a runtime YAML lookup." Rejecting the derive would require a vision revision.

### Alternative 2: Function-like macro (`fsm_table!(Status, transitions = [...])`)

- **Description:** Don't use derive; use `fsm_table!` as a top-level macro that produces both the enum and the impl in one go.
- **Pros:** Slightly less syntax at the use site; no need for a separate `#[fsm(...)]` helper attribute.
- **Cons:** `crates/derive/CLAUDE.md` explicitly forbids function-like macros: "They hide expansion, encourage DSL-style 'magic', and re-introduce the string-keyed-dispatch failure class v5 is built to avoid." A function-like macro that declares the enum also obscures the enum definition from rust-analyzer's "go to definition" — the rustc output reveals the enum but the source is the macro call.
- **Why not chosen:** direct CLAUDE.md violation. Derives + helper attributes are explicitly allowed; function-like macros explicitly forbidden.

### Alternative 3: Manual `impl Fsm for WorkStatus { ... }` for every record (no derive)

- **Description:** Consumers write the transition table by hand as a `const TRANSITIONS: &[FsmEdge<Self>] = &[...]` and hand-write `validate_transition`. No macro crate needed.
- **Pros:** Zero proc-macro machinery; the derive's debug burden goes away.
- **Cons:** Every record (Plan, Work, Spec, Phase, Bundle, Tick, and the coordinator FSM) repeats the same ~100 lines of boilerplate, differing only in state names. Eight copies of the same algorithm is exactly the maintenance hazard v4's YAML approach was designed around. Also loses v4's rich-error output unless every consumer hand-writes that too.
- **Why not chosen:** the derive's sole purpose is eliminating that duplication. Hand-writing is a reasonable fallback if the derive implementation takes longer than Stage 5 can afford, but not a permanent model.

### Alternative 4: Runtime `Fsm` trait + generic `FsmInterpreter<S>` (half-runtime, half-compile)

- **Description:** Keep a runtime interpreter, but parameterize it on a `Status: 'static` enum. Each record defines `impl Fsm for Status { fn definition() -> &'static FsmDefinition { ... } }` and the interpreter reads that at runtime.
- **Pros:** Halfway between v4 and the pure-derive approach. Typos at the enum boundary are compile errors; table contents remain data-driven.
- **Cons:** Still has a runtime interpreter layer; still stringifies states for lookup unless the trait returns typed `FsmEdge<Self>` slices (in which case why not just generate the methods directly?). Combines the debug surface of "runtime interpreter" with the code volume of "typed tables." No wins over the derive.
- **Why not chosen:** strictly dominated by the derive in both correctness and ergonomics.

### Alternative 5: derive-macro expansion into a runtime registry (consumers opt into a `FsmRegistry<'a>`)

- **Description:** Derive emits a `register_with(registry: &mut FsmRegistry)` fn; the daemon populates a registry at startup by calling each record's register fn. Legal-transition checks go through the registry.
- **Pros:** Cross-FSM dispatch works (`FsmRegistry::validate("work", "ready", "in-progress", "coordinator")`).
- **Cons:** Resurrects v4's `fsm_name` string dispatch. Polymorphic-over-status-type access is a Stage 7+ speculative need; no concrete Stage 5 or 6 caller needs it.
- **Why not chosen:** speculative; add if Stage 7 actually demands it.

## Technical Considerations

### Dependencies

Added to `crates/derive/Cargo.toml`:

- `proc-macro2 = "1"` — token streams.
- `syn = { version = "2", features = ["full", "extra-traits"] }` — parse derive input + helper attribute. `extra-traits` gives Debug impls for syn types, useful during macro development.
- `quote = "1"` — emit token streams from templates.

Added to `crates/domain/Cargo.toml`:

- `strum = { workspace = true, features = ["derive"] }` — for `Role`'s Display (kebab-case) impl.

All added via `cargo add` at Phase 1/2 start, not speculatively.

No runtime deps added to downstream consumers (the generated code references only `core`, the consumer's enum variants, and `::domain::*` support types).

**Dev-dep shape (subtle but correct).** `crates/derive` has no normal dep on `domain` — the generated code references `::domain::*` paths symbolically and they resolve at the CONSUMER's compile time. But `crates/derive/tests/fsm.rs` needs the real `domain` symbols to link against fixture enums that use the derive. So `derive`'s `[dev-dependencies]` pulls `domain = { path = "../domain" }`. `domain`'s normal `[dependencies]` pulls `derive = { path = "../derive" }`. This creates the appearance of a cycle, but cargo accepts it because `derive`'s dev-dep graph and `domain`'s normal-dep graph are separate: the non-test `cargo build -p derive` has no `domain` edge. Confirmed on every workspace cargo understands this pattern (see `scottidler/taskstore` for a production precedent).

### Performance

- **`is_terminal`**: single `&[Self]::contains` over a slice of at most 4 variants. Inlines to a few compares.
- **`validate_transition`**: one `match (from, to)` over at most ~30 edges, then one `&[Role]::contains` over at most ~4 roles. Rust's match codegen makes this O(1) in practice for small enums (jump table) and O(log N) for sparse ones (binary search). No allocations.
- **`validate_override`**: at most 2x `validate_transition` cost on the failing-normal path; on the happy-normal path it's identical to `validate_transition`.
- **`valid_targets`**: one `Vec<(Self, TargetKind)>` allocation sized at most ~8 entries; negligible.
- **`FsmError` construction**: happens only on rejection paths. The `valid_normal` / `valid_override` slices are const-generated per `from` state, so no allocation. The single `Box<FsmError<S>>` for chained context allocates once on override failure; override failures are user-facing errors and already slow; the allocation is noise.

Expected allocation count per successful transition validation: **zero**. Per rejected transition: **zero** for `validate_transition` (all data comes from const tables), **one** for `validate_override` (the `Box<FsmError>` for chaining).

### Security

- Proc macros run at compile time with full user privilege. A malicious FSM annotation could theoretically emit arbitrary Rust. This derive's parser rejects anything it doesn't explicitly understand; emitted tokens are fully data-driven (no user-controlled raw token forwarding). Surface is equivalent to any other proc macro in the workspace.
- No runtime secrets handled. No I/O. No network. No subprocess execution.

### Testing Strategy

- **Integration tests in `crates/derive/tests/fsm.rs`**: the standard proc-macro testing approach (proc-macro crates can't unit-test their own macros). Derives are applied to fixture enums inside test modules; assertions exercise every generated method.
- **`trybuild` compile-fail tests** in `crates/derive/tests/compile-fail/` for the validation paths:
    - `terminal_has_outgoing_edge.rs` — expects compile error.
    - `variant_not_in_enum.rs` — expects compile error.
    - `duplicate_transition.rs` — expects compile error.
    - `non_unit_variant.rs` — expects compile error.
    - `wrong_role_path.rs` — expects compile error (typoed role name).
- **Snapshot tests** for `FsmError::Display` rendering.
- **Fuzz-ish sweep test**: `for every (from, to) in all_states × all_states { for every role in Role::iter() { assert validate_transition behaves consistently with the annotation }}`.

### Rollout Plan

- **Phase 1 - 4 land as sequential commits on `v5` branch.** Each phase ends with `otto ci` green inside `crates/derive` and at the workspace root.
- **No tag between phases.** The four commits bump to `v0.5.8` at the end (patch bump per `memory/project-v5-branch-versioning.md`).
- **Consumers (Stage 5 records) land in later commits.** This doc ships the derive + runtime support types; `domain::Plan`, `domain::Work`, etc. derive `Fsm` in Stage 5 design docs, not here.
- **No coexistence window with v4 FSM interpreter.** v5 never imports `FsmInterpreter`. The YAML files in `resources/engine/fsm/` are not copied into v5. Port happens once, as annotations in Stage 5+ records.

## Risks and Mitigations

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| `syn::meta::ParseNestedMeta` ergonomics for the `#[fsm(...)]` grammar surface are clumsy enough that parsing becomes a tar pit | Medium | Medium | Keep the grammar narrow (five top-level keys, no nested conditionals). Implement parsing with a hand-rolled recursive descent over `ParseStream` if `ParseNestedMeta` chafes. Budget the Phase 2 spike for "ditch ParseNestedMeta if it fights back"; escape valve is raw `Punctuated<Meta, Token![,]>`. |
| `FsmError<S>` carrying `Box<FsmError<S>>` for chained context leaks into public error types and forces downstream error enums to box | Low | Low | `FsmError` implements `std::error::Error`; consumers wrap it in their own `DomainError` via `#[from]` as usual. No contagion. |
| Const tables for `valid_normal` / `valid_override` grow large for dense FSMs (e.g., a 20-state record with 100+ edges) | Low | Low | v4's largest FSM (`work`) has 10 states and ~26 edges. First-gate FSMs are all under that size. If a future FSM blows up, move to a hand-rolled trait impl for that one enum; derive stays for the common case. |
| `match (from, to)` with 30+ arms generates code that blows up in debug builds / slows rust-analyzer | Low | Low | 30 arms is negligible; std lib has match statements an order of magnitude larger without issue. If it becomes a measurable hit, switch emission to a `&[(Self, Self, &[Role])]` slice + linear scan — same API surface, different codegen. Easy local swap. |
| Two records need slightly different Role sets (e.g., `BundleStatus` has a `Reviewer`-only edge that `WorkStatus` doesn't) | Medium | Low | `Role` is shared across all records; every record accepts any role value and the transition table decides what's authorized. Not a real issue; flagged for clarity. |
| Stage 5 discovers the derive shape doesn't match what `Plan`'s FSM needs (e.g., Plan has no "role" concept) | Low | Medium | `by (Any)` sugar covers role-free FSMs. If a Plan transition is `Draft => Ready` with no role gate, the annotation is `Draft => Ready by (Any)` and the generated code never checks role. No special handling needed. |
| Override-table inclusion cost: for records with no overrides, we still emit an empty second `match` | Low | Low | An empty match is optimized to an `_` arm returning the chained error immediately; zero runtime cost. If macro-expansion size becomes an issue (unlikely), skip emitting the override arm when the table is empty. |
| Consumer forgets `use domain::Role` | Medium | Low | The derive emits fully-qualified `::domain::Role` paths in all internal references; the user only needs to have `domain` on their `Cargo.toml` dependency list, which it is for every record consumer. Error messages reference `Role` by its Debug repr, requiring no use-statement in the error path. |

## Open Questions

- [ ] **Should `Role` live in `domain` or a new `roles` crate?** Current draft: `domain`. Argument for separating: `domain` should be the pure symbol layer (records + FSM); `Role` is an authorization axis, not a record. Argument for keeping: every record consumer already depends on `domain` for records; adding a sibling crate for one enum is overhead. Decision deferred to Stage 5 records design; this doc reserves space.
- [ ] **`validate_transition` signature: free fn or method on `self`?** Current draft: `fn validate_transition(from: Self, to: Self, role: Role) -> ...`. Alternative: `fn validate_transition(self, to: Self, role: Role) -> ...` (`self` is `from`). Free-fn is marginally more verbose at call sites; method has ambiguity with `self` as the record vs. the status. Stick with free-fn — the Status enum is the subject, not "a record instance."
- [ ] **FsmError nesting depth limit.** `validate_override` chains one error. If a future caller invokes `validate_super_override` that tries both tables again, the chain could grow. Current draft: depth is always 0 (normal) or 1 (override). If a deeper chain is ever needed, switch `context: Option<Box<FsmError<S>>>` to `Vec<FsmError<S>>`. Not a Stage 5 concern.
- [ ] **`Any` in role lists vs. omitted `by (...)`.** Current draft syntax requires `by (Any)` explicitly; no implicit "empty role list". Reasoning: explicit is auditable (a grep for `by (Any)` finds every un-gated transition). Open to reversing if it reads as noise.
- [ ] **Status enum representation for serialization.** Status enums are serialized into TaskStore via `#[derive(Record)]`. The Fsm derive doesn't care about serialization, but the kebab-case wire representation (`in-progress` vs `InProgress`) needs a decision somewhere. Current draft: out of scope for this doc; Record derive handles it. Flagged so the Fsm design isn't accidentally coupled to the serde choice.

## Addendum A: Lessons Learned (v3 → v4 → v5)

The historical provenance of this design matters because the roadmap entry ("port `#[derive(Fsm)]` from v4's `loopr-derive`") is misleading. The actual arc:

- **v3** (`~/repos/scottidler/loopr`, v0.1.121) shipped `#[derive(Fsm)]` with per-variant `#[transitions(...)]` / `#[overrides(...)]` attributes and hardcoded `crate::...` paths in the generated code.
- **v4** (`~/repos/scottidler/loopr-v4`, v0.1.141) **deleted the derive** and moved every FSM to YAML files at `resources/engine/fsm/*.yml`, loaded at startup by a runtime `FsmInterpreter` that did string-keyed HashMap lookups.
- **v5 is reviving v3's compile-time approach** with v4's rich-error lessons baked in, and it is not a direct port of either.

### Side-by-side

| Dimension | **v3** | **v4** | **v5** (this design) |
|---|---|---|---|
| Shape | `#[derive(Fsm)]` proc-macro | `FsmInterpreter` runtime (YAML) | `#[derive(Fsm)]` proc-macro |
| Transition location | Per-variant `#[transitions(...)]` / `#[overrides(...)]` attrs on each variant | `resources/engine/fsm/{work,bundle,tick,agent,hierarchy}.yml`, `rust-embed`'d | Single `#[fsm(...)]` helper attr on the enum (one place to read) |
| Call shape | `self.status.validate_transition(target, role)` — method on `Self` | `fsm.validate_transition(fsm_name, from_str, to_str, role_str)` — 4 strings | `WorkStatus::validate_transition(from, to, role)` — free fn, typed |
| Terminal declaration | Inferred (variants with no `#[transitions]`) | YAML `terminal: [...]` key | Explicit `terminal = [Done, ...]` in attr |
| "Any role" syntax | Empty parens or bare variant | YAML `by: []` | Explicit `by (Any)` keyword |
| Role type wiring | Hardcoded `crate::domain::role::Role` in generated code | Runtime `&str` compared against YAML `by: [...]` | Consumer-provided via `#[fsm(role = ::domain::Role)]`; `derive` crate has no `Role` dep |
| Error type | Hardcoded `crate::error::LooprError::InvalidTransition` | `eyre::Result` with rich hints | `::domain::FsmError<S>` with const-generated hints; no `eyre` in the API |
| Typo safety | `Intergrated` → compile error | `"intergrated"` → runtime "unknown FSM transition" | `Intergrated` → compile error (same as v3) |
| `fsm_name` dispatch | n/a (scoped to the enum) | Required: 5 string keys | n/a (scoped to the enum) |
| Rich error hints | Terse: `{from, to, role}` only | Full: "valid targets from X: A (any), B (coordinator), ..." | Same as v4 (const-generated at expansion) |
| Lookup cost | Single `match (Self, Self)` with `_ => false` | HashMap double-lookup + role-vec linear scan + String alloc per error | Single `match (Self, Self)` returning `&[Role]`, role-slice `contains` |
| Editable without rebuild | No | Yes | No |

### What v5 carries forward **from v3**

- The whole proc-macro shape. v3 proved a compile-time derive is practical for the 5-6 FSMs in the domain.
- The `validate_transition` / `validate_override` / `is_terminal` method trio.
- Match-based dispatch over `(from, to)` tuples — the compiler's natural jump-table for small enums.

### What v5 carries forward **from v4**

- Rich error output with "valid targets" hints. v3's `InvalidTransition { from, to, role }` was terse; v4's YAML interpreter printed "valid targets from `ready`: `in-progress (coordinator), blocked (coordinator), ...`". v5 pre-generates those hint slices at macro-expansion and stashes them in `FsmError::valid_normal` / `valid_override` so the rich output is free at runtime.
- Kebab-case role names in error output (`"coordinator"`, not `"Coordinator"`), via `strum::Display` on `Role`. v3 used `{:?}` (PascalCase). v4's wire-format names win for grep-ability across logs.

### What v5 corrects about **v3**

1. **Transition-table location.** v3 sprinkled `#[transitions(...)]` across every variant. Reading the full FSM requires scanning the whole enum. v5 puts the entire machine in one `#[fsm(...)]` attribute on the enum - one place to read, one place to audit.
2. **Hardcoded `crate::...` paths.** v3's generated code references `crate::domain::role::Role`, `crate::error::LooprError`, `crate::domain::transition::Transition`. The derive only works inside loopr; it cannot be reused. v5 takes `Role` via `#[fsm(role = ...)]` and references support types as `::domain::*`. v5's `derive` crate has ZERO deps on `domain`, so the two crates can be re-organized independently.
3. **Implicit terminal detection.** v3 treats a variant without `#[transitions]` as terminal. Easy to trip over: comment out a transition for debugging, the variant silently becomes terminal. v5 requires `terminal = [...]` explicitly.
4. **Empty parens for "any role".** v3's `Blocked` (bare) vs `Blocked(Coordinator)` is subtle; missing parens is easy to typo. v5's `by (Any)` is an unmissable keyword.
5. **Compile-time rejection of nonsense.** v3's derive doesn't check terminal-has-no-outgoing, doesn't reject zero-variant enums, doesn't reject generic enums, doesn't reject self-loops, doesn't forbid multi-`#[fsm]` attrs. v5's validate list (§Goals) runs eleven checks with spanned `compile_error!` pointing at the offending source.

### What v5 explicitly rejects from **v4**

1. **YAML-at-runtime.** v4's `FsmInterpreter` was chosen to allow editing FSMs without rebuild. In practice no one ever edited the YAML in a deployed install, but every caller paid the stringified-lookup cost forever. `docs/vision.md` §domain pins: "compile-time mismatch, not runtime YAML lookup."
2. **String-keyed dispatch.** v4's `validate_transition(fsm_name_str, ...)` means a typo in `fsm_name` compiles. v5's enum-scoped methods make `WorkStatus::validate_transition(...)` the only call shape; the "which FSM" question is answered by which type you call it on.
3. **`eyre::Result` in the error path.** v4 boxes every error through `eyre`. v5 uses typed `FsmError<S>` so callers can `match` on `FsmErrorKind` without downcasting.
4. **`to_yaml_name()` / `fsm_name()` boilerplate.** Every v4 record had two helpers to round-trip its enum to a YAML lookup string. v5 doesn't need them - the enum IS the lookup key.

### Net

v5 is **v3 restored** (the derive shape) **plus v4's lessons absorbed** (rich errors, kebab-case roles) **minus v4's regressions** (YAML runtime, string dispatch, boxed errors).

## Addendum B: Alignment with `docs/vision.md`, `docs/roadmap.md`, crate CLAUDE.mds

Three documentation drifts surfaced during the alignment check on this design doc. All three were resolved in the same commit that landed this doc: `docs/vision.md` and `docs/roadmap.md` were updated so every source-of-truth document is internally consistent with the shipped design.

### Resolved drift 1: `FsmTransition<T>` type name (vision.md:104)

Vision originally asserted "`FsmTransition<T>` — const transition tables with role guards." The design does NOT expose a `FsmTransition<T>` type; tables are inlined into `match` arms inside the generated methods, and the derive emits no external struct for the edges. Vision updated to describe "`#[derive(Fsm)]`-generated state machines — compile-time transition dispatch with role guards expanded as `match (from, to)` arms. ... no publicly-exposed `FsmTransition<T>` wrapper type." Principle preserved; specific type name removed.

### Resolved drift 2: Design-doc location (roadmap.md Stage 5)

Roadmap originally listed `crates/derive/docs/design/fsm-macro.md`. Actual location is `docs/design/2026-04-20-fsm-macro.md` (repo root), per `crates/derive/docs/CLAUDE.md`: "Designs touching a second crate. Those go in `../../../docs/`." This design touches two crates (`derive` + `domain`). Roadmap Stage 5 entry updated to link the actual path with a short note on why it sits at the repo root.

### Resolved drift 3: "Port from v4's loopr-derive" — actually v3

Both `docs/vision.md:621` (Open Questions closed) and `docs/roadmap.md:80` (Stage 5) originally said "port from v4's loopr-derive." v4's `loopr-derive` ships only `#[derive(FlexibleEnum)]`; the Fsm derive was in **v3**'s `loopr-derive`, and v4 deleted it in favor of the YAML runtime that v5 also rejects. Both files updated: vision now says "revive `#[derive(Fsm)]` from v3's `loopr-derive` (v4 deleted it in favor of a runtime YAML interpreter that v5 also rejects)"; roadmap says "`#[derive(Fsm)]` revived from v3's `loopr-derive`." The full provenance (v3 shape + v4 lessons - v4 regressions) lives in Addendum A.
