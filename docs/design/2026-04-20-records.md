# Design Document: Plan Record Type

**Author:** Scott A. Idler
**Date:** 2026-04-20
**Status:** Implemented (shipped in v0.5.11)
**Review Passes Completed:** 5/5 + Architect

## Summary

The first concrete record type in v5. This doc defines the `Plan` struct, the `PlanStatus` state machine (six states copied verbatim from v4's proven `hierarchy.yml`), the typed-ID infrastructure (`PlanId` via a documented `id_type!` `macro_rules!` plus `generate_id` / `now_millis` helpers from v3/v4), and the minimum Stage 5 field set: five fields, one indexed, one terminal state reachable from three intermediaries. Ships the first production consumer of `#[derive(Fsm)]` (v0.5.8/9) and `#[derive(Record)]` (v0.5.10). Stage 5's exit criterion (`loopr plan "x" && loopr plan "y" && loopr list plans` → both plans; `.taskstore/plans.jsonl` → two lines) becomes reachable the moment this lands and its sibling `store.md` follows.

## Problem Statement

### Background

v4 hand-wrote 11 `impl Record for X` blocks across `src/domain/{plan,spec,phase,work,bundle,tick,coverage,validation,...}.rs`. v5 replaced that boilerplate at the meta-layer (Stage 5 Phase 1 + 2) by shipping `#[derive(Fsm)]` (v0.5.8, tightened v0.5.9) and `#[derive(Record)]` (v0.5.10). Both derives work — their test fixtures prove it — but no production record type consumes them. `crates/domain/src/lib.rs` today exports only `FsmError`, `Transition`, `TargetKind`, `Role`: runtime support types, no records.

The daemon (Stage 4, shipped) can receive a Plan request over IPC but has nothing typed to construct. Stage 5's exit criterion requires the daemon to accept `Plan` requests, persist the Plan record, and let a second invocation list both. That requires a concrete `Plan` type, a `PlanStatus` enum, a `PlanId`, and the machinery to mint and stamp fresh IDs.

### Problem

- **No Plan record type exists in v5.** `loopr plan "x"` has no typed target to construct and persist.
- **No typed IDs exist.** The Record derive's `AsRef<str>` contract on the `id` field needs something to consume. v4 used raw `String`; v5 wants newtypes (so a `WorkId` can't silently be assigned to a `Plan.id` field).
- **No shared ID-generation primitive.** v3/v4's `generate_id()` + `now_millis()` in `src/id.rs` need a v5 home.
- **No PlanStatus state machine.** Persisted Plans need a status field; the Fsm macro needs a concrete enum to attach to.
- **Seven record types will want typed IDs** across Stages 5-8 (Plan, Work, Spec, Phase, Bundle, Tick, Run). Hand-writing seven near-identical newtypes is the exact copy-paste pattern v5 is built to collapse; do it once correctly.

### Goals

- **`Plan` struct** with the minimum Stage 5 field set (`id`, `updated_at`, `created_at`, `goal`, `status`) and `#[derive(Record)]`.
- **`PlanStatus` enum** carrying v4's proven 6-state hierarchy (`Draft` / `Pending` / `Active` / `Complete` / `Superseded` / `Abandoned`) with `#[derive(Fsm)]`, role guards, and director-only override back-edges.
- **`PlanId` typed newtype** generated by an `id_type!(PlanId, "pl")` invocation.
- **`id_type!` `macro_rules!` macro** in `crates/domain/src/id.rs` that stamps out identical newtypes for future record types. Stage 5 calls it once (`PlanId`); Stage 6-8 docs will call it in their own implementation phases (`WorkId`, `SpecId`, `PhaseId`, `BundleId`, `TickId`, `RunId`). The macro itself ships complete here; future calls are pure consumers.
- **`generate_id(prefix: &str) -> String`** producing `{prefix}-{5-char-base36}`. Identical output format to v3/v4.
- **`now_millis() -> i64`** — wall-clock, milliseconds since epoch. Unchanged from v3/v4.
- **Seam tests** crossing this crate's boundary: serde round-trip for `Plan`, FSM transition coverage (accepted and rejected role paths, each normal edge, each override) for `PlanStatus`, format / uniqueness coverage for `PlanId`.
- **One-line `lib.rs` re-exports** of the public items so downstream crates (`store`, `loopr`) consume the flat path `domain::{Plan, PlanStatus, PlanId, generate_id, now_millis}`.

### Non-Goals

- **Spec / Phase / Work / Bundle / Tick / Run record types.** Each gets its own design doc in the stage that motivates it (Stage 6 for `Work` + `hierarchy.md`; Stage 7 for `Bundle`; Stage 8 for `Tick`). This doc invokes `id_type!` once, not seven times.
- **`acceptance_criteria`, `parent_id`, `tier`, `decomposition_attempts`, `bubble_up_count`.** All present on v4's `Plan`, all dead weight at Stage 5. Re-earn each in the Stage that actually consumes it. Stage 6's `hierarchy.md` owns `parent_id` and `tier`; Stage 6's `decomposer.md` owns `decomposition_attempts`; `bubble_up_count` returns only if retry escalation comes back. Adding fields with no consumer is a v5 rule #1 violation ("one design doc at a time, motivated by a failing run").
- **Plan constructor interview / clarity loop.** v4's `Draft` state existed partly to support an interactive clarity flow before a Plan activated. Stage 5's CLI just takes a goal string and persists it; Plans can be born `Active` without passing through `Draft`. The `Draft` state is kept on the enum (Stage 6+ may want it back) but `Plan::new()` sets status=`Active` immediately. Earn the interview path in the doc that reintroduces it.
- **Markdown / frontmatter emission.** v4's `Plan` implemented `DocMarkdown`. v5's markdown emission is a separate concern tracked in its own design work (see memory note `project-docs-loopr-design`); this doc covers the record shape only.
- **Store wrapper accessors.** `Store::plans().create(...)` and collection-shaped APIs live in `crates/domain/docs/design/store.md`, the fourth Stage 5 doc. This doc ends at `impl Record for Plan`.
- **Custom ID schemes per record type** (variable prefix length, phantom-typed IDs, UUIDs, ULIDs). The `id_type!` macro is intentionally rigid: 2-char prefix, 5-char base36 body, inner `String`. Any record wanting a different shape writes a manual newtype — but no current or planned v5 record wants that.
- **`IndexValue::Int` / `IndexValue::Bool`.** `Plan` has one indexed field (`status`, a stringifiable enum). Numeric indexing is a `Record`-derive follow-on when a caller needs it.
- **Defining a shared `HierarchyStatus` enum re-used by Spec / Phase.** v4 shared `HierarchyStatus` as `type PlanStatus = HierarchyStatus`. Stage 5 has no Spec and no Phase; the generalization has no current consumer. `PlanStatus` ships as a distinct enum; Stage 6 can opt Spec / Phase into sharing, or specialize. Deferred decision, one search-and-replace if they unify.

## Proposed Solution

### Overview

One struct (`Plan`), one enum (`PlanStatus`), one newtype (`PlanId`), one macro (`id_type!`), two free functions (`generate_id`, `now_millis`). Everything lives in `crates/domain/src/{plan.rs, id.rs}`. `lib.rs` re-exports the public items. No I/O. No allocations beyond what record construction inherently requires. Copy-paste-debuggable relative to v4: the FSM table, the ID format, and the helpers are byte-equivalent; only the record struct is narrowed.

Runtime shape: a daemon IPC handler receives a goal string, calls `Plan::new(goal)`, the constructor synthesizes `PlanId::new()` (wrapping `generate_id("pl")`) and `now_millis()` into a record with `status = PlanStatus::Active`, and hands it to the (future, Stage 5 doc #4) `Store` wrapper for persistence. A second invocation reads both Plan records from `.taskstore/plans.jsonl`.

```
crates/domain/
├── src/
│   ├── lib.rs        edit: add mod id; mod plan; re-export Plan, PlanStatus, PlanId,

```

### Data Model

#### PlanId (generated by `id_type!`)

```rust
// Emitted by id_type!(PlanId, "pl");
#[derive(Debug, Clone, PartialEq, Eq, Hash, Serialize, Deserialize)]
#[serde(transparent)]
pub struct PlanId(String);

impl PlanId {
    pub fn new() -> Self { Self(generate_id("pl")) }
    pub fn prefix() -> &'static str { "pl" }
}

impl AsRef<str> for PlanId {
    fn as_ref(&self) -> &str { self.0.as_ref() }
}

impl fmt::Display for PlanId {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        f.write_str(&self.0)
    }
}

impl FromStr for PlanId {
    type Err = std::convert::Infallible;
    fn from_str(s: &str) -> Result<Self, Self::Err> { Ok(Self(s.to_string())) }
}
```

Key details:

- **`#[serde(transparent)]` on the newtype is load-bearing.** Without it, serde serializes a single-field tuple struct as `["pl-abc12"]` (a one-element array). With it, the wire form is `"pl-abc12"` (the inner string) — what every Plan record needs on disk. This is the one piece of serde etiquette that makes typed IDs play nicely with JSONL persistence.
- **`AsRef<str>` satisfies the Record derive's contract.** `#[derive(Record)]` emits `::std::convert::AsRef::<str>::as_ref(&self.id)` for the `id()` method; this impl makes that resolve.
- **`FromStr` with `Infallible`.** Matches v3/v4: no ID-format validation on read. The `.taskstore/` is single-writer and trusted. Malformed IDs on disk are a human-edit bug, not an on-read concern.
- **No `Default` impl.** `new()` requires OS entropy (via `rand::rng()`) — legal but surprising behavior for `Default`. Callers write `PlanId::new()` explicitly.

#### PlanStatus (6 states, Fsm-derived)

Copies v4's `resources/engine/fsm/hierarchy.yml` verbatim into `#[fsm(...)]` attribute form:

```rust
use crate::Role;
use strum::Display;

#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash, Serialize, Deserialize, Display, Fsm)]
#[serde(rename_all = "lowercase")]
#[strum(serialize_all = "lowercase")]
#[fsm(
    role = crate::Role,
    terminal = [Complete, Superseded, Abandoned],
    transitions(
        Draft   => Pending    by (Coordinator),
        Draft   => Active     by (Coordinator),
        Draft   => Superseded by (Coordinator, Director),
        Draft   => Abandoned  by (Coordinator, Director),
        Pending => Active     by (Coordinator),
        Pending => Superseded by (Coordinator, Director),
        Pending => Abandoned  by (Coordinator, Director),
        Active  => Complete   by (Coordinator, Decomposer),
        Active  => Superseded by (Coordinator, Director),
        Active  => Abandoned  by (Coordinator, Director),
    ),
    overrides(
        Active  => Draft by (Director),
        Pending => Draft by (Director),
    ),
)]
pub enum PlanStatus {
    Draft,
    Pending,
    Active,
    Complete,
    Superseded,
    Abandoned,
}
```

Rationale for keeping v4's table unchanged:

- **Two prior iterations converged here.** v3 shipped a 5-state machine; v4's reactive-execution work (memory note `project-reactive-execution-model`) added `Pending` as the explicit "deps settled, cleared for activation" state after v3 surfaced bugs from that distinction being implicit. Restarting state design from scratch invites re-paying a debt v4 already paid.
- **Three terminals preserve reporting distinctions.** `Complete` = succeeded; `Superseded` = replaced by a later Plan (same lane, different shape); `Abandoned` = gave up. Flattening to one terminal loses information the daemon, the Store, and later-stage agents all depend on.
- **Role guards match agent seat ownership.** `Coordinator` drives normal progression; `Decomposer` gets `Active → Complete` because it's the last agent to touch a Plan before terminalization; `Director` is the escalation role and owns all `Superseded` / `Abandoned` edges plus the two override back-edges.
- **The override back-edges (`Active → Draft`, `Pending → Draft`) are Director-only.** These exist for escalation recovery: a Plan that went sideways can be kicked back to `Draft` for rework. Stage 5 has no Director agent, so override paths are latent; the FSM just refuses them for any caller that isn't Director.
- **`Draft` survives on the enum even though `Plan::new()` births Active.** Stage 6+'s clarity / interview flow may reintroduce it as the birth state. Keeping the state avoids a breaking FSM-table change when that happens; changing the birth state is a one-line edit.
- **Display output is lowercase to match the serde wire form.** `#[derive(strum::Display)] #[strum(serialize_all = "lowercase")]` aligns `format!("{}", PlanStatus::Active)` → `"active"` with `serde_json::to_string(&PlanStatus::Active)` → `"\"active\""`. This matters because `#[derive(Record)]` emits `IndexValue::String(ToString::to_string(&self.status))` for the indexed field (see `crates/derive/src/record/emit.rs:52`), so the index map value and the on-disk JSON value use the same spelling. Without the strum attribute, strum defaults to the variant name (`"Active"`), which would diverge from the lowercase wire form and break any future query layer that matches index against raw JSON. Mirrors the pattern already established in `crates/domain/src/role.rs`. A Phase 2 test pins the invariant: `assert_eq!(format!("{}", PlanStatus::Active), "active");`.

#### Plan struct

```rust
#[derive(Debug, Clone, Serialize, Deserialize, Record)]
#[serde(deny_unknown_fields)]
pub struct Plan {
    pub id: PlanId,
    pub updated_at: i64,
    pub created_at: i64,
    pub goal: String,
    #[record(indexed)]
    pub status: PlanStatus,
}
```

Five fields. All public. `#[serde(deny_unknown_fields)]` per `crates/domain/CLAUDE.md` — rejects JSON with fields the struct doesn't know, preventing silent drift between what the daemon writes and what the Store reads back.

Why exactly these five:

- **`id: PlanId`** — primary key. Typed newtype (not raw `String`); the Record derive's `AsRef<str>` contract resolves against `PlanId: AsRef<str>` which is emitted by `id_type!`.
- **`updated_at: i64`** — Record trait requires this field literally. `i64` milliseconds per `taskstore-traits`.
- **`created_at: i64`** — set once at construction, never mutated. Separate from `updated_at` so "when was this filed" stays distinct from "when was this last modified" — matters for reporting and audit even at Stage 5.
- **`goal: String`** — the user-supplied string from the CLI. Stage 5's only user-facing input field.
- **`status: PlanStatus`** — FSM state. Indexed because the Store queries by status (e.g., "all active plans") from Stage 6 onward; indexing now costs nothing and avoids a schema-evolving change later.

Fields explicitly omitted that existed on v4's Plan:

| v4 field | Why not in Stage 5 |
|---|---|
| `parent_id: Option<String>` | Stage 6 (`hierarchy.md`) owns parent linkage; nothing to point at yet. |
| `title: String` | v4 had `title` + `acceptance_criteria`. Stage 5 collapses to `goal`; Stage 6 revisits if a title-vs-goal distinction re-earns itself. |
| `acceptance_criteria: AcceptanceCriteria` | Returns with the decomposer in Stage 6. No consumer at Stage 5. |
| `tier: Tier` | First-gate is always `Brief` (flat Plan → Work); `Tier` is a switch with only one arm until Spec/Phase exist. |
| `decomposition_attempts: u32` | Decomposer loop state; no decomposer yet. |
| `bubble_up_count: u32` | Retry-escalation counter; adds back only if retry escalation re-surfaces. |

#### generate_id / now_millis (in id.rs)

Byte-equivalent to v3/v4's `src/id.rs`:

```rust
use rand::RngExt;
use std::time::{SystemTime, UNIX_EPOCH};

pub fn generate_id(prefix: &str) -> String {
    let mut rng = rand::rng();
    let code: String = (0..5)
        .map(|_| {
            let idx = rng.random_range(0..36u8);
            if idx < 10 {
                (b'0' + idx) as char
            } else {
                (b'a' + idx - 10) as char
            }
        })
        .collect();
    format!("{prefix}-{code}")
}

pub fn now_millis() -> i64 {
    SystemTime::now()
        .duration_since(UNIX_EPOCH)
        .expect("system clock before UNIX epoch")
        .as_millis() as i64
}
```

Why keep exactly:

- **Already proven across v3 and v4** (identical between them; not touched for 18+ months).
- **Legible in logs.** `pl-k7m2p` vs a 26-char ULID or 36-char UUID. Columnar log output readable at a glance.
- **Fixed 8-char width.** `{2-char-prefix}-{5-char-body}` total 8 chars. Consistent alignment in tables and dashboards.
- **Sufficient entropy.** 36⁵ = 60,466,176 IDs per prefix; 50% birthday collision at ~√60M ≈ 7,750 IDs. Plans are human-filed and low-cardinality; collision within one repo's history is effectively impossible. Scope is per-`.taskstore/`, so cross-repo collision is a non-concern.

#### id_type! macro (in id.rs)

```rust
/// Declare a typed-ID newtype with a fixed 2-char prefix.
///
/// Invocation:
///
///     id_type!(PlanId, "pl");
///
/// Generates a public `struct PlanId(String)` with:
///   - derives: Debug, Clone, PartialEq, Eq, Hash, Serialize, Deserialize
///   - #[serde(transparent)] so the wire form is the inner string, not a
///     one-element array
///   - impl AsRef<str> — required by #[derive(Record)] on consumer structs
///   - impl fmt::Display — indexed-field code path may call ToString
///   - impl FromStr<Err = Infallible> — symmetric serde round-trip, no
///     format validation
///   - PlanId::new() -> Self, calling generate_id("pl")
///   - PlanId::prefix() -> &'static str, returning "pl"
///   - one #[cfg(test)] assertion that PlanId::new().as_ref() starts with "pl-"
///
/// Constraints (by convention, enforced by code review):
///   - Prefix must be a 2-char lowercase ASCII string literal. Longer breaks
///     the 8-char ID convention; shorter loses readability; uppercase clashes
///     with the lowercase base36 body.
///   - Inner type is fixed at String.
///   - Derive set is fixed.
///
/// This macro exists to collapse seven near-identical newtypes. Any record
/// wanting a different shape (different derive set, different inner type,
/// different ID format) writes a manual newtype instead. None of the v5
/// first-gate records need that escape hatch.
#[macro_export]
macro_rules! id_type {
    ($name:ident, $prefix:literal) => {
        #[derive(
            ::std::fmt::Debug,
            ::std::clone::Clone,
            ::std::cmp::PartialEq,
            ::std::cmp::Eq,
            ::std::hash::Hash,
            ::serde::Serialize,
            ::serde::Deserialize,
        )]
        #[serde(transparent)]
        pub struct $name(::std::string::String);

        impl $name {
            pub fn new() -> Self {
                Self($crate::id::generate_id($prefix))
            }

            pub fn prefix() -> &'static str {
                $prefix
            }
        }

        impl ::std::convert::AsRef<str> for $name {
            fn as_ref(&self) -> &str {
                self.0.as_ref()
            }
        }

        impl ::std::fmt::Display for $name {
            fn fmt(&self, f: &mut ::std::fmt::Formatter<'_>) -> ::std::fmt::Result {
                f.write_str(&self.0)
            }
        }

        impl ::std::str::FromStr for $name {
            type Err = ::std::convert::Infallible;
            fn from_str(s: &str) -> ::std::result::Result<Self, Self::Err> {
                ::std::result::Result::Ok(Self(s.to_string()))
            }
        }
    };
}
```

Fully-qualified paths (`::std::…`, `::serde::…`, `$crate::id::…`) mirror the `Record` derive's hygiene posture: generated items compile in any consumer context regardless of what `use` statements exist in scope.

### API Design

#### Plan construction and transitions

```rust
use crate::{FsmError, Role, Transition};
use crate::id::now_millis;

impl Plan {
    /// New Plan: fresh PlanId, status = Active, created_at = updated_at = now.
    pub fn new(goal: String) -> Self {
        let now = now_millis();
        Self {
            id: PlanId::new(),
            updated_at: now,
            created_at: now,
            goal,
            status: PlanStatus::Active,
        }
    }

    /// Read current status. The field is pub; this method exists for call sites
    /// that prefer the method form.
    pub fn status(&self) -> PlanStatus {
        self.status
    }

    /// Validated FSM transition. Delegates to the Fsm-derived validate_transition.
    /// On Transition::Changed, updates self.status and self.updated_at.
    /// On Transition::Unchanged (from == to), mutates nothing.
    /// Invalid transitions (from/to pair absent, or role not in the `by` list)
    /// return Err(FsmError<PlanStatus>).
    pub fn transition(
        &mut self,
        target: PlanStatus,
        role: Role,
    ) -> Result<Transition, FsmError<PlanStatus>> {
        let result = PlanStatus::validate_transition(self.status, target, role)?;
        if result != Transition::Unchanged {
            self.status = target;
            self.updated_at = now_millis();
        }
        Ok(result)
    }

    /// Validated FSM override. Delegates to the Fsm-derived validate_override,
    /// which itself tries the normal path first and falls through to the override
    /// table only if the normal path rejects. On any state-changing result
    /// (Transition::Changed or Transition::Override), updates self.status and
    /// self.updated_at. Only Transition::Unchanged (from == to) leaves state intact.
    pub fn override_status(
        &mut self,
        target: PlanStatus,
        role: Role,
    ) -> Result<Transition, FsmError<PlanStatus>> {
        let result = PlanStatus::validate_override(self.status, target, role)?;
        if result != Transition::Unchanged {
            self.status = target;
            self.updated_at = now_millis();
        }
        Ok(result)
    }
}
```

Design notes:

- **`new()` births plans `Active`, not `Draft`.** Stage 5 has no interview / clarity loop; the goal string is the entire user input. A future stage that reintroduces clarity changes exactly this one line.
- **Both `pub status` and `fn status()` exist.** Consistent with v4. Direct field access is allowed; the method is a convenience for method-chain call sites.
- **No `force_status()` bypass.** v4 had one for recovery and test fixtures. Stage 5 has no recovery path; test fixtures construct Plans directly via `new()` + `transition()`. Add back if Stage 6+ surfaces a real need.
- **`transition` and `override_status` are distinct methods.** v4 had them as flags on a single function; splitting makes call-site intent explicit ("I am using the director-only override path").
- **The two methods are structurally identical except for which validator they call.** A `#[cfg(test)]` helper could collapse them, but at two call sites the DRY payoff is below the clarity cost.
- **The state-mutation guard is `!= Transition::Unchanged`, not `== Transition::Changed`.** The Fsm derive emits three success variants: `Unchanged` (from == to, no-op), `Changed` (normal-path success), and `Override` (fallback-path success, emitted only by `validate_override` when the normal table rejects but the override table authorizes). `validate_override` furthermore delegates to `validate_transition` first, so `override_status` can return any of the three. A guard of `== Transition::Changed` would silently drop `Override` results, leaving the Plan in its prior state after an authorized Director override — exactly the scenario the override path exists to support. `!= Transition::Unchanged` handles all state-changing variants symmetrically and is forward-compatible if the derive ever grows a fourth success variant.

  - `plan_serde_rejects_unknown_fields` — JSON with `{"bogus_field": 1, ...}` fails to deserialize (pins `deny_unknown_fields`).
  - `plan_record_id_matches_as_ref` — `<Plan as Record>::id(&p) == p.id.as_ref()`.
  - `plan_record_collection_name` — `Plan::collection_name() == "plans"`.
  - `plan_record_indexed_fields_single_entry` — `indexed_fields()` has exactly one entry; key `"status"`; `IndexValue::String("active")` for a fresh Plan.
  - `plan_transition_active_complete_by_decomposer` — `Active → Complete` by `Decomposer`: returns `Transition::Changed`; `status` and `updated_at` advance.
  - `plan_transition_active_complete_by_coordinator` — same edge accepts Coordinator too (v4 table has `by (Coordinator, Decomposer)`).
  - `plan_transition_active_complete_by_director_rejects` — Director is not in the `by` list: returns `Err(FsmError{ kind: RoleNotAuthorized, ... })`.
  - `plan_transition_draft_complete_rejects` — no direct `Draft → Complete` edge exists: returns `Err(FsmError{ kind: NoTransition, ... })` regardless of role.
  - `plan_transition_same_state_unchanged` — `Active → Active`: `Transition::Unchanged`, `updated_at` does not advance.
  - `plan_override_active_draft_by_director` — `Active → Draft` via `override_status` by Director: `Transition::Changed`, `status` back to Draft.
  - `plan_override_active_draft_by_coordinator_rejects` — Coordinator cannot use Director-only override: `Err`.
  - `plan_override_active_complete_rejects` — no such override edge exists: `Err(NoTransition)`.
  - `plan_status_is_terminal` — `is_terminal()` true for `Complete` / `Superseded` / `Abandoned`; false for `Draft` / `Pending` / `Active`.
  - `plan_serde_status_lowercase` — serialized `status` value is `"active"` (lowercase), pins `#[serde(rename_all = "lowercase")]`.
  - `plan_status_display_lowercase` — `format!("{}", PlanStatus::Active) == "active"` for all six variants. Pins `#[strum(serialize_all = "lowercase")]` and the alignment between the Display output (used by the `Record` derive to populate indexed fields) and the serde wire form (used for JSONL on disk). A divergence here would mean the index map disagrees with the stored value — a silent failure class.
  - `plan_override_returns_override_variant_mutates_state` — calling `override_status(Active, Draft, Director)` returns `Ok(Transition::Override)` AND mutates `self.status` to `Draft` and advances `self.updated_at`. Pins the `!= Transition::Unchanged` guard against regression; a guard of `== Transition::Changed` would pass the return-value assertion but fail the state-mutation assertion.
  - `plan_override_returns_changed_for_normal_edge` — calling `override_status(Active, Complete, Decomposer)` (a valid normal-table edge) returns `Ok(Transition::Changed)` because `validate_override` falls through to `validate_transition` first. Confirms the override path is strictly permissive, not exclusive.

## Alternatives Considered

### Alternative 1: Copy v4's Plan struct verbatim

- **Description:** Import v4's `domain/plan.rs` including `parent_id`, `title`, `acceptance_criteria`, `tier`, `decomposition_attempts`, `bubble_up_count`. Match the v4 shape exactly.
- **Pros:** Least thinking. Drop-in v4-shape for future Stage 6+ re-use. No migration when Stage 6 reintroduces decomposer state.
- **Cons:** Five fields in use + five fields as dead weight at Stage 5. Dead fields silently rot (nothing tests them, nothing writes them, nothing reads them). Later cleanup is harder than incremental growth. Violates v5 rule #1 ("one design doc at a time, motivated by a failing run") — the fields without current motivation land with no corresponding failing test.
- **Why not chosen:** v5's explicit discipline is to earn each field in the stage that needs it. The migration cost of adding fields incrementally is a few lines per Stage 6+ doc; the cost of carrying dead weight is that Stage 5 ships with code nothing exercises.

### Alternative 2: Share a `HierarchyStatus` enum for Plan / Spec / Phase (as v4 did)

- **Description:** Define the six-state enum once as `HierarchyStatus`; `type PlanStatus = HierarchyStatus`. When Spec and Phase land in Stage 6, they alias the same enum.
- **Pros:** One FSM table, one set of tests, one point of change if the lifecycle evolves.
- **Cons:** Stage 5 has no Spec, no Phase. A shared enum has no current consumer to justify the generalization; the name `HierarchyStatus` would be aspirational rather than descriptive. If Stage 6 decides Spec needs a different state (e.g. a `Blocked` state while waiting on external review) the sharing inverts into a blocker — one enum serving three semantics poorly.
- **Why not chosen:** premature generalization. Stage 6's `hierarchy.md` re-examines this with Spec / Phase in hand; they can opt into a shared enum, or specialize, or introduce a `HierarchyStatus` umbrella at that point. Deferring costs one search-and-replace later if they unify; that's cheap.

### Alternative 3: Hand-write seven typed ID newtypes (no macro)

- **Description:** Define each of `PlanId`, `WorkId`, `SpecId`, `PhaseId`, `BundleId`, `TickId`, `RunId` as a separate named struct with its own derives, constructors, and trait impls.
- **Pros:** Zero macro machinery. Each newtype is visible in full; rust-analyzer tooltips show literal code.
- **Cons:** Seven near-identical 25-line blocks. The exact boilerplate pattern a declarative macro exists for. Typos in one newtype (forgotten `impl AsRef`, missed `#[serde(transparent)]`, wrong derive) produce compile errors at call sites instead of at a single source of truth. Exactly the shape of the `impl Record` boilerplate that earned its own proc macro — repeated one layer down.
- **Why not chosen:** the second newtype is where the cost-benefit flips. v5 will hit six more newtypes across Stages 6-8. The macro saves ~150 lines and one class of copy-paste bug for ~30 lines of `macro_rules!`.

### Alternative 4: Generic `Id<Kind>` with phantom-type parameter

- **Description:** `struct Id<K>(String, PhantomData<K>)` + marker types `struct PlanKind;` etc. → `type PlanId = Id<PlanKind>;`. Used in several codebases (including Cersei — memory note `reference-cersei-rust-sdk`).
- **Pros:** One source of truth for the ID shape. Cross-collection misuse (assigning a `WorkId` to a `PlanId` field) is a compile error via the type parameter. Very Rust-idiomatic.
- **Cons:** ID format (prefix, entropy, body) becomes a runtime argument rather than a compile-time property. The 2-char prefix convention has no compile-time home — whoever constructs the `Id` passes `"pl"` or `"wk"` in, and a bug putting `"wk"` into a `PlanId` compiles clean and fails at runtime. Opaque in error messages — `Id<PlanKind>` prints as its inner string same as `PlanId` would, but rustc diagnostics and rustdoc show the generic name, costing legibility.
- **Why not chosen:** the macro keeps the prefix literal at the declaration site. Miss-typing the prefix in the generic form is a runtime failure; miss-typing it in the macro form is a compile-time error local to the ID-generating code path. The extra type safety from `PhantomData<Kind>` is not worth giving up the prefix-at-declaration guarantee. Cersei's use of phantom types is for graph-memory edge typing, not ID generation — different axis.

### Alternative 5: UUIDs or ULIDs for IDs

- **Description:** Use `uuid::Uuid` or `ulid::Ulid` for all record IDs. Drop the prefix entirely, or keep the prefix as a separate column.
- **Pros:** 128-bit entropy (essentially zero collision risk). ULID adds monotonic sortability.
- **Cons:** 32-char (UUID) or 26-char (ULID) bodies vs 5-char base36. Log legibility collapses — `pl-k7m2p` becomes `01HGY1P7QK4Q2W0D4R8N4S5H9A`. No built-in record-type annotation (a UUID doesn't tell you it's a Plan vs a Work at a glance; the prefix does). v3/v4's 5-char base36 scheme, scoped per-repo, has zero real-world collision history; the larger entropy solves a problem that doesn't exist.
- **Why not chosen:** readability is an explicit goal in v5's logs and debug output. Giving up the 2-char prefix and 8-char width for collision resistance we don't need is a bad trade.

### Alternative 6: Make `id_type!` a proc macro in `crates/derive`

- **Description:** Instead of `macro_rules!`, write `#[derive(TypedId)]` or `#[typed_id(prefix = "pl")]` in the derive crate.
- **Pros:** Proc macros can enforce prefix validity more richly (fail on non-2-char, non-ASCII, uppercase).
- **Cons:** `crates/derive/CLAUDE.md` says function-like macros and attribute macros are out of scope; only derives. A `#[derive(TypedId)]` would technically qualify, but the thing being derived on would be an empty marker struct — an awkward usage. `macro_rules!` does the declarative-expansion job without proc-macro complexity: no `syn` parsing, no `quote!`, no separate crate boundary.
- **Why not chosen:** `crates/derive` is reserved for code that must inspect existing types. `id_type!` stamps new types into existence — exactly the `macro_rules!` sweet spot. Keeping it declarative keeps the derive crate narrow.

## Technical Considerations

### Dependencies

- `rand = "0.9"` (or workspace-current, via `cargo add rand -p domain` at Phase 1 start). New dependency for `crates/domain`; v4's domain had it, v5's does not yet. Promote to `[workspace.dependencies]` if `decomposer` or `agents` adopt it later.
- `strum` (with the `derive` feature, via `cargo add strum --features derive -p domain`). Already used by `crates/domain/src/role.rs`; verify the Cargo.toml dep line exists before Phase 2. Needed for `#[derive(strum::Display)]` on `PlanStatus`.
- `taskstore-traits` — already a workspace dep of domain, inherited via `workspace = true`.
- `derive` — already a workspace dep of domain (the FSM runtime types live here and the derive references them via `::domain::*`).
- `serde`, `serde_json` (dev-dep for tests) — already present.

Architect's rule from `crates/domain/CLAUDE.md` ("must not `use` anything from tokio, reqwest, ureq, rusqlite, or any I/O-bound dependency") is not violated by `rand`: `rand::rng()` reads from a thread-local RNG seeded from OS entropy once per thread. Seeding is one-time, non-blocking, same category as `std::time::SystemTime::now()` which the crate already uses.

### Performance

- `Plan::new()`: one `generate_id` call (one thread-local RNG read, five `random_range(0..36)` calls, one small `String` collection, one `format!` into the final 8-char `String`) + one `now_millis` (one syscall on most Unix platforms, sub-microsecond). Total: ~1μs. Human-filed plans are nowhere near a hot path.
- `Plan::transition()`: one linear scan through the const transition table (10 entries for `PlanStatus`) + one role comparison. Sub-microsecond. Matches the Fsm macro's const-table design goal.
- Serde round-trip: five fields, one `String` (`goal`) + one stringifiable enum (`status`). ~5μs per record for typical goals.
- `indexed_fields()`: one `HashMap` allocation + one `String` key + one `String` value. ~100ns per call. Called by the Store on every write; amortized into the Store's serialize + fsync path.

No caching, no memoization. Records are constructed once per operation; there's nothing to cache.

### Security

No new security surface. `rand` uses OS entropy seeding; IDs are not cryptographic (an attacker seeing 100 Plan IDs could predict the sequence in the next RNG, which does not matter because IDs are not secret and not a security boundary). `#[serde(deny_unknown_fields)]` is the right posture for persisted records — rejects malformed JSONL on read rather than silently dropping fields.

### Testing Strategy

Seam tests cross the crate boundary per v5 working rule #2 ("every crate boundary has at least one round-trip serde test and one integration test that crosses the seam with real types").

- **Unit tests in `src/id/tests.rs`** — PlanId format, `#[serde(transparent)]` wire-form check, `FromStr` round-trip, body charset, uniqueness, `now_millis` sanity bounds, Display-matches-AsRef.
- **Integration tests in `tests/plan.rs`** — Plan construction defaults, serde round-trip in both directions, `deny_unknown_fields` rejection, Record trait methods (`id()`, `updated_at()`, `collection_name()`, `indexed_fields()` shape + contents), FSM coverage: each normal edge (accept + role-reject), each override edge (accept + role-reject), same-state `Unchanged`, terminal-state detection for all six states, `serde(rename_all = "lowercase")` wire-form check.
- **Tests in their own files** per rules/rust.md — no `#[cfg(test)] mod tests` blocks at the bottom of production source. `src/id.rs` declares `#[cfg(test)] mod tests;` at the bottom; bodies live in `src/id/tests.rs`.
- **No compile-fail tests.** All error cases here are runtime (invalid transitions return `Err`) or serde-runtime (unknown fields fail deserialization). The derives already have compile-fail fixtures for their own misuse.

## Risks and Mitigations

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| PlanStatus shape proves wrong once Stage 6 introduces the decomposer and reactive deps | Low | Low | v3 → v4 already paid for this iteration; the 6-state machine is the convergence point. If Stage 6 surfaces a gap it lands as a new transition or a new state in Stage 6's own doc, not this one. |
| Dropping `Draft` as the birth state breaks a clarity-loop we haven't designed yet | Low | Medium | `Draft` is kept on the enum and kept in the transition table. `Plan::new()` chooses `Active`; a future doc that reintroduces clarity changes exactly that one line without touching the enum. |
| `id_type!` fixed shape (`String` inner, 2-char prefix, 5-char body) bites a future record type | Low | Low | Hand-written newtype is always available. Macro's doc-comment documents the escape hatch. Grow the macro only when two or more records need an alternate shape — not speculatively. |
| `#[serde(transparent)]` is forgotten in a hand-written alternate, and a future record's ID serializes as `["..."]` breaking JSONL compatibility | Low | Medium | Every typed ID in v5 goes through `id_type!`. Any hand-written alternate is a deliberate choice that the author owns reviewing; phase-2 test `plan_id_serde_wire_form` pins the invariant for the macro. |
| `rand` dep on `crates/domain` introduces hidden test non-determinism | Low | Low | Tests assert on format (`starts_with("pl-")`, body charset) and uniqueness-over-N, not on content. No test compares a specific ID value. |
| Five-field Plan is too small — daemon integration needs more state than fits | Low | Low | Daemon state (run_id, session state, socket bookkeeping) lives in the daemon, not on Plan. Plan is the user-facing persisted object; nothing else. If integration proves the split wrong, widen in Stage 6. |
| 5-char base36 body produces a collision | Vanishingly low | Low | 60M IDs per prefix; 50% birthday collision at ~7,750 IDs. No real repo files 7k Plans. If it ever happens, the Store's upsert path overwrites rather than corrupts; detectable via `updated_at` mismatch. |
| `#[serde(deny_unknown_fields)]` blocks forward-compatibility of the JSONL on disk (newer daemon writes a new field → older daemon restarted against that `.taskstore/` crashes on read) | Medium | Low | v5 is single-reader per `.taskstore/` in practice: only the daemon ever reads `plans.jsonl`. The CLI is a thin client that talks to the daemon over the Unix socket (Stage 4 contract); it does not parse records itself, so version skew between CLI and daemon has no blast radius through this schema. The remaining skew case is "daemon process restarts across a version bump": schema additions ship with the daemon binary that writes them, so a restart picks up matching read and write code. Mixed-version daemons against one `.taskstore/` are not a supported configuration. Relax to `#[serde(default)]` on individual new fields when a real upgrade-skew break occurs. |
| `crate::Role` path in the `#[fsm(role = ...)]` attribute fails to resolve inside the `domain` crate (self-referencing absolute path) | Low | Low | Rust edition 2018+ resolves `crate::Role` inside the current crate cleanly — and the Fsm macro's test fixture for external consumers uses `::domain::Role`, so both shapes are exercised. Phase 2 compile error here is unambiguous and immediate; the fix is `use crate::Role as FsmRole;` or similar. |

## Addendum: Architect Review (pre-implementation)

After converging at 5/5 Rule-of-Five passes, this doc went to an Architect consultation (Gemini via `~/.claude/skills/architect/script.sh`). Four findings surfaced. All four were accepted and are now folded into the design above. Logged here so future readers can see what was caught and how.

### Accepted and incorporated

1. **`override_status` silent no-op (critical).**
   - Architect critique: the proposed `override_status` checked `result == Transition::Changed`, but the Fsm derive's `validate_override` returns `Transition::Override` on authorized override-table edges (verified at `crates/derive/src/fsm/emit.rs:172`). The guard would never fire; the Director's entire escalation path (`Active → Draft`, `Pending → Draft`) would silently leave the Plan in its prior state.
   - Accepted. Both `transition` and `override_status` now guard on `!= Transition::Unchanged`, which correctly handles `Changed`, `Override`, and any future state-changing variant. A new Phase 2 test (`plan_override_returns_override_variant_mutates_state`) asserts both the return variant AND the state mutation, so a regression to the old broken guard fails the test rather than passing silently. Design notes section added to §API Design explaining the choice and referencing the derive emit location.

2. **`PlanStatus` missing `Display` (critical, compile-time).**
   - Architect critique: `#[derive(Record)]` emits `::std::string::ToString::to_string(&self.#ident)` for indexed fields (verified at `crates/derive/src/record/emit.rs:52`). `PlanStatus` must implement `Display`. The original doc declared `#[serde(rename_all = "lowercase")]` but no `Display` impl — Phase 2 would fail to compile the moment the `Record` derive expanded against the `#[record(indexed)] status` field.
   - Accepted. `PlanStatus` now carries `#[derive(strum::Display)]` with `#[strum(serialize_all = "lowercase")]` — the exact pattern already in use for `Role` (`crates/domain/src/role.rs:3-4`). The strum lowercase configuration also fixes Finding #3 as a side effect.

3. **Display output vs. serde wire-form divergence.**
   - Architect critique: if `Display` defaulted to variant names (TitleCase: `"Active"`) while serde serialized lowercase (`"active"`), the indexed-field map value and the on-disk JSON value would disagree. Future query code matching index against raw JSON would silently return nothing.
   - Accepted. The strum `serialize_all = "lowercase"` attribute lands both in the same form (`"active"`). New test `plan_status_display_lowercase` pins the invariant. Design note added to §Data Model explaining the alignment requirement and pointing at the `Record` derive's emit site that consumes it.

4. **`deny_unknown_fields` forward-compat fragility.**
   - Architect critique: strict schema rejection under rolling upgrades converts additive schema evolution into a breaking change.
   - Accepted, with refined context. The Architect's scenario assumed a CLI directly parsing `plans.jsonl`, but the Stage 4 IPC contract keeps the CLI as a thin socket client — only the daemon reads records. Version skew between CLI and daemon has no blast radius through this schema. Version skew between daemon restarts across a binary bump is real; the risk-table row was tightened to call this out explicitly and spell out the mitigation (`#[serde(default)]` on the added field when the break actually occurs, not preemptively). Strict rejection stays as the Stage 5 default because its loud failure is more valuable than silent drift at this stage.

### Architect items not addressed

None. All four findings have corresponding design changes above.
