## Phase 1: Parse-layer fixes
### Design decisions
- `normalize_action_key` (`crates/agents/src/parse.rs`) is now JSON-aware: it parses the input to a `serde_json::Value`, renames `"action"` -> `"type"` only on the object's own top-level key (or on each object in a top-level array via `rename_top_level_action_keys`), and re-serializes. Nested objects (a `run_tool` action's own `input` payload, which may legitimately carry an `action` field for the target tool) are never touched. — why: the prior blind `input.replace("\"action\":", "\"type\":")` rewrote every occurrence of that substring anywhere in the response, including inside a tool's own input object, silently corrupting it.
- `normalize_action_key` returns the input unchanged when the full string does not parse as JSON (e.g. still wrapped in surrounding prose) — `parse_actions` re-applies it to each balanced-bracket-extracted candidate substring (`crates/agents/src/parse.rs:parse_actions`), so the legacy `"action"` key still normalizes correctly once isolated from prose, without ever falling back to the unsafe blind replace.
- `parse_director_actions` (`crates/agents/src/director.rs`) now mirrors `parse_actions`' fence-strip + balanced-bracket-extraction pipeline exactly, reusing `crate::parse::{strip_markdown_fences, bracket_start_positions, extract_array_substring_from}` rather than reimplementing them — why: those helpers already existed in `parse.rs` for this exact purpose (per the design doc's "reuse the helper" instruction) and director's array shape (`Vec<DirectorAction>`) is structurally the same recovery problem as `Vec<AgentAction>`.
- Made `strip_markdown_fences`, `bracket_start_positions`, `extract_array_substring_from` `pub(crate)` in `parse.rs` (previously private) so `director.rs` — a sibling module in the same crate — can reuse them directly instead of a third copy-pasted implementation (reviewer.rs already has its own independent copy predating this phase; not touched, since Phase 1's scope is `parse.rs` + `director.rs` only).

### Deviations
- Design doc's literal example ("implementer writes a file containing `\"action\":` verbatim survives intact") describes a scenario that, on inspection, is not actually reachable through a well-formed JSON response: any string value containing literal quote characters is escaped (`\"action\":`) by JSON serialization, so the blind-replace bug never fired on that exact shape even on old code (verified empirically). The real, reachable corruption case — and the one the regression test (`run_tool_input_field_named_action_survives_intact`) exercises and confirmed breaks old code / passes new code — is a `run_tool` action whose own `input` object has a field literally named `action` (e.g. a tool like `docker`/`kubectl` that takes an `action` parameter). Same effect (a nested `action:` occurrence must survive untouched), correct seam (nested object key, not escaped string content).
- Phase 1 asked for "the same fence-strip + balanced-bracket extraction" to be added to `parse_director_actions`; implemented as a direct reuse of `parse.rs`'s existing helpers (now `pub(crate)`) rather than a duplicated implementation in `director.rs`. Same effect, tighter code (no third copy of the balanced-bracket scanner alongside `parse.rs`'s and `reviewer.rs`'s existing ones).

### Tradeoffs
- Re-applying `normalize_action_key` to each bracket-extracted candidate (rather than only to the whole response once) vs. leaving the legacy `"action"`-key normalization broken for the prose-wrapped case: chose to re-apply per candidate. The extra JSON parse attempt is cheap (already-isolated, already-small candidate strings) and keeps the legacy-key tolerance working in every case it worked in before, rather than narrowing behavior further than the JSON-safety fix requires.
- Did not touch `reviewer.rs`'s independent `strip_markdown_fences` / `extract_object_substring` (a pre-existing, separate copy for `parse_verdict`'s object-shape parsing) even though it duplicates logic now shared between `parse.rs` and `director.rs` — out of scope for Phase 1 (which names only `parse.rs` and `director.rs`); a follow-up phase could consolidate all three call sites onto one shared helper module if that consolidation is ever requested.

### Open questions
- `otto ci` at the workspace level could not be confirmed green during this phase due to a machine-level environment issue on this dev box, unrelated to this diff (see the phase report for full evidence). `cargo test -p agents` (this phase's actual scope) is green and repeatable: 187 unit tests + all integration suites, 0 failures, including explicit break-to-prove verification that all 4 new/changed regression tests fail on the pre-Phase-1 code and pass on the new code. Scott should confirm the desktop's `otto ci` environment (heavy swap pressure, ~14GB/15GB used, multiple concurrent `rust-analyzer` instances hitting this same repo's `target/`) before treating a subsequent phase's `otto ci` run as authoritative, or re-run `otto ci` once the machine is less contended.

## Phase 2: Director session fixes
### Design decisions
- Restart-budget reset off-by-one (`crates/agents/src/director.rs::run_director`, the `'restart` loop): changed the match guard from `Err(e) if restart < max_restarts` to `Err(e) if restart < max_restarts || iterations_completed >= HEALTHY_ITERS_BEFORE_RESTART_RESET`. The reset body (`if iterations_completed >= HEALTHY_ITERS_BEFORE_RESTART_RESET { restart = 0; }`) already lived inside the arm; the bug was that the arm itself never matched once `restart == max_restarts` (the exhausted/"final restart" state), so a healthy 10+-iteration run's next transient blip fell straight to the terminal `Err(e) => return Err(e)` arm instead of getting a fresh budget. — why: bullet 7's whole point (a long-lived Plan must not accumulate restarts across unrelated transient blips and die on the Nth-ever one) is defeated at exactly the boundary condition it was meant to cover.
- Operator-note render/read parity (`crates/agents/src/director.rs::DirectorSession::run_once`): introduced `rendered_note_ids`, a second `Vec<NoteId>` distinct from `unread_note_ids`. `unread_note_ids` (the full unread set) is kept as-is for the two sites that legitimately mean "was there any unread note this iteration" (the `NeedsOperator` grace-counter idempotence check, and the `unread_note_count` field on `DirectorStatusSnapshot`). `rendered_note_ids` starts equal to the full set and is narrowed to `unread_notes.iter().skip(skipped)` (the exact tail actually written into `state.operator_notes`) only when `OPERATOR_NOTES_RENDER_CAP` trips. The `mark_notes_read` call after a successful LLM round-trip now passes `rendered_note_ids`, not `unread_note_ids`. — why: a note the LLM never saw (because the render cap omitted it) must not be marked read; marking it read anyway silently and permanently drops it, which is precisely the loss bullet describes.

### Deviations
- None. Both fixes land at the exact call sites and line ranges the design doc named (`director.rs:699-710` restart guard, `director.rs:945-963`/`1040-1050` operator-note render/mark-read), with no signature or seam changes.

### Tradeoffs
- Kept `unread_note_ids` (full set) alongside the new `rendered_note_ids` (rendered subset) rather than collapsing to one variable, because two of its existing call sites (`NeedsOperator` idempotence check, status-snapshot `unread_note_count`) are correctly asking "are there ANY unread notes" / "how many are unread total," not "how many were rendered." Renaming/merging them would have silently changed those signals' meaning as a side effect of an unrelated fix.
- Chose `restart < max_restarts || iterations_completed >= HEALTHY_ITERS_BEFORE_RESTART_RESET` (an `||` widening the match guard) over restructuring the match into an `if`/`else` inside a single catch-all arm. The `||` form is a one-line diff against the existing guard and keeps the "does this arm retry" condition legible in the `match` itself, at the cost of putting boolean logic in a match guard rather than the arm body; given the arm body already re-checks the same condition to decide whether to actually reset (`if iterations_completed >= ...`), the duplication is one short, named-constant comparison, not meaningfully worse than the alternative.

### Open questions
- None. Both regressions have break-to-prove tests (see below) that were confirmed to fail against the pre-fix code and pass against the fix; `otto ci` inside `crates/agents` is green (`agents CI passed`, exit 0). Per the prior phase's open question, the workspace-level `otto ci` / `loopr::failure_paths` baseline-red status was not re-investigated in this phase (out of scope; the gate for this phase is the agents-crate `otto ci`, per the owner's per-phase-gate decision recorded above).

## Phase 3: LLM retry policy + cost sink hygiene
### Design decisions
- Retry helper lives in `agents`, not `llm` (`crates/agents/src/retry.rs`: `with_llm_retry`, `RetryPolicy`, `RETRY_MAX_ATTEMPTS`/`RETRY_BASE_DELAY_MS`/`RETRY_MAX_DELAY_MS`). — why: `crates/llm/CLAUDE.md` puts "Retry / escalation / advisor strategy selection" explicitly out of scope for `llm`, and `error.rs`'s own doc comment states "Retry counts and backoff shape remain caller-owned." `llm` owns the typed taxonomy (`RetryableReason`); `agents` owns the *policy* that consumes it. This module is the taxonomy's first consumer (it had zero before).
- Bounded combinator over a future-producing closure (`with_llm_retry(policy, || deps.llm.complete_free(...))`) rather than a `complete_free`-specialized helper. — why: it re-issues the caller's identical call each attempt, keeps the retry boundary at the network call only (the surrounding parse-retry sub-loops that mutate `messages` are untouched), and is unit-testable with a plain closure (no `LlmClient` needed). Wired at all three named sites: implementer (`implementer.rs` main sub-loop + the correctable-tool-error re-prompt), reviewer (`reviewer.rs::call_llm_with_retry`), director (`director.rs` parse-retry loop).
- Backoff honors `RateLimited { retry_after: Some(secs) }` (capped at `max_delay`) and uses exponential `base * 2^(attempt-1)` (capped at `max_delay`) for every other reason. Attempts are hard-bounded by `max_attempts`; a `Fatal` error short-circuits with no retry. Module-level consts for base/max/attempts (no magic numbers); `RetryPolicy` is a struct so tests inject a zero-delay fast policy.
- Cost sink async hygiene (`crates/llm/src/metered.rs`): `CostSink::append` is now `async`; the JSON line (including `CallContext::current()`, which must be read on the async task, not the blocking pool) is built inline, and only the blocking file open+`writeln!` is moved onto `tokio::task::spawn_blocking`. The handle is awaited so the write completes and its outcome is logged before the call returns. `MeteredLlmClient::meter` became `async` in turn; the snapshot `Mutex` lock stays fully synchronous inside `record` (no `.await` held across it).
- Cap validation (`crates/agents/src/config.rs`): typed `ConfigError::InvalidCostCap(f64)` (thiserror) + `ImplementerConfig::validate()` rejecting negative/NaN `per_work_cost_cap_usd`; `None` and non-negative finite pass. Exported from the crate root.
- Cast fix (`implementer.rs::over_work_budget`): added a `MICROS_PER_USD` const and a finite/non-negative guard before `(cap * MICROS_PER_USD).round() as u64`. The old `(cap * 1e6) as u64` saturated a negative/NaN cap to 0 micros, making `spent >= 0` always true and escalating every Work on its first call; the guard fails closed against that false positive (validation is the loud gate; the guard is defense-in-depth).

### Deviations
- Config validation is provided and unit-tested in `agents` (the crate that owns `ImplementerConfig`) but is NOT yet *called* from `loopr`'s daemon-context build path (`crates/loopr/src/daemon.rs:735`, where `budgets.per-work-cost-usd` overlays onto the field). `loopr` is out of Phase 3's crate scope (llm, agents) and its CI has unrelated known-red tests, so wiring the `validate()` call at load is left as a one-line follow-up for a loopr-touching phase. The success criterion ("a config with a negative cap fails load with a typed error") is satisfied as a test at the validation seam; the production call-site wiring is the open item below. Same-effect, correct seam.

### Tradeoffs
- `spawn_blocking` + await (write completes, errors logged, existing cost-ledger tests stay deterministic) vs. fire-and-forget detached `spawn_blocking` (lower latency, but a torn/lost write on fast process exit and racy test assertions). Chose await: cost audit is best-effort but the per-call latency cost of awaiting a blocking-pool hop is negligible against an LLM round-trip.
- Generic closure combinator vs. a `complete_free`-specialized function: the generic form needs the caller to write `|| deps.llm.complete_free(...)`, marginally more verbose at each site, but it is reusable (a future `complete_with_tool` retry can use the same helper) and testable without a stub client.

### Open questions
- Wire `ImplementerConfig::validate()` (or an equivalent check on `budgets.per-work-cost-usd`) into `loopr`'s config-load / daemon-context-build path so a negative/NaN cap actually aborts daemon startup in production, not just in the agents unit test. This is a loopr-crate edit (out of Phase 3 scope) — confirm which loopr-touching phase should own it.

## Phase 4: Cost/budget attribution
### Design decisions
- `ProcessSnapshot::record_llm_call` (`crates/telemetry/src/digest/process.rs`) now takes the call's actual `model: &str` and prices with it (`cost_micros(model, ...)`), instead of always pricing at `self.model` (the process's configured/primary model). `MeteredLlmClient`'s free `record()` fn (`crates/llm/src/metered.rs`) derives that model from `usage.model.as_deref().unwrap_or("unknown")` — the same fallback `CostSink::append` already used — and passes it through. This is the fix for "Director Opus calls priced at the config's single `llm.model` rate": a per-process snapshot now prices every call by the model that actually ran it, which is what the per-run budget brake (`DaemonContext::run_budget_exceeded` / `budget_blocks_spawn`) reads.
- Warn-once-per-unknown-model-id de-dup lives in TWO independent places, matching the design doc's explicit "both the brake path and the costs.jsonl path": `ProcessSnapshot` gained a private `warned_unknown_models: HashSet<String>` field (checked/inserted inside `record_llm_call`, guarded by the same `Mutex` callers already hold); `CostSink` gained its own `warned_unknown_models: Mutex<HashSet<String>>` (checked/inserted inside `append`). They are not the same call site and not sharing state on purpose — `record_llm_call` and `CostSink::append` are two distinct consumers of the same `Usage` (one feeds the budget brake's gauge, one feeds the `costs.jsonl` ledger), each callable independently of the other (`MeteredLlmClient::new` has no `CostSink` at all), so each needed its own dedup to actually warn once regardless of which paths are wired up.
- Dead pipeline counters (`plans_created`, `works_created`, `works_completed`, `works_blocked`, `bundles_proposed`, `bundles_accepted`, `bundles_merged`, `ticks_created`) are wired at the closest in-scope seam to each event, all inside `loopr` (telemetry/llm own no daemon orchestration code to wire into):
  - `works_completed` / `works_blocked`: inside the shared `transition_and_persist_work` helper (`crates/loopr/src/daemon/context.rs`), keyed on `work.status` after a successful persist. A new `snapshot: &Arc<Mutex<ProcessSnapshot>>` parameter was threaded through all 20 call sites (`context.rs`, `context/spawner.rs`, `context/integration.rs`, plus the two loopr test files that call the function directly) so every caller's transitions land in the same counters regardless of which orchestration path drove them. The increment is a SEPARATE `if let Ok(mut snap) = snapshot.lock() { match work.status { ... } }` block, NOT nested inside the existing `if work.status.is_terminal() { info!(...) }` block above it — caught by the new e2e test below going red first: `WorkStatus::Blocked` has outgoing FSM edges (`Blocked => Ready/Superseded/Abandoned`) so `is_terminal()` is `false` for it, and a first draft that nested the counter inside the terminal-only block silently never counted a single Blocked transition.
  - `plans_created`: `transport/handler.rs::handle_plan_create`, immediately after `ctx.store.plans().create(...)` succeeds (a Plan is never "transitioned" into existence, so `transition_and_persist_plan` is not the right seam for this one).
  - `works_created`: `transport/handler.rs::decompose_and_dispatch`, immediately after `persist_works_with_remint` succeeds (same reasoning — a batch of new Works is inserted, not transitioned).
  - `bundles_proposed`: `daemon/context.rs::spawn_implementer_for_work`'s `Ok(Ok(bundle))` arm — the actual `Bundle` record is created inside `agents::dispatch::propose_bundle` (out of this phase's crate scope: telemetry, llm, loopr), so this is the closest loopr-side observation point for "a Bundle was proposed."
  - `bundles_accepted`: `daemon/context/spawner.rs::accept_bundle`, right after the `Reviewed -> Accepted` OCC update persists.
  - `ticks_created` + `bundles_merged`: `daemon/context/integration.rs::spawn_integrator_for_bundle`'s `Ok(tick) => {}` arm — the exact "Tick-persist site" named in the design doc. `integrate()` is called with `std::slice::from_ref(&bundle)` (a single-element slice), so `Ok(tick)` means exactly the one `bundle` in scope got merged to produce that Tick; both counters increment together at that one site.
- Phase 3 carry-over closure: `ImplementerConfig::validate()` is now called in `crates/loopr/src/daemon.rs::build_context`, immediately after the `budgets.per-work-cost-usd` overlay onto `implementer_config.per_work_cost_cap_usd` and before `DaemonContext::new` runs. A validation failure returns `LooprError::DaemonStartup(format!("agents.implementer config: {e}"))`, aborting daemon startup loudly and closed (per Phase 3's own doc comment on `ConfigError`) instead of letting an invalid cap reach the per-Work runtime brake's `(cap * 1e6) as u64` cast.

### Deviations
- `plans_created` and `works_created` are wired at the record-creation call sites (`handle_plan_create`, `decompose_and_dispatch`), not literally inside `transition_and_persist_plan`/`transition_and_persist_work` as the design doc's prose suggests ("at the `transition_and_persist_*` ... sites"). Neither Plan creation nor Work creation is a status *transition* in this FSM (both start life already at their initial status via `::new()` + a plain store `create()`), so there is no `transition_and_persist_*` call to hook for these two counters. Same effect (the counter increments exactly once per successfully-persisted new record), correct seam.
- `bundles_proposed` increments at the loopr-side call site that receives the already-constructed `Bundle` from `run_implementer`, not inside `agents::dispatch::propose_bundle` where the record is actually built — `agents` is out of this phase's crate scope (telemetry, llm, loopr only). Same effect for a single-Work-at-a-time daemon (one Bundle in, one counter tick), correct seam given the scope boundary.
- The design doc groups all eight counters under one bullet ("wire the dead pipeline counters... at the `transition_and_persist_*` and Tick-persist sites"); implemented as five distinct call sites across `context.rs`, `context/spawner.rs`, `context/integration.rs`, and `transport/handler.rs`, because the eight counters correspond to five genuinely different daemon events (Plan create, Work create, Work terminal-transition x2, Bundle propose, Bundle accept, Tick/Bundle-merge), not one shared chokepoint.

### Tradeoffs
- Threading `snapshot: &Arc<Mutex<ProcessSnapshot>>` as a new required parameter on `transition_and_persist_work` (touching all 20 call sites, including two test files) vs. leaving the function's signature alone and incrementing `works_completed`/`works_blocked` at each of the ~8 individual call sites that target `Blocked`/`Done`. Chose the signature change: the terminal-state counting logic already lives in exactly one place in the function body (the existing `if work.status.is_terminal() { info!(...) }` block); duplicating the counter increment at 8 scattered call sites would have been the same DRY violation the original `terminal-state summary` log block was written to avoid, and a future ninth call site would silently miss the counter if it forgot to duplicate the increment.
- Two independent `warned_unknown_models` de-dup sets (one on `ProcessSnapshot`, one on `CostSink`) vs. a single shared `Arc<Mutex<HashSet<String>>>` passed into both. Chose independent: `ProcessSnapshot` and `CostSink` have no existing shared-state relationship (`MeteredLlmClient` holds them as two separate optional fields; `CostSink` is entirely absent in the no-cost-ledger test/CLI path), and each path's own "one WARN per distinct unknown id, for the life of this consumer" is the literal, defensible reading of the design doc's "both the brake path and the costs.jsonl path" phrasing — introducing a threaded shared dedup handle would have added a new cross-struct coupling the design doc never asked for.
- New Phase 4 regression tests in `crates/llm/src/metered.rs` were placed in a SECOND, non-feature-gated `#[cfg(test)] mod pricing_tests` block rather than added to the existing `#[cfg(all(test, feature = "stub"))] mod tests` alongside them. Discovered mid-phase: `crates/llm/.otto.yml`'s `test` task runs plain `cargo test -p llm` (no `--features stub`), so the existing stub-gated module — including all of Phase 3's `metered.rs` cost-sink tests — never actually executes under `otto ci` for this crate (confirmed empirically: `cargo test -p llm --lib -- --list` shows zero `metered::` tests without `--features stub`, and all of them with it). Rather than expand this phase's scope into fixing that infrastructure gap (editing `Cargo.toml`/`.otto.yml` is not named in Phase 4), the new tests were written against `record()` and `CostSink::append()` directly (no `ScriptedLlm`/stub needed), so they run — and are actually verified by — the exact `otto ci` command this phase is gated on.
- The "nonzero counters after a scripted e2e" success criterion needed a new e2e test in `crates/loopr/src/transport/handler/tests.rs` (`plan_create_scripted_e2e_increments_process_digest_counters`), since the design doc's own e2e vehicles (`tests/stage_8_plan_to_tick.rs`, `tests/stage_9_director_plan_to_tick.rs`) are both pre-existing red (see Open Questions) and can't prove anything here. The new test drives `plan.create` over the real `dispatch()` path with a scripted decomposer (one Work) and a scripted Implementer that immediately escalates (`need_help`) — self-contained (no Reviewer/Integrator stub responses needed) while covering `plans_created`, `works_created`, and `works_blocked`. It needed its own `DirectorNoopLlm` wrapper (mirrors `stage_8_plan_to_tick.rs::Stage8DirectorAwareLlm`) because `decompose_and_dispatch` unconditionally spawns a per-Plan Director alongside the Implementer, and both draw from the same `ScriptedLlm` FIFO queue if not shielded — the Director raced the single queued Implementer response and starved it, surfacing as `ScriptedLlm: complete_free called with empty queue` (this is likely the same root-cause family as the two additional pre-existing red tests below, though not confirmed).

### Open questions

## Phase 5: Daemon lifecycle fixes

### Design decisions
- Shutdown drain guard added at two seams: a pre-spawn `shutting_down` check in `promote_unblocked_siblings` (`crates/loopr/src/daemon/context.rs`) — the integrator's post-`Integrated->Done` continuation — so a signal landing mid-integrate never promotes a sibling into an already-draining pool; plus a `shutting_down` entry guard at the top of `spawn_implementer_for_work` (belt-and-suspenders for the check-then-spawn race under the JoinSet lock, mirroring the existing reviewer/integrator guards). - Client socket-wait is now a typed `transport:` knob: `client-connect-secs` on `TransportSection` (`config.rs`), default 60s, tied to `daemon-startup-secs` via a shared `DEFAULT_STARTUP_BUDGET_SECS` const — a client must wait at least as long as the daemon may spend on a slow crash-recovery reconcile before binding its socket. Threaded through `ClientTimeouts.connect_wait` (`transport.rs`); `connect_or_wait_with_timeouts` uses it and polls the startup-error sentinel every cycle so a genuine boot failure surfaces immediately with its real reason instead of burning the full budget.
- Span hygiene: each of `spawn_implementer_for_work` / `spawn_reviewer_for_bundle` / `spawn_integrator_for_bundle` (context.rs + context/integration.rs) carried TWO `#[instrument]` attributes (a default fn-named one + the canonical `daemon.spawn_*` named one), producing two nested spans per spawn. - Span-guard-across-await fixed in `RealTools::execute` (`crates/agents/src/dispatch.rs`): replaced `let _enter = span.enter();` held across `tools::dispatch(...).await` with `.instrument(span)` on the async block (per the Rust-rules footgun list).

### Deviations
- The brief said "delete duplicate `#[instrument]` attributes." Deleting the default-named one outright would have dropped `session_id` from the spawn spans (it lived only on the default-named attribute), silently breaking per-session-fanout routing for implementer/reviewer/integrator events. Instead I merged `session_id` into the surviving canonical `daemon.spawn_*` attribute — same effect (exactly one span per spawn) with no telemetry field lost.
- The brief scoped the wait fix to `transport.rs` (`connect_or_wait_with_timeouts`). Removing the shared `START_TIMEOUT_SECS` const forced updating its other consumer, the fork-parent sync poll `wait_for_socket` (`daemon.rs`); I pointed it at the same knob (best-effort `Config::load`, default fallback) so a slow-reconcile daemon also survives the parent poll on the auto-fork path, not just the async client connect. Correct seam for the doc's intent ("a client connecting to a slow-reconcile daemon succeeds").
- Slow-reconcile test uses a 4.5s delayed bind rather than the doc's literal 10s, to keep the test fast while still exceeding the retired 3s hard cap; break-to-prove is self-contained (a 3s `connect_wait` attempt asserts `is_err()` before the bind, the 60s default asserts success after).

### Tradeoffs
- Capture-layer span test drives `spawn_implementer_for_work` through the new `shutting_down` guard (immediate no-op emitting one debug event inside the span) rather than a full implementer run — no git worktree or LLM round-trip needed to assert span cardinality. Spawned into a `JoinSet` exactly as production does (boxes the recursive implementer->reviewer->integrator->promote spawn-chain future); a direct `.await` on it overflows the type-layout depth limit.
- `wait_for_socket` runs pre-telemetry in the fork parent, so its best-effort config-load `warn!` on a broken config goes to a no-op subscriber. Accepted: the daemon's own startup surfaces a broken config strictly; the parent just needs a sane wait budget.

## Phase 6: Store/domain hardening
### Design decisions
- `Store::open`'s `.version` guard (`crates/store/src/store.rs`) now routes every error-return path through a new `close_on_open_err(inner, err) -> StoreError` helper before returning `Err`: it calls `AsyncStore::close().await` (the documented async-safe teardown), logs a `warn!` if the close itself fails, and returns the original open-time error unchanged. Applied to all three error returns in the version-check block (mismatch, unparseable, and the generic `Io` read-failure arm) — previously only the happy path (`Ok(Self { .. })`) ever called `close()`; every error path let `inner` drop implicitly, which tears the writer thread down via `AsyncStore`'s synchronous `Drop` (a blocking `JoinHandle::join()` on whichever thread is unwinding the `Err`, i.e. a tokio worker) instead of the async-safe path `Store::close`'s own doc comment warns against.
- `StoreError::UnparseableVersion { raw: String }` (`crates/store/src/error.rs`) is a new variant, distinct from `VersionMismatch`. Previously an unparseable `.version` file synthesized `VersionMismatch { found: 0, expected: STORE_VERSION }` — indistinguishable from a real on-disk version 0. The new variant carries the raw on-disk string verbatim so a hand-edited or corrupt `.version` is diagnosable without guessing whether "0" was synthesized or genuine. `crates/loopr/src/transport/handler.rs::map_store_error` gained a matching arm (`RpcError::Internal`, same treatment as `VersionMismatch` — both are operator/ops-visible store-integrity failures, not client-request errors).
- `Tick::new` (`crates/domain/src/tick.rs`) returns `Result<Self, TickError>` instead of asserting via `debug_assert_eq!` (a release-build no-op). `TickError` is hand-rolled `Display` + `std::error::Error` (no `thiserror` dep added to `domain`), matching the crate's existing `FsmError`/`GraphError` style exactly (`domain`'s own doc comment on `GraphError` states this convention). `domain::TickError` is exported from the crate root alongside `Tick`.
- `integrator::IntegrationError` gained a `TickConstruction(#[from] domain::TickError)` variant so `integrate()`'s one production call site (`crates/integrator/src/lib.rs`) propagates via `?` instead of unwrapping; `bundles`/`merge_commits` are always built from the same `outcomes` iterator there, so this arm is defense-in-depth (should never fire in production) rather than a live wiring gap.
- `record.get`'s size guard (`crates/loopr/src/transport/handler.rs::handle_record_get`) serializes the result once, measures its byte length, and — if it exceeds `RECORD_GET_MAX_RESULT_BYTES` (`ipc::MAX_LINE_BYTES` minus a `RECORD_GET_ENVELOPE_MARGIN_BYTES` const covering the `DaemonResponse` envelope) — returns a new typed `RpcError::PayloadTooLarge` instead of handing an oversized `DaemonResponse` to `transport/server.rs`'s `framed.send`, where today `LinesCodec`'s own encode-time length check fails generically ("response send failed") and the connection is dropped. `RpcError::PayloadTooLarge` was added end-to-end: enum variant, `CODE_PAYLOAD_TOO_LARGE = -32007`, `code()`/`message()`/`RpcErrorWire` round-trip arms (`crates/ipc/src/error.rs`).

### Deviations
- None from the phase's three named fixes; all three land at the exact seams the doc named (`store.rs:96-111`, `tick.rs:62-68`, `handler.rs:463-513`).
- `Tick::new`'s `Result` return ripples to every call site (all were previously infallible constructions): `crates/integrator/src/lib.rs` (`?`), `crates/integrator/tests/integrate_seam.rs` (`.unwrap()` x2), `crates/store/src/ticks/tests.rs` (`.expect(...)` inside the `fresh_tick` test helper), `crates/store/tests/instrumentation.rs` (`.unwrap()`), `crates/domain/tests/tick.rs` (`.unwrap()` at every call site). This ripple was flagged as expected in the phase brief and is mechanical (every existing call site constructs a length-matched `Tick`, so every non-test call becomes a bare `.unwrap()`/`?`).

### Tradeoffs
- `Store::open`'s "no reactor stall" success criterion is verified as "the failing open, and a subsequent corrected reopen/close, each complete within a bounded `tokio::time::timeout` on a single-threaded `#[tokio::test]` runtime" (`crates/store/tests/version.rs::open_error_paths_close_store_and_do_not_stall_reactor`), not as a literal repro of a pre-fix hang. Traced the actual mechanics in `scottidler/taskstore`'s `WriterHandle`: at version-check time the writer thread is idle (blocked on `receiver.blocking_recv()`, nothing queued), so dropping the sender wakes it near-instantly regardless of whether `close()` or an implicit `Drop` runs the `thread.join()` — there is no per-open flock or other cross-open resource held for the store's lifetime that would make a leaked pre-fix teardown observably hang in a two-open test. The fix is real (deterministic, async-safe teardown per `Store::close`'s own documented invariant, matching the pattern already used on the happy path) even though this specific bug's failure mode is a hygiene/blocking-hop risk rather than a reproducible deadlock at this code's current call pattern. Chose the bounded-timeout test over inventing an artificial "held resource" to force a hang, since that would test a resource-contention scenario Phase 6 did not create.
- `RECORD_GET_MAX_RESULT_BYTES` reserves a flat 4096-byte margin below `ipc::MAX_LINE_BYTES` for the `DaemonResponse` JSON envelope (`{"id":...,"result":...}`) rather than computing the exact envelope overhead per-request. The envelope is well under 100 bytes in practice (a `u64` id plus two JSON keys); 4096 is a generous, named, constant-time margin that avoids a second exact-fit calculation for a boundary that only needs to be "safely under," not maximally tight.
- `TickConstruction` on `IntegrationError` unwraps via `#[from]` rather than a custom message-wrapping variant, since `domain::TickError`'s `Display` already states both lengths clearly and `thiserror`'s `#[from]` requires no additional boilerplate given `TickError` already implements `std::error::Error`.

### Open questions
- None. All three fixes have break-to-prove tests (inverting/replacing the exact test that previously pinned the old behavior in each case: `open_rejects_unparseable_version` now asserts the new variant instead of the folded-in `VersionMismatch{found:0,..}`; `tick_new_debug_asserts_length_parity` (`#[should_panic]`) is replaced by `tick_new_rejects_length_mismatch` (asserts `Err`); the new `record_get_oversized_result_yields_payload_too_large` / `record_get_oversized_result_yields_typed_error_connection_survives` tests exercise a payload this phase's fix was required to catch before it could ever reach the wire).

## Phase 9: FSM enforcement at the store chokepoint

### Design decisions

### Deviations

## Phase 10: Reviewer executed checks
### Design decisions
- `CheckRunner` trait + `CheckOutcome` + `ProductionCheckRunner` land in a new `crates/agents/src/check.rs`. The trait is `pub trait CheckRunner: Send + Sync` with a boxed-future method (`fn run<'a>(&'a self, checkout_path: &'a Path, commands: &'a [String]) -> Pin<Box<dyn Future<Output = Vec<CheckOutcome>> + Send + 'a>>`) so it is dyn-compatible and satisfies the doc's `check_runner: Arc<dyn CheckRunner>` API Design WITHOUT pulling in `async_trait` (the workspace has none; store's `*UpdateSink` traits use `#[trait_variant::make(Send)]` for generic bounds, but that is not dyn-compatible, hence the hand-written boxed future here).
- `ProductionCheckRunner::run_one` spawns each command's PROGRAM DIRECTLY (`Command::new(argv[0]).args(..)`), not via `sh -c`, and routes it through the EXISTING tools heavy-lane spawn infra (`tools::LaneRouter::spawn(cmd, Lane::Heavy, checkout, None, persist)`): heavy lane is unsandboxed (KillStrategy::Pgid), carries the existing wall-clock timeout (600s default/1800s max) + bounded/persisted output. Running the program directly puts the check tool AT the OS spawn boundary, which is the load-bearing choice for the failure taxonomy (see Deviations).
- Failure taxonomy keyed on `CheckOutcome::spawn_error: Option<String>`: `LaneRouter::spawn` returns `Err` ONLY on a spawn-level failure (program not found / exec failure) or a closed lane, so `Err -> spawn_error: Some` (environment problem); `Ok(SpawnResult)` with `exit_code != 0 -> is_red()` (code signal). `run_bundle_checks` (`crates/agents/src/reviewer.rs`) short-circuits on the FIRST spawn error, returning `ReviewerError::CheckEnvironment { command, detail }` BEFORE assembling/calling the LLM — the "no LLM turn on an env failure" invariant holds structurally (the return is upstream of `call_llm_with_retry`).
- Code-gate lives in `reviewer.rs::apply_code_gate`, called between `call_llm_with_retry` (parses the verdict) and the FSM transition/`deps.store.update` (`run_reviewer`, right where the doc says ~212-220): an `Accept` with any red check is rewritten to `Verdict::ChangeRequested` carrying one synthesized `ReviewIssue` per red command (`file` = command, `message` = `executed check \`<cmd>\` failed with exit code N: <tail>`). Non-Accept verdicts pass through (a red check only tightens). The rewritten verdict drives `target_status` (Rejected), `bundle.verification`, and the criteria roll-up, so the LLM never gets the final word over an exit code.
- CheckRun persistence: `run_bundle_checks` persists one `domain::CheckRun` per cleanly-spawned command via a new narrow `store::CheckRunSink` trait (`create_check_run`), `#[trait_variant::make(Send)]` + `&B`/`Arc<B>` forwarding impls, mirroring `BundleUpdateSink`. `SummaryFanout<S>: CheckRunSink` (loopr) forwards to `self.store.check_runs().create(..)` (no summary artifact — CheckRuns are append-only evidence). `output_digest` is a real sha256 (`sha2` added to agents via `cargo add`; hand-rolled `hex_encode` to avoid a `hex` dep); `output_excerpt` is a `CHECK_EXCERPT_CAP` (4096-byte) tail, prefixed with an ephemeral-checkout marker when applicable.
- Prompt evidence: `run_reviewer` appends a `## Executed checks (evidence)` block to the assembled user message before the LLM call, each command's output fenced via a NEW public `context::dynamic_fence` helper (extracted from the reviewer prompt's private `push_fenced`, which now delegates to it — the "existing dynamic-fence helper" the doc names).
- Worktree lifetime: `spawn_implementer_for_work`'s cleanup tail now calls a new `Worktree::retain()` (marks the handle `consumed` so `Drop` is a no-op and the on-disk worktree survives) instead of `cleanup()` WHEN the work reached `InReview` (a Bundle is under review). This is the minimum "don't delete at the too-early point"; terminal-state reaping is Phase 19's job (NOT implemented here). Non-review exits (Blocked) clean up as before.
- Checkout resolution (`DaemonContext::resolve_review_checkout`): when `check_commands` is non-empty, parse `bundle.branch_name` via `worktree::parse_branch` -> `(work_id, seq)` -> warm worktree path `<target>/.loopr/worktrees/<work_id>-<seq>`. Present -> use it warm (`ephemeral = false`). Missing (crash) -> `create_ephemeral_checkout` recreates a detached worktree at `<...>-<seq>-review` from `bundle.head_commit` (`git worktree prune` then `worktree add --detach`), `ephemeral = true`, reaped by an `EphemeralCheckout` Drop guard held across the review. `ephemeral` is flagged into each CheckRun excerpt and the prompt evidence block.
- Noop-bundle fix: the noop file-contents read (`reviewer.rs::read_file_contents`) now reads from `deps.checkout_path` (the worktree the implementer wrote in) instead of `deps.target` (the main repo, where an uncommitted noop change does not exist). Diff-based bundles still read via `git -C target show/diff` (commits live in the shared object DB).
- `ReviewerConfig` gains `check_commands: Vec<String>` (kebab `check-commands`, default empty). Empty -> checks skipped, verdict proceeds LLM-only (the universal merge gate is Phase 12; reviewer checks stay opt-in per target this phase). The daemon routes `ReviewerError::CheckEnvironment` to `Work -> Blocked` with a `blocked_reason` naming the command (dedicated match arm in `spawn_reviewer_for_bundle`, before the generic error arm).

### Deviations
- The doc says the runner "shells the configured check-commands"; implemented as a DIRECT program spawn (argv split on whitespace), not `sh -c`. Rationale: the Resolved Decision "only SPAWN-level system errors map to Blocked ... env-vs-code split at the spawn boundary" requires the check tool to sit at the OS `Command::spawn()` boundary. Via `sh -c`, `sh` always spawns cleanly and a missing tool degrades to exit 127 (a code signal), defeating the taxonomy. Direct spawn makes a missing tool a genuine `io::ErrorKind::NotFound` (env). Same effect for single-program checks (`cargo test`, `otto ci`); the tradeoff is that shell features (pipes, `&&`, quoted args) are not supported by the whitespace tokenizer. Same effect, correct seam.
- `ReviewerDeps` gained the CheckRun store handle by extending the existing `S` bound to `BundleUpdateSink + CheckRunSink` rather than adding a fourth generic param `CR` — the daemon already passes `&*self.summary_fanout` as `store`, and `SummaryFanout` now impls both, so no new generic threads through `run_reviewer`/`make_deps`/the daemon. Same effect, less ripple.
- Reused the tools heavy-lane `LaneRouter::spawn` (which does NOT yet set `kill_on_drop`) for the "existing subprocess timeout + bounded output"; `kill_on_drop` on the tools spawn path is Phase 18's explicit deliverable, so it is intentionally NOT added here. The wall-clock timeout + process-group SIGKILL on timeout are present.

### Tradeoffs
- Ephemeral-checkout cleanup is a synchronous `worktree::cleanup_at` in an `EphemeralCheckout` Drop guard (mirrors `Worktree::Drop`'s best-effort sync-remove posture) rather than a `spawn_blocking` explicit cleanup, because it must fire on every early-return path (verdict, error, panic-unwind) of `spawn_reviewer_for_bundle`. A failed cleanup logs and defers to reconcile. Acceptable given the ephemeral path is a rare crash-recovery fallback.
- Whitespace tokenization of check commands vs. a `shell_words` dep: chose whitespace split (no new dep) and documented the shell-feature limitation. Check commands in practice are single programs; revisit if a real target needs pipes/`&&`.
- CheckRun persistence and the code-gate both use the (post-gate) verdict for the criteria roll-up and verification string, so a code-gated Accept surfaces as change_requested consistently across events, the persisted Bundle, and the retry Implementer's feedback.

### Open questions
- None. The three success criteria are covered by agents-level break-to-prove tests: `accept_over_red_check_is_overridden_to_change_requested` (code-gate + CheckRun real exit codes), `spawn_level_check_failure_blocks_without_llm_call` (`PanicLlm` proves no LLM turn), `noop_bundle_reads_file_contents_from_checkout_not_target` (`CapturingLlm` asserts the checkout-only file content reaches the prompt), plus `accept_over_green_check_stays_reviewed` and the `check::tests` runner suite. The daemon Work->Blocked mapping for `CheckEnvironment` is wired in `spawn_reviewer_for_bundle`; the 5 known-red loopr tests remain the only loopr failures (verified `plan_to_tick_happy_path` fails identically on baseline ebd7d9c5 with changes stashed).

## Phase 11: Persist reviews + deterministic accept gate
### Design decisions
- Deterministic accept gate lives in `domain::decide_accept(reviews, check_runs) -> AcceptDecision` (`crates/domain/src/review.rs`), a PURE function over the persisted `Review` history + `CheckRun` evidence for a Bundle. Both the accept-site code gate (`crates/loopr/src/daemon/context/spawner.rs`) and the Director state summary (`agents::build_director_state`) call it, so the gate and the operator read ONE source of truth. `AcceptDecision` variants: `Accept{round}` (permits), `NoReview`, `Stale{latest_round, review_count}`, `NotAccept{verdict_kind, round}`, `RedChecks{count, round}` — only `Accept` returns `is_accept() == true`. Fail-closed by construction.
- **Accept-site gate (panel must-fix #1):** `spawner.rs::accept_bundle`, in the `BundleStatus::Reviewed => {}` arm (now populated, ~line 106 pre-transition). Before the `Reviewed -> Accepted` transition it lists `ctx.store.reviews().list_by_bundle` + `ctx.store.check_runs().list_by_bundle`, runs `decide_accept`, and `return`s (refuses, no transition) when `!is_accept()`. The Bundle stays `Reviewed`; the Director's next state summary flags it evidence-broken. Any lookup error also refuses (fail-closed). **"stale (round mismatch)"** is detected as `latest_review.round != reviews.len()` — the append-only history must be a contiguous 1..N chain, so the max round equals the count; a mismatch is ambiguous evidence and refused. **"red check"** is detected by counting the latest Review's `check_run_ids` whose referenced `CheckRun.exit_code != 0`.
- Review persist: `run_reviewer` (`crates/agents/src/reviewer.rs`) appends one `Review` per round BEFORE the Bundle FSM transition. `round = deps.store.list_reviews_by_bundle(&bundle.id).len() as u32 + 1`. The record carries the post-code-gate `verdict`, `verdict_summary`/`verdict_reasons` (structured `ReviewIssue`s for a ChangeRequested), the `Vec<CriterionResult>` Phase 8 produces (`review.criteria = criteria_results`), the `check_run_ids` `run_bundle_checks` now returns, and the concrete `model` the provider echoed (`call_llm_with_retry` now returns `(Verdict, Option<String>)` from `usage.model`). Crash between persist and transition is benign (reconcile re-reviews, appends a fresh round; no dedup).
- New `store::ReviewSink` trait (`crates/store/src/reviews.rs`): `create_review` + `list_reviews_by_bundle`, mirroring `CheckRunSink`. Impls for `Store`, `&B`, `Arc<B>`; `SummaryFanout<S>` (`crates/loopr/src/daemon/summary_fanout.rs`) forwards to `self.store.reviews()` (no summary artifact — append-only evidence). `ReviewerDeps.store` bound widened to `BundleUpdateSink + CheckRunSink + ReviewSink`; the daemon already injects `&*self.summary_fanout`, so no new generic threads through.
- Rejected-bundle retry feedback: `spawn_implementer_for_work` (`crates/loopr/src/daemon/context.rs`) now assembles `StateSummary.rejected_bundle_reason` from the latest Rejected bundle's persisted `Review` via `agents::render_review_feedback(&Review) -> Option<String>` (structured reasons, capped at `REJECTION_REASONS_CAP = 20`), falling back to the one-line `Bundle.verification` string ONLY when no Review is on record (pre-Phase-11 rows / crash gap).
- Director summary evidence: `DirectorStore` gains `list_reviews_for_bundle` + `list_check_runs_for_bundle` (impls on `Store`, `Arc<S>`, and the test `FakeStore`); `build_director_state` computes `decide_accept(..).evidence_label()` per `Reviewed` bundle into the new `context::BundleLine.evidence` field (empty for non-Reviewed). Rendered after the status in `director/user.pmt` (`{{#if evidence}} -- {{evidence}}{{/if}}`).

### Deviations
- Design doc says the gate refuses "unless the persisted latest Review ... is Accept with ZERO red referenced CheckRuns" and names "stale (round mismatch)" without pinning what defines staleness. Implemented staleness as `latest.round != reviews.len()` (broken append-only 1..N chain) — the concrete, testable reading of "round mismatch," fail-closed. Recorded here per the spec-gap convention.
- Doc lists the gate's "flagged to the Director as evidence-broken" as a behavior; implemented as: the gate leaves the Bundle `Reviewed` (no transition) and the Director state summary renders the `decide_accept` evidence label (`NO REVIEW EVIDENCE ...` / `STALE ...` / `... red check(s) ...`) per Reviewed bundle. There is no separate "flag" record — the summary IS the flag, and the code gate is the enforcement. Same effect, correct seam (no new record type invented).
- `context::BundleLine` gained `#[derive(Default)]` + a new `evidence: String` field; the one existing struct-literal in `context/src/implementer/tests.rs` uses `..Default::default()`. The Director user prompt template changed by one line; the baked-canary suite does not assert the director bundle line, and the `build_for_director` unit tests use empty-evidence BundleLines so their rendered output is byte-unchanged.

### Tradeoffs
- `decide_accept` picks the max-round Review and requires `round == count`; an out-of-order or duplicated round refuses rather than "best-efforting" a verdict. Chose fail-closed strictness over leniency: an ambiguous evidence chain must not accept (panel must-fix intent). The cost is that a (currently impossible) legitimate non-contiguous history would refuse until re-reviewed — acceptable, since the only writer (`run_reviewer`) always appends `count + 1`.
- Review `model` is `usage.model.unwrap_or_default()` (empty string when the provider echoes no model, e.g. test fakes). Chose an empty string over a synthetic `"unknown"` sentinel so audit tooling can distinguish "no model echoed" from a real id without parsing a magic literal; Phase 13 (per-role routing) is where a resolved model id starts flowing in.
- Accept-gate test (`crates/loopr/tests/accept_gate.rs`) asserts on the `ProcessSnapshot.bundles_accepted` counter (incremented at the accept site before the Integrator spawn) rather than racing the downstream Integrator's Bundle mutation. Deterministic and side-effect-free for the assertion.

### Open questions
- None. Success criteria covered by break-to-prove tests: `accept_gate.rs::reviewed_bundle_without_persisted_review_is_not_accepted` (refused, stays Reviewed, `bundles_accepted == 0`) vs `reviewed_bundle_with_accept_review_is_accepted` (same call, only a persisted Accept Review added -> accepted) proves the gate load-bearing; `..._with_change_requested_review_...` and `..._with_accept_over_red_check_...` prove non-accept/red refusal. `domain::review::tests::decide_accept_*` (6 tests incl. stale round-mismatch and accept-over-red). `agents::reviewer::tests::run_reviewer_persists_review_round_1_with_criteria`, `re_review_appends_new_round_no_dedup` (one row per round), `change_requested_review_persists_structured_reasons`, `code_gated_accept_persists_change_requested_review_linking_check_runs`, `render_review_feedback_*` (structured reasons, cap, None-when-empty). `agents::director::tests::build_state_flags_reviewed_bundle_with_no_review_evidence` + `build_state_shows_accept_evidence_for_valid_review` (Director summary flag). The 5 known-red loopr e2e tests remain the only loopr failures (verified `stage_8_plan_to_tick::plan_to_tick_happy_path` and `stage_9_director_plan_to_tick::director_plan_to_tick_happy_path` fail identically — "Work reached Blocked", ~0.27s — on baseline 7e21d19b with Phase 11 stashed out; the 3 `failure_paths::*` are consistently red per the brief).

## Phase 12: Validation on by default + integrator evidence
### Design decisions
- `integrator.require_validation: bool` (default `true`) lives ONLY on `loopr::config::IntegratorSection` — it is NOT plumbed into `integrator::IntegratorConfig`. `integrate()` itself never needed to know the operator's startup posture; it already skips validation when `validation_commands` is empty. `require_validation` is purely the loopr-level fail-closed STARTUP gate, so the integrator crate's own config, `IntegratorDeps`, and every existing integrator seam test using `IntegratorConfig::default()` (empty commands) needed zero changes for this field.
- `IntegratorSection::validate()` (`crates/loopr/src/config.rs`) is the single fail-closed check: `require_validation && validation_commands.is_empty()` -> `Err(LooprError::DaemonStartup(..))` naming both knobs by their YAML keys (`integrator.require-validation`, `integrator.validation-commands`) plus the fix (configure a command, or opt out). `require_validation == false` logs one `tracing::warn!` naming the escape hatch — fires on every boot, not just the first, since a daemon that silently forgets it opted out of evidence is exactly the failure mode the WARN exists to prevent.
- The check is called from `daemon::build_context` (`crates/loopr/src/daemon.rs`), as the FIRST statement — before `store::Store::open`, before the sandbox/LaneRouter probe, before anything else. `build_context` is the single choke point shared by production (`run_active_daemon` -> `build_context`) and every test that constructs a `DaemonContext` directly (its own doc comment already called it "the test-reachable entry point for the pipeline"), so both paths get the identical fail-closed gate — the same pattern the pre-existing `implementer_config.validate()` call already established two hundred lines later in the same function.
- Rejected an alternative of putting the check inside `Config::load` itself: `Config::load`'s own unit tests (`crates/loopr/src/config/tests.rs`) construct a bare tempdir with no `integrator:` section ~20 times and assert `Config::load(..).expect("load")` — gating there would have broken every one of them for a reason unrelated to what they test (LLM section parsing, transport defaults, env overrides, etc.). Gating in `build_context` instead scopes the refusal to "constructing a runnable daemon," which is what "the daemon refuses to start" actually means, and leaves `Config::load` a pure parse+merge function.
- Integrator evidence: `validation::run_validation` (`crates/integrator/src/validation.rs`) now returns `Result<Vec<CommandOutcome>, ValidationFailure>` instead of `Result<(), ValidationError>`. `CommandOutcome { command, exit_code, output_digest, output_excerpt, duration_ms }` is captured for every command that reaches an exit code — 0 or nonzero — mirroring the Reviewer's Phase 10 `CheckOutcome` shape (sha256 digest of the FULL combined output + a capped head+tail excerpt). A timeout or spawn/io error (no exit code was ever produced) is NOT captured as a `CommandOutcome` — same "environment problem, not a check outcome" reasoning Phase 10 already established for the Reviewer's spawn-error path, so no `CheckRun` is fabricated for a command that never ran.
- `lib.rs::integrate` persists one `CheckRun` (`executor: Role::Integrator`) per `CommandOutcome` — success AND failure — via `deps.bundle_sink.create_check_run(..)` (the existing `store::CheckRunSink` from Phase 7/10; `IntegratorDeps<U, ..>`'s bound widened from `U: BundleUpdateSink` to `U: BundleUpdateSink + CheckRunSink`, zero new generic parameters, matching the Reviewer's Phase 10/11 precedent of widening the existing sink bound rather than adding one). Every caller already passes `&Store`/`&SummaryFanout<Store>` for `bundle_sink`, both of which already implement `CheckRunSink`, so this ripples to zero call sites outside the two files touched. Persistence happens BEFORE the pass/fail branch (both the green-path fallthrough and the rollback-and-fail path), so the failing command's own `CheckRun` (real nonzero exit code) survives even when its merge is rolled back — evidence is a fact about what ran, independent of whether the git state it produced was kept.
- First-gate single-Bundle anchor: `allow_multi_bundle` still defaults `false` (unchanged, out of this phase's scope), so `bundle_states.first()` is always the one Bundle/Work this integration-level evidence belongs to. Documented inline as a first-gate assumption, not a silent single-bundle hardcode.
- A `create_check_run` failure propagates via `?` as `IntegrationError::Store(_)` (no new error variant): the Bundles are still `Integrating` at that point (no rollback has run), and the daemon's existing retry contract (`spawn_integrator_for_bundle` in `crates/loopr/src/daemon/context/integration.rs`) already retries `IntegrationError::Store(_)` up to `INTEGRATOR_BACKOFF`'s length — a retry re-runs validation and re-persists cleanly.
- `loopr init` gains a `step_seed_config_template` step (between `loopr-dir` and `taskstore`): writes `.loopr/config.yml` as an ALL-COMMENT documentation template (idempotent — `Preserved` if the file already exists, never clobbers an operator's real config) naming `validation-commands` with `cargo test` / `otto ci` / `npm test` examples and the `require-validation: false` escape hatch, per "no autodetection magic — config drives behavior."
- Discovered while writing the template: an all-comment (or empty) YAML file parses to `serde_yaml::Value::Null`, and `Config::load`'s pre-existing `deep_merge` treated a `Null` overlay as "replace the whole merged tree" — so freshly seeding a documentation-only `config.yml` would have silently ERASED a real `$XDG_CONFIG_HOME/loopr/loopr.yml` layer the instant a target ran `loopr init`. Fixed at the source: `deep_merge` now treats `(_, Value::Null)` as a no-op, matching the XDG-layer's own pre-existing null-safety (`read_optional_layer` already special-cased `value.is_null()` -> `Ok(None)`). This is a one-line, directly-motivated defensive fix (not a drive-by refactor) — the template this phase ships is exactly what would have tripped the latent bug, so it had to be closed to ship the template safely. Covered by `config/tests.rs::comment_only_target_file_does_not_clobber_xdg_layer` (break-to-prove: fails without the `Null` guard).

### Deviations
- None from the phase's own bullets. One pre-existing bug fixed as a direct, disclosed prerequisite for shipping the `loopr init` template safely: see the `deep_merge`/`Value::Null` note above.

### Tradeoffs
- `require_validation` lives only in `loopr::config::IntegratorSection`, not on `integrator::IntegratorConfig`, even though the design doc's YAML sample shows both `validation-commands` and `require-validation` under one `integrator:` block. The YAML shape is unchanged (still one section, both keys); only the Rust struct that owns the field differs from what a literal reading of the doc might suggest. Chose this over threading a field the `integrator` crate's own `integrate()` function has no use for — the crate's own config docstring already says validation is "skipped when validation_commands is empty," which stays exactly true; the by-default POSTURE is entirely a loopr-daemon-startup concern.
- Test-harness ripple was resolved per call site (each `Config::default()`-constructing test file sets `config.integrator.require_validation = false` explicitly) rather than flipping a single global test default, so every test's opt-out is visible in its own diff and grep-able (`grep -rn require_validation crates/loopr/tests crates/loopr/src`) rather than hidden in one shared fixture nobody remembers changed. The shared `common::harness::spawn_test_daemon` and the four CLI-subprocess files' `loopr()`/`init_target` builders got the single-point fix where a true single choke point existed (see Files below); the four bespoke `build_context`-direct test files (`accept_gate.rs`, `corruption_gate.rs`, `director_stuck_states.rs`, `director_reconcile.rs`) and three in-crate `daemon/startup/tests.rs` fixtures each got their own one-line opt-out.
- CheckRun persistence order (before the pass/fail branch, not after) means a `create_check_run` Store error can now surface where none could before (`integrate()` could previously only fail validation via the command itself). Accepted because it maps to an EXISTING retryable error class (`IntegrationError::Store`) with an existing retry contract, not a new failure mode operators must learn.

### Open questions
- None. Success criteria covered by break-to-prove tests: `crates/integrator/src/validation/tests.rs` (`passing_command_succeeds` / `failing_command_returns_error` / `second_command_failure_preserves_first_commands_outcome` / `timeout_returns_error_with_no_exit_code` all assert on the new `CommandOutcome`/`ValidationFailure` shape — every one of these fails to compile against the pre-Phase-12 `Result<(), ValidationError>` signature, proving the seam actually changed); `crates/integrator/tests/validation_wiring.rs` (`passing_validation_produces_tick_and_merged_bundle` now asserts `store.check_runs().list_by_bundle(..)` has one Integrator-executed green row, `failing_validation_resets_branch_and_no_tick_written` asserts one red row survives the rollback, `second_command_failure_rolls_back` asserts both the passing prefix's and the failing command's rows persist — real `Store`, real git tempdir, no fakes); `crates/loopr/src/commands/init/tests.rs::run_seeds_config_template_documenting_the_validation_knob` (every line is a comment) + `step_seed_config_template_preserves_an_existing_config_yml` (break-to-prove: without the `config_path.exists()` guard this test's operator config gets overwritten); `crates/loopr/src/config/tests.rs::comment_only_target_file_does_not_clobber_xdg_layer` (break-to-prove against the `deep_merge` fix). The refuse-to-start / configured / opt-out-with-WARN states are additionally proven end-to-end (real compiled binary, real fork attempt) by a new `crates/loopr/tests/validation_gate.rs`: `no_validation_config_refuses_daemon_start` (bare target, no config.yml -> nonzero exit, stderr names both `integrator.require-validation` and `integrator.validation-commands`, no pid file left behind), `configured_validation_commands_permit_daemon_start` (`["true"]` -> daemon starts, pid file present), `require_validation_false_permits_daemon_start_with_no_commands` (explicit opt-out -> daemon starts despite empty `validation-commands`).

## Phase 13: Per-role model routing
### Design decisions
- `model: String` added to `ImplementerConfig` and `ReviewerConfig` (`crates/agents/src/config.rs`), kebab `model:` on disk, tier-name-or-literal shape matching `llm.model` / `agents.director.model`. Passed as `Some(deps.config.model.as_str())` at the two `implementer.rs` `complete_free` call sites (main sub-loop, correctable-error re-prompt) and the one `reviewer.rs` call site (`call_llm_with_retry`) — previously all three passed `None`. The decomposer is untouched (still `llm.model`, per the phase's own scope line).
- New fail-closed resolver `llm::ModelTiers::resolve_checked(&self, reference: &str) -> Result<String, UnknownModelTier>` (`crates/llm/src/tier.rs`), used ONLY for `agents.implementer.model` / `agents.reviewer.model` in `loopr::config::Config::resolve_model_tiers` (`crates/loopr/src/config.rs`). `llm.model` and `agents.director.model` keep the pre-existing lenient `resolve` (any non-tier string passes through as a literal) — unchanged by this phase, per the doc's explicit "decomposer keeps llm.model" scope line and to avoid touching Director routing this phase doesn't own. `resolve_model_tiers` now returns `Result<(), LooprError>` and `Config::load` propagates it with `?`, so an unknown tier name fails config LOAD (not just a downstream runtime call) with a typed, named error (`agents.implementer.model: unknown model tier "..."`).
- `resolve_checked`'s literal test is `starts_with("claude-")`: every model id anywhere in this workspace (`ModelTiers::default()`'s three fields, `LlmConfig::default().model`, `DirectorConfig::default().model`) already matches that prefix, and it is the only signal available — the crate has no external registry of valid Anthropic model ids to validate against, and `resolve()`'s existing lenient fallback treats literally ANY non-tier string as a valid literal, which is exactly the silent-typo hole this phase closes.
- `ImplementerConfig::model` / `ReviewerConfig::model` DEFAULT to a concrete literal id (`"claude-sonnet-4-6"`, matching `ModelTiers::default().primary`), not the bare tier name `"primary"`. This mirrors the pre-existing convention on their sibling fields (`LlmConfig::default().model` and `DirectorConfig::default().model` are both already literal, not tier names) and is load-bearing: this crate's own test harnesses, and `loopr`'s own integration-test harness (`crates/loopr/tests/common/harness.rs::spawn_test_daemon`), construct `Config::default()` / `ImplementerConfig::default()` DIRECTLY, bypassing `Config::load`'s `resolve_model_tiers` pass entirely. A tier-name default there would ship `"primary"` verbatim to `complete_free`'s `model: Option<&str>` parameter with zero resolution step ever running against it.
- Test-stub compatibility: `llm::stub::ScriptedLlm::complete_free`'s model-FIFO lookup now tries the exact `Some(model)` queue first, then falls back to the untargeted `None` queue (`crates/llm/src/stub.rs`). Before this phase, Implementer/Reviewer always called with `model: None`, so every existing test's `queue_free(...)` (routed to the `None` key) was found directly. Passing `Some(resolved_model)` at those two call sites would otherwise 100% break every implementer/reviewer test across `agents` and `loopr` that uses the untargeted queue (11 test files) with "empty queue" panics, since nothing is queued under the model-specific key. The fallback keeps `None` as the general-purpose default route (matching how `queue_free_for`'s own doc comment already described the Director's `Some(model)` queues as the SPECIFIC-override case); `queue_free_for(model, ...)` still takes precedence when a test wants to assert an exact model was used (verified by a new pair of stub tests).

### Deviations
- `llm.model` / `agents.director.model` stay on the lenient `resolve()`; the doc's Phase 13 bullets don't call this out explicitly but its own Config block only shows the new knob under `agents.implementer` / `agents.reviewer`, and the "Decomposer keeps `llm.model`" line signals the phase is scoped to the two new fields, not a blanket tightening of every model-reference field. Recorded here since the fail-closed behavior is now inconsistent between roles (implementer/reviewer fail closed on a typo; llm.model/director.model do not) — see Open Questions.
- Implementer/Reviewer config defaults changed from a tier-name string (`"primary"`, my first draft) to the literal `"claude-sonnet-4-6"` after `cargo test -p loopr` surfaced `crates/loopr/tests/failure_paths.rs` panicking on `model=Some("primary")` — the test harness (`common::harness::spawn_test_daemon`) builds `Config::default()` directly and never calls the private `resolve_model_tiers`, so the bare tier name reached `complete_free` unresolved. Fixed at the correct seam (literal default, matching the sibling fields' existing convention) rather than patching the test harness, since any other caller constructing these configs directly (present or future) would hit the identical bug. Same effect (unconfigured behavior is unchanged either way), correct seam.

### Tradeoffs
- Chose a `starts_with("claude-")` heuristic over threading a real allow-list of valid Anthropic model ids into `llm`, since no such registry exists in this codebase (models are configured, not enumerated) and the workspace's own defaults all satisfy the heuristic. Accepted risk: a non-Anthropic backend's model id that doesn't start with `claude-` would be rejected as an "unknown tier" by `resolve_checked` even though it might be a valid literal for a future non-Anthropic `LlmClient` impl. Not a live concern today (the only `LlmClient` impls are `AnthropicClient` and test stubs); revisit if/when a second provider backend ships.
- `ScriptedLlm`'s None-key fallback is scoped to `complete_free` only (not `complete_with_tool`), since no Phase 13 call site changed `complete_with_tool`'s `model` argument and no test needed the fallback there. Kept the change minimal to the actually-affected surface.

### Open questions
- `llm.model` / `agents.director.model` remain on the lenient tier resolver (a typo silently becomes a literal "model" string, same as before this phase), while `agents.implementer.model` / `agents.reviewer.model` now fail closed. Worth deciding whether to retrofit the strict resolver onto those two fields too in a follow-up phase, or whether the Director/decomposer's existing operational maturity (long-lived, hand-tuned, rarely reconfigured) makes the lenient behavior an acceptable, deliberate asymmetry.

## Phase 14: Programmatic scope enforcement (agents, decomposer, tools)

### Design decisions
- Scope-match semantics live in one helper — `is_in_scope(path, scope_files)` in `crates/agents/src/scope.rs` — consumed by BOTH `partition_by_scope` (staging-time drop) and the new `out_of_scope_paths` (propose-time gate). Single source of truth so the two enforcement points can never diverge on what "in scope" means. Exact repo-relative path, OR trailing-slash directory prefix (matched at the `/` boundary, so `src/` does not admit `src-gen/`), with `.loopr/` always excluded and empty-scope as the artifact-only fallback.
- The propose-time gate is defense-in-depth, not the primary filter — `propose_bundle` re-checks the full branch-vs-base diff (`crates/agents/src/dispatch.rs`, `propose_bundle`) against `work.files` and returns `ActionResult::Error` when any committed path is out of scope, reusing the exact shape of the existing "no commits to propose" guard so it routes through the implementer's bounded re-prompt loop (lifeguard + attempt budgets). Staging already drops out-of-scope dirty paths; this catches anything that reached a commit by another path.
- `files` made required in the decomposition schema (`crates/decomposer/src/tool.rs`) with a new typed `DecomposerError::EmptyFiles(title)` (`crates/decomposer/src/error.rs`) rejected in `parse_and_validate` (`crates/decomposer/src/decompose.rs`), routing through the existing retry-with-error path. A whitespace-only entry counts as empty.
- Git history/index mutation added to the default denylist as DATA — `GIT_MUTATION_SUBCOMMANDS` const in `crates/tools/src/denylist.rs` drives a loop that appends one `DenyPattern` per subcommand (add/commit/checkout/switch/reset/rebase/merge/cherry-pick/stash), rather than nine special-cased blocks. Read-only git (log/diff/status/show/blame) is absent from the set and stays allowed.
- Prompt/docstring truth fix: `crates/context/prompts/agents/implementer/system.pmt:8` and `AgentAction::CommitChanges` docstring (`crates/agents/src/action.rs`) both claimed `commit_changes` does `git add -A`; corrected to shipped reality (scoped staging: only in-scope, non-`.loopr/` paths are committed).

### Deviations
- The design doc names `propose_bundle` comparing `bundle.paths` against `work.files`; implemented at the correct seam by checking `branch_paths` (the branch-vs-base diff that becomes `bundle.paths`) BEFORE constructing the Bundle, so a rejection returns `ActionResult::Error` and no Bundle is built. Same effect, correct seam.
- `#[serde(default)]` kept on `DecomposeChild::files` (rather than making it a hard serde-required field): an omitted key routes through the clear `EmptyFiles` validation message + retry rather than a generic deserialize failure. The schema's `required` list still names `files` so the model is told to produce it. Recorded because the doc said "required in the schema" and this keeps the deserialize lenient by one hop for a better retry message.
- Existing decomposer + loopr test fixtures that omitted `files` were updated to supply it (behavior change: `files` is now required). The loopr integration fixtures got `files` matching the file each implementer response writes (`VERSION.md`, `A.md`, `B.md`) so the propose-time scope gate admits them.

### Tradeoffs
- Directory-prefix scope is opt-in via a trailing slash on the `files` entry; a bare entry stays an exact-path match. Chosen over auto-treating any entry as a prefix so a Work scoped to `src/lib.rs` cannot silently admit `src/lib.rs.bak` or a sibling. Fail-closed: a bare `/` (or empty-after-strip) entry matches nothing rather than everything.
- The propose gate rejects on any out-of-scope COMMITTED path but leaves uncommitted out-of-scope dirty paths as the existing soft `dropped` warning (they never entered a commit). Keeps the hard gate narrow to real violations.

## Phase 15: Concurrency + budget brakes (loopr)

### Design decisions
- Global implementer semaphore: `DaemonContext::implementer_semaphore: tokio::sync::Semaphore` (`crates/loopr/src/daemon/context.rs`), sized from a new `budgets.max-concurrent-implementers: usize` config field (`crates/loopr/src/config.rs::BudgetsSection`), defaulting to a new named const `DEFAULT_MAX_CONCURRENT_IMPLEMENTERS = 4`. `BudgetsSection` switched from `#[derive(Default)]` to a hand-written `impl Default` (matching the existing `TransportSection` pattern) so the concurrency field gets a concrete non-`Option` default while the two cost caps stay `None` (unlimited) — the container-level `#[serde(default)]` still fills in every field via that hand-written `Default::default()`.
- Permit acquisition is the literal FIRST statement in `spawn_implementer_for_work`, before the Phase 2 `ScopedIdGuard` insert, before the `shutting_down` check, before the budget-brake check — per the design doc's "top of `spawn_implementer_for_work`" placement. Bound via `let _permit = self.implementer_semaphore.acquire().await.expect(...)` (the drop-guard `_permit` naming exception; the `.expect` documents that the semaphore is never `close()`d in production, so `Err` is unreachable, not a live error path silenced). Released via an explicit `drop(_permit)` immediately after `run_implementer(...).catch_unwind().await` returns — before the terminal-status routing `match`, before the Reviewer-spawn arm inside `Ok(Ok(bundle))`, and before the FSM transition that follows. The Reviewer and Integrator spawns are never touched by the semaphore.
- `budget.reset` IPC verb: `MethodName::BudgetReset` / `Method::BudgetReset` (no params) in `crates/ipc/src/method.rs`, dispatched in `crates/loopr/src/transport/handler.rs::handle_budget_reset` (synchronous, no `.await` — a single atomic swap). New `DaemonContext::reset_budget_event(&self) -> bool` (`context.rs`) does `self.budget_event_sent.swap(false, SeqCst)`, returning the PRIOR value so the IPC result (`ipc::BudgetResetResult { was_tripped: bool }`) tells the operator whether the reset actually mattered.
- CLI: `loopr budget reset` (`Command::Budget { cmd: BudgetCmd::Reset }` in `crates/loopr/src/cli.rs`; body `budget_reset_command` in `crates/loopr/src/lib.rs`). Modeled on `daemon_status`, NOT on the auto-forking client commands (`Command::Plan`/`Director`/etc. in `run()`'s pre-telemetry match): resetting a budget-brake flag on a daemon that doesn't exist is meaningless, so `budget_reset_command` checks the pid sentinel itself and prints `no daemon running` rather than forking a fresh daemon (whose guard starts clear on every boot anyway) just to reset it.

### Deviations
- **The design doc's stated mechanism for "so a budget-tripped daemon can resume after the operator raises the cap, without a restart" does not hold as literally written, and this phase does not invent a fix beyond what was asked.** Tracing the actual code path: `DaemonContext::budget_blocks_spawn` (pre-existing, Phase 4) derives its allow/block answer FRESH on every call from `run_budget_exceeded()` — a direct comparison of the immutable `per_run_cost_usd` field against the live (monotonically non-decreasing) `snapshot.llm_cost_micros`. `budget_event_sent` (the flag this phase's `reset_budget_event` clears) is ONLY a WARN/event-emission dedup latch; it plays no role in the block/allow decision. So clearing it, by itself, changes nothing about whether the next spawn attempt is blocked — if the cap is unchanged and cost is still over it, the very next `budget_blocks_spawn` call re-trips (blocks again, and re-emits the one-shot event once more). Dispatch only ACTUALLY resumes once `per_run_cost_usd` itself is raised, and `Config` is loaded once at `build_context` with no live-reload path in this codebase — today that requires an operator-visible `daemon stop` + edit `.loopr/config.yml` + `daemon start`, not a live-without-restart cap raise. This phase ships `budget.reset` exactly as scoped in the design doc's bullet (clear the one-shot flag, nothing more); a live cap-reload mechanism is a different, unrequested feature and is NOT added here. Recorded per the spec-gap convention ("implement at the correct seam ... record the difference"); see the test `daemon::context::tests::budget::reset_clears_the_flag_but_dispatch_resumes_only_after_the_cap_is_raised` for the exact mechanics, and Open Questions below.
- `stub_ctx_scripted` (`crates/loopr/src/transport/handler/tests.rs`, pre-existing Phase 4 test helper) was made generic over `L: llm::LlmClient` (previously hardcoded to construct a `DirectorNoopLlm` internally) and gained a `max_concurrent_implementers: usize` parameter, so the Phase 15 concurrency tests could reuse the exact production `decompose_and_dispatch` dispatch path (which is what genuinely fans out N Works into concurrent `spawn_implementer_for_work` tasks) instead of hand-rolling a parallel harness. The one pre-existing caller was updated to pass `DirectorNoopLlm { inner: scripted }` explicitly and a cap of `4`; behavior-identical for that test. Same effect, correct seam (a mechanical widening, not a new dependency).

### Tradeoffs
- Concurrency proof lives at the LLM-call boundary (an `AtomicUsize` in-flight counter + `fetch_max` inside a purpose-built `ConcurrencyProbeLlm` test double that shields the Director's calls exactly like the pre-existing `DirectorNoopLlm` and answers every genuine Implementer call directly, without touching `ScriptedLlm`'s FIFO queue), not a periodic sample of `WorkStatus::InProgress` rows in the Store. Chosen because a Store-polling sampler is inherently racy (a transition can slip between poll ticks) and would prove "we didn't happen to observe more than N," not "the semaphore genuinely bounds it to N." The LLM-call counter is exact: the permit is held for the Implementer's entire body, including its LLM call(s), so counting concurrent calls is counting concurrent permit-holders directly.
- The concurrency tests use a 150ms artificial hold inside the probe's `complete_free` (a real `tokio::time::sleep`, not a mock clock) rather than a deterministic/virtual-time harness, so the pair of tests (`implementer_semaphore_caps_concurrent_dispatch_at_configured_limit` cap=2, and its break-to-prove companion `implementer_semaphore_break_to_prove_uncapped_dispatch_exceeds_two_concurrent` cap=6) carry a small, deliberate timing margin (150ms hold vs. sub-20ms real `git worktree add` calls on a tempdir repo) rather than depending on `tokio::time::pause()`, since the semaphore's `acquire().await` interacts with real async scheduling that a paused clock does not exercise the same way. Accepted: same tradeoff class as the repo's other timing-sensitive daemon tests (e.g. Phase 5's slow-reconcile test).
- `reset_budget_event`'s break-to-prove test (`reset_clears_the_flag_but_dispatch_resumes_only_after_the_cap_is_raised`) mutates `DaemonContext.per_run_cost_usd` directly via `Arc::get_mut` on the sole not-yet-cloned `Arc` in scope, standing in for the config-edit + daemon-restart a real deployment needs today. Chosen over building a second `DaemonContext`/`build_context` call (which would just prove "a freshly-booted daemon with a higher cap doesn't block," a much weaker claim) because it isolates exactly the two moving parts the success criterion actually names — the same context, reset called twice, cap raised in between — inside one test.

### Open questions
- Should a follow-up phase make `per_run_cost_usd` (and/or the whole per-run budget cap) live-reloadable, so `budget.reset` plus a raised cap can genuinely take effect on a live daemon without `daemon stop`/`daemon start`? The design doc's own phrasing ("without a restart") reads as though it expected this; this phase does not build it (out of Phase 15's named scope: "clears the one-shot `budget_event_sent` soft-pause"), and no design doc names a live-config-reload mechanism anywhere in this repo today. Flagging for Scott to confirm whether that's a real gap to close (a Phase 16+ candidate) or whether the doc's wording should simply be read as "no restart is needed to CALL `budget reset`," which this phase's implementation already satisfies.

## Phase 16: Fat status (ipc, loopr)

### Design decisions
- New `ipc::PlanRollup` struct (`crates/ipc/src/method.rs`): `plan_id`, `plan_status` (lowercase wire form matching `PlanStatus`'s `Display`), `works_by_state: BTreeMap<String, u32>`, `bundles_by_state: BTreeMap<String, u32>`, `director_mode: Option<String>`, `total_attempts: u32`, `stuck: bool`. `BTreeMap` (not `HashMap`) per the repo's determinism rule — the wire form and rendered YAML/JSON key order must be stable run-to-run. `StatusResult` gains `cost_so_far_usd: f64` and `plans: Vec<PlanRollup>`.
- `handle_status` (`crates/loopr/src/transport/handler.rs`) now reads Plans/Works/Bundles ONCE and reuses the same three `Vec`s for both the pre-existing scalar counts (`active_plans`/`active_works`) and the new per-plan rollups, rather than issuing a fourth/fifth store read. A new `build_plan_rollup` helper computes one Plan's rollup by filtering the shared Works/Bundles vecs by `parent_id`/`work_id` membership — `O(works + bundles)` per Plan, called once per Plan (`O(plans * (works + bundles))` overall), which is fine at "fat status is an operator's once-per-glance call" scale.
- `director_mode` is read from the existing `ctx.director_statuses` sidecar map (the same one `director.status` reads), keyed by `plan.id`, mapped through `DirectorMode::as_str()` — identical mechanism to `handle_director_status`, just inlined per-Plan instead of one Plan at a time.
- `stuck: bool` = `plan.status == PlanStatus::Stalled || director_mode == Some("NeedsOperator")` — the two states an automatic dispatch cannot resolve; only operator intervention (`plan override`, `director chat`) unsticks either one. Doesn't require a live Director task to flag stuck (a Stalled Plan with no live Director — the common case, since the Director exits after the Stalled transition — is still `stuck: true`), covered by `status_marks_stalled_plan_as_stuck_with_no_live_director`.
- Read-verb no-auto-fork: extracted a single `pub fn daemon::is_running(target) -> Result<bool, LooprError>` (probes the pid sentinel + liveness, no printing, no forking) and wired it into three places — `commands::list::run` (before `connect_or_wait`, since list has no local pre-check to preserve ordering for), `commands::show::run` (AFTER the existing local id-prefix validation, so a malformed id still fails on that check alone and never touches the daemon-liveness probe), and a thin `lib::daemon_is_running` wrapper (adds the "no daemon running" print) reused by `daemon_status` and `budget_reset_command`, which already had this exact inline check duplicated twice before this phase.
- `lib::run`'s pre-telemetry auto-fork arm (`Command::Plan{..} | Command::Plans | Command::Works | Command::Bundles | Command::Ticks | Command::Show{..} | Command::Director{..} => ensure_daemon_if_needed(...)`) dropped `Plans`/`Works`/`Bundles`/`Ticks`/`Show` — those five now fall through to `dispatch`, which checks `daemon::is_running` itself and reports "no daemon running" instead of forking. `Plan{..}` (writes) and `Director{..}` (mixes `chat`, a write, with `status`) were left auto-forking; the design doc's Phase 16 bullet names only `status, plans, list, show` as the read verbs to fix.

### Deviations
- **`cost_so_far_usd` is process-wide, not per-Plan**, despite living inside a per-plan-rollup-bearing result. The design doc's bullet reads "per-plan rollups: ... cost-so-far (from the now-correct ProcessSnapshot)" as if cost were one of the per-`PlanRollup` fields, but `ProcessSnapshot` (Phase 4's accuracy fix) has no per-Plan cost attribution anywhere in the codebase — every LLM call increments one process-wide `llm_cost_micros` counter with no `plan_id` tag. Implemented at the correct seam: `cost_so_far_usd` is a top-level `StatusResult` field (the daemon's total spend-so-far, correctly priced per-call per Phase 4), not a per-`PlanRollup` field. Same effect for the stated success criterion ("status ... shows ... cost > 0"), correct seam given what the codebase can actually attribute.
- **`total_attempts` is a Plan-level sum**, not the doc's literal (and ambiguous) "attempt counts" plural. Implemented as `Σ work.attempt_count` across the Plan's Works — a single number expressing total retry spend against the Plan's `max_work_attempts` budget — rather than a per-Work breakdown, since `works_by_state` already gives the granular per-Work view and a second full per-Work attempt listing would be redundant in an operator-glance summary.
- The design doc's exact signature bullet ("`crates/loopr/src/lib.rs ~118-134`") pointed at the pre-fork match arm, which is correct; but making read verbs report-no-daemon required touching THREE files, not one: `lib.rs` (drop the arm), `commands/list.rs` and `commands/show.rs` (add the check at the right point in each verb's own body, since `show`'s local prefix-validation ordering only exists inside `show.rs` itself). Same effect, correct multi-seam implementation.

### Tradeoffs
- `daemon::is_running` deliberately does NOT print "no daemon running" itself (unlike the pre-existing inline checks it replaces) — printing lives at each of the three call sites instead. Chosen so `commands::show::run` can run its own local prefix-validation FIRST and only print/return-early on the daemon-liveness question if the id was well-formed; a printing-and-returning `is_running` would have forced either duplicating the check or reordering `show`'s existing "fail fast on a bad id without touching the network" contract (which `tests/smoke.rs::show_with_unknown_prefix_errors_cleanly_without_ipc` pins).
- Existing tests that used `plans` purely as a cheap, non-LLM way to trigger `ensure_daemon_if_needed`'s auto-fork (`tests/daemon.rs` AC 15, `tests/director_chat.rs` x2, `tests/stage_7_wiring.rs`, three tests in `tests/validation_gate.rs`, and one in `tests/smoke.rs`) were switched to `loopr daemon start` — the direct, still-auto-forking equivalent — rather than left green by accident. Per the phase-changes-behavior rule, `tests/daemon.rs::ac15_pid_reuse_protection_rejects_non_loopr` (renamed conceptually, not renamed in code — same test name, updated command + inline comment) and the others were inverted at the command level, not silently deleted; each carries a comment citing this phase and the design doc.
- New break-to-prove coverage lives at two levels: unit (`crates/loopr/src/tests.rs` — `run_{plans,works,bundles,ticks,show}_on_empty_target_prints_no_daemon_and_does_not_fork`, calling `dispatch` directly so a regression back to auto-forking would hang the test on `connect_or_wait`'s full daemon-startup-budget poll rather than fail fast) and E2E (`crates/loopr/tests/daemon.rs` — `plans_on_quiet_target_does_not_fork_a_daemon` and `works_bundles_ticks_show_on_quiet_target_do_not_fork_a_daemon`, against the compiled binary, asserting no pid file appears). Both levels kept deliberately since the unit level is fast/cheap CI signal and the E2E level is the actual fork-mechanics proof the design doc's success criterion asks for.

## Phase 17: loopr watch (ipc, loopr)

### Design decisions
- New long-lived `events.subscribe` method modeled as a STREAM, not a one-shot verb — `crates/ipc/src/method.rs` (`MethodName::EventsSubscribe`, `Method::EventsSubscribe`, no-params like `system.status`/`budget.reset`). The server intercepts it in `transport::server::handle_client` BEFORE `handler::dispatch` (which can only return one `DaemonResponse`) and hands the connection to `serve_event_stream`; the `handler::dispatch` arm for it is a defensive loud reject, so routing the stream through the one-shot path can never silently half-work.
- Gap marker is a TYPED variant, not a magic string — `crates/ipc/src/stream.rs` `WatchFrame { Event | Heartbeat | Gap { dropped } }`. Wire form stays the existing `DaemonEvent {event,data}` envelope (client decode path unchanged); the two reserved control-frame names (`STREAM_HEARTBEAT_EVENT`, `STREAM_GAP_EVENT`) are the discriminators, `WatchFrame::classify` is the single typed seam both sides match on. `Gap` carries a `dropped: u64`, never a re-parsed string.
- Read-idle exemption is achieved by NOT arming the idle `Sleep` in `serve_event_stream` (`crates/loopr/src/transport/server.rs`) — the subscribe path has no idle timer at all, so a quiet subscriber is never dropped. Heartbeats are additional (liveness + prompt dead-client detection via write failure), not the exemption mechanism.
- Heartbeat cadence is a named-const-defaulted, config-tunable, test-injectable value — `DEFAULT_SERVER_HEARTBEAT_SECS = 5` (`crates/loopr/src/config.rs`), surfaced as `transport.server-heartbeat-secs`, carried on `ServerTimeouts::heartbeat` (`crates/loopr/src/transport.rs`). Injecting via the existing `ServerTimeouts` struct (not an env var) lets tests drive several heartbeats in <200ms with zero env-race risk.
- `EVENTS_CAPACITY` bumped 64 -> 1024 as a named const with updated rationale — `crates/loopr/src/daemon/context.rs`.
- Live tail replays nothing: `serve_event_stream` re-subscribes to the broadcast bus at subscribe-time (after handshake), so anything buffered between connect and subscribe is not replayed.
- Clean teardown with no leaked forwarder: `serve_event_stream` selects on `framed.next()` so a dropped client socket is observed as EOF immediately; on EOF/write-error/shutdown the function returns, `handle_client` returns, and both broadcast receivers drop (unsubscribe). The `Lagged -> gap` decision is extracted into `event_recv_to_action` so it is unit-testable against a real `RecvError::Lagged`.
- Client stream reader added as `IpcClient::subscribe_events` (`crates/loopr/src/transport/client.rs`) — long-lived, NOT wrapped in `request_impl`'s wall-clock cap; reads the ack then invokes a caller `FnMut(WatchFrame) -> ControlFlow<()>` per frame. `loopr watch` (`crates/loopr/src/commands/watch.rs`) races it against `ctrl_c`; `render_watch_line` is the pure one-line renderer (heartbeat -> nothing, gap -> visible marker, event -> `"<event>  <compact-json>"` with `--plan` filtering that always passes plan-less/process-wide events).
- `loopr watch` does NOT auto-fork (mirrors Phase 16 read verbs): prints "no daemon running" and exits when no daemon is up.

### Deviations
- Design doc says the subscribe method is "EXEMPT from the server read-idle timeout (send heartbeat frames so the pinned idle Sleep doesn't fire)". Implemented the exemption by NOT arming the idle Sleep on the subscribe path at all (cleaner and directly testable via the idle-exempt heartbeat test), rather than by relying on heartbeat writes to reset a still-armed idle timer. Same effect (a quiet subscriber survives), correct seam; heartbeats retained for liveness + dead-client detection.
- Design doc referenced `server.rs ~318` (the `RecvError::Lagged => continue` in the one-shot `handle_client` event-forward path). That one-shot path is left unchanged (it still `continue`s on lag — appropriate for a request/response client that only incidentally forwards events); the typed gap marker is emitted on the NEW dedicated `serve_event_stream` path, which is where a `loopr watch` subscriber actually reads. Same intent (lag is visible to a watcher), correct seam.

### Tradeoffs
- Forced-lag gap-marker coverage is a deterministic unit test (`lagged_recv_maps_to_typed_gap_marker`) driving a real `broadcast::channel(2)` overflow through `event_recv_to_action`, rather than a wall-clock socket-overflow integration test. A true end-to-end overflow of the 1024-slot bus behind a stalled socket is timing-dependent and flaky on a loaded box; the extracted-function test exercises the exact real `RecvError::Lagged` value and is break-to-prove (flip the Lagged arm to Stop/swallow and it fails).
- Idle-exemption + heartbeat proven with a shortened-interval test (idle=100ms, heartbeat=40ms, assert >=3 heartbeats with no disconnect => ~120ms > idle) instead of a literal >60s wait, per the long-idle-test-pragmatics guidance. No test wall-clock-waits beyond a few hundred ms.
- No-orphan-task proven via `broadcast::Sender::receiver_count()` returning to 0 after the client drops, rather than reaching into `accept_loop`'s private `JoinSet` — receiver_count is the observable that directly proves the subscription task dropped its receiver and exited.

### Open questions
- Cross-repo/system-mutating work: none in this phase.
- Heartbeats are silent in `loopr watch` output (liveness only). If an operator wants a visible "still alive" tick during long quiet periods, that is a rendering choice deferrable to the TUI; flagged, not built.

## Phase 18: Intervention verbs

### Design decisions
- Operator role for both override verbs is `Role::Director`, not a new `Role::Operator` — `crates/loopr/src/transport/handler.rs::handle_work_override` / `handle_plan_override`. The codebase already treats `Director` as the operator/human override role (plan.override precedent); adding an `Operator` variant would touch every FSM `by(...)` guard and `CheckRun.executor` serialization for no behavioral gain.
- Work-abort FSM edge added to the override table, not the transition table — `crates/domain/src/work.rs` `overrides(... InProgress => Blocked by (Director))`. Per the Phase 9 discipline ("the fix is an explicit override table entry in domain, never a store-level bypass flag"). `Blocked => Ready` already exists as a `(Reactor, Director)` transition, so no edge was needed there.
- `FailureReason::OperatorAbort` is a typed unit variant (kebab wire tag `operator-abort`) — `crates/domain/src/failure.rs`. Distinguishes an operator-driven block from agent/crash blocks without prose-parsing `blocked_reason`.
- Keyed cancellation via `implementer_abort_handles: Arc<StdMutex<HashMap<WorkId, AbortHandle>>>` — `crates/loopr/src/daemon/context.rs`. A `JoinSet` has no abort-by-key, so every implementer dispatch routes through the new `DaemonContext::spawn_implementer_registered` (4 former `implementer_tasks.spawn` sites consolidated), which holds the abort-map lock across `JoinSet::spawn` + insert so the handle is registered before the task body can run.
- Abort ordering in `handle_work_override`: fire the `AbortHandle` FIRST (cancel the task, drop its spawn future -> reap subprocess tree), then stamp `OperatorAbort` + `blocked_reason` and run the store-chokepoint `override_status(Blocked, Director)`. The cancelled task never runs its own Blocked-transition arm, so the handler owns the terminalizing write. `Blocked -> Ready` re-dispatches via `spawn_implementer_registered`.
- Abort-map cleanup is a `is_finished()` prune in the pool reaper (`DaemonContext::prune_finished_abort_handles`, called from `reap_all_pools`), race-free: a handle inserted for an already-finished task reads finished and is pruned next sweep; firing a finished handle is a harmless no-op.

### The reaping mechanism (panel must-fix #5)
- `crates/tools/src/spawn.rs::spawn_with_process_group` now sets `cmd.kill_on_drop(true)` (was absent; `integrator/validation.rs` already had it) so a dropped `Child` SIGKILLs the DIRECT child on abort.
- `kill_on_drop` alone leaks grandchildren (a `setsid()` group leader that forked its own children). A `ProcessGroupReaper` drop-guard, declared AFTER `child` (locals drop in reverse order, so the group kill lands before `child`'s own kill), fires on any abort/early-return: for `KillStrategy::Pgid` it `killpg(child_pid, SIGKILL)` (pgid == child_pid via the existing `setsid`), reaping the whole tree; for `KillStrategy::BwrapChild` the `Child`'s own `kill_on_drop` + bwrap `--die-with-parent` namespace teardown handles descendants. The reaper is `disarm()`ed on the normal completion path.
- The no-surviving-pid test (`crates/tools/src/spawn/tests.rs::abort_reaps_subprocess_tree_no_surviving_pid`) spawns `sleep 300 &` (a GRANDCHILD of the shell) that records its pid, parks the spawn future on `child.wait()`, then aborts the task and polls `kill(pid, 0)` until ESRCH. Break-to-prove verified: with `kill_on_drop` + the `force_kill_group` reaper-arm both neutered, the grandchild survives and the test fails ("subprocess tree survived abort"); restored, it passes.

### Deviations
- Doc says `Role::Operator` (and implies Phase 9 introduced it). No such role exists; Phase 9 did not add it. Implemented at the correct seam with `Role::Director` (same effect, the established operator override role) plus the one missing override edge. Recorded here per spec-gap discipline.
- Doc phrases cleanup as "cleaned at join." Implemented as an `is_finished()` prune in the pool reaper rather than a per-join hook, because a `JoinSet` join surfaces no work-id to key the removal. Same effect (bounded map, no leak), race-free.

### Tradeoffs
- Abort map keyed on `WorkId` in a `std::sync::Mutex` vs. a per-task Drop guard: the Mutex+prune is simpler and race-free (no insert-vs-guard-drop ordering hazard across the multi-thread runtime) at the cost of a between-sweeps stale-but-harmless entry.
- `parse_work_status` accepts the full `WorkStatus` vocabulary (defensive, matches `parse_plan_status`'s shape) while the CLI `WorkOverrideTo` value-enum exposes only the two operator edges (`ready`/`blocked`); the daemon's `override_status` FSM guard is the real gate for anything else.

### Open questions
- "Director exits on plan abandon" is asserted at the FSM level (`Abandoned.is_terminal()` is true, which the Director loop's existing terminal-status check acts on); a full running-Director exit is covered by the existing Director loop, not re-tested here.
- Cross-repo / system-mutating work: none in this phase.

## Phase 19: Failure-path reaping

### Design decisions
- Single shared reap primitive, `crates/loopr/src/daemon/context/reap.rs::reap_terminal_work_worktree(target, work_id, status)`, keyed on `WorkStatus::is_terminal()` (the domain FSM's own predicate, not a hand-rolled status list). A non-terminal `status` is a guaranteed no-op INSIDE the function itself, not just caller discipline — the same guard the design doc asks for ("never delete a retained (in-flight) worktree") is enforced at the one call site all three production call sites route through.
- Enumerates worktrees via `worktree::list` + `worktree::parse_branch`, filtering to entries whose parsed `work_id` matches — this sweeps EVERY seq for that Work (every retry's worktree, not just the latest), since a retry allocates a fresh seq and never reuses a prior attempt's branch (`worktree` crate's own contract).
- Three live call sites wired (all the places a Work can reach a terminal status at RUNTIME, found by auditing every `transition_and_persist_work` call site for a `Done`/`Superseded`/`Abandoned` target — the other ~15 sites only ever land `Blocked`/`InReview`/`Ready`/`InProgress`):
  1. `crates/loopr/src/daemon/context/integration.rs` — after the `Integrated -> Done` transition lands (the success path).
  2. `crates/loopr/src/daemon/context/spawner.rs::override_work` — after a Director `OverrideWork` action lands `Abandoned`/`Superseded` (the LLM giving up on a Work, e.g. after repeated `IntegrationFailed` retries).
  3. `crates/loopr/src/transport/handler.rs::handle_work_override` — the Phase 18 operator `work.override` IPC verb, which can ALSO land any terminal status directly (e.g. `loopr work override <id> --status abandoned`). This site was not in the design doc's file:line citations but is a real, previously-unreaped terminal-transition site discovered during the audit; wiring it closes the same gap the other two close.
- `startup::sweep_worktrees` (the restart reconcile) extended: `delete_branch` now runs for EVERY terminal status, not only `Done` — `Superseded`/`Abandoned` Works left a dead `loopr/wk-*` branch behind forever under the old gate. `delete_branch` is idempotent on a branch already removed by the live reap, so this is pure belt-and-suspenders.
- Reap is best-effort throughout (mirrors `integrator::integrate`'s existing post-merge branch-cleanup posture): every failure is a `warn!`, never a propagated error, since the Work's terminal transition has already persisted by the time reap runs — a failed reap must not re-open or fail an already-terminal Work. The startup reconcile sweep is the explicit backstop for anything a live reap misses.

### Deviations
- The design doc cites `crates/integrator/src/lib.rs:594-610` as needing the "not only Done" extension. That block is the post-Tick MERGED-branch cleanup (the success path only); it is already correct and untouched. The integrator crate has no notion of "this Work is now terminal" — it only knows a Bundle reached `IntegrationFailed`, after which the Work goes `Blocked` (retryable) and stays that way until the Director (an `agents`-crate, LLM-driven decision, iterations later) gives up. Reaping on the Work's eventual terminal status is therefore implemented at the correct seam — the `loopr` daemon's own terminal-transition call sites (integrator, Director-action spawner, and operator IPC) — not inside `integrator`, which structurally cannot make that call. Same effect, correct seam.
- Found and wired a third live call site (`transport/handler.rs::handle_work_override`) not named in the design doc's file:line citations. The design doc only pointed at `crates/integrator/src/lib.rs` and `crates/loopr/src/daemon/startup.rs`; auditing every Work-terminalizing write turned up the Phase 18 operator override verb as an equally real (and previously unreaped) site.
- The e2e success-criterion test does NOT drive the pipeline through a real Implementer/Reviewer LLM round to reach `IntegrationFailed` — it pre-seeds an `Accepted` Bundle directly into the store (real on-disk worktree, real `loopr/plan-<id>` integration branch, real `validation-commands: ["false"]`) and lets the daemon's own cold-boot reconcile drive the REAL integrator against it. Reason: the Implementer -> Reviewer -> Director-accept path exercised the SAME pre-existing OCC "stale record" race that makes `failure_paths.rs`'s three tests consistently red (reproduced independently while diagnosing this test's own flakiness: the Reviewer's `Triaged -> Reviewed` bundle-transition write loses a race and the Bundle never leaves `Triaged`, stranding the Work at `InReview` for the rest of the poll deadline). That race is not Phase 19's to fix (pre-existing, out of scope); routing around it via direct store-seeding + cold-boot requeue still exercises the real `spawn_integrator_for_bundle` / real `integrate()` / real Work-Blocked transition / real reap call sites this phase adds, with no LLM round-trip in the critical path, and is reliably green (8/8 consecutive runs before this note, plus the CI run itself).
- `crates/loopr/tests/common/harness.rs` gained `spawn_test_daemon_with_config` (a config-customizable variant of `spawn_test_daemon`), added while first attempting the e2e via the shared harness. The final e2e test does not end up using it (it needs to pre-seed the store before `build_context` runs, which the shared harness does not expose a hook for), but the addition is backward-compatible (`spawn_test_daemon` is now a one-line wrapper around it) and documented as available for a future test that only needs a config override.

### Tradeoffs
- One shared `reap_terminal_work_worktree` helper called from three sites vs. inlining the sweep at each call site: the helper is the only place `worktree::list`/`parse_branch`/`cleanup_at`/`delete_branch` are sequenced together outside `startup::sweep_worktrees`, so a future fourth terminal-transition site gets the same guarantee by calling one function, not by copying a five-line sweep loop.
- Best-effort (warn, never propagate) vs. surfacing reap failures as errors on the transition call: the Work's terminal status is the source of truth the operator and Director act on; a filesystem/git hiccup during cleanup is real but secondary, and the existing pattern for exactly this class of problem (`integrator`'s post-merge branch delete) is already warn-and-continue. Consistency won over a new error-propagation path with no consumer.

### Open questions
- Cross-repo / system-mutating work: none in this phase.
- The pre-existing Reviewer `Triaged -> Reviewed` OCC-stale race (surfaced while diagnosing this phase's e2e test, not fixed here) is very likely the same root cause behind `failure_paths.rs`'s three consistently-red tests and possibly the `stage_8`/`stage_9` "load-flaky" happy-path tests too — all five share the identical shape (a Reviewer or Director-driven bundle/work transition losing an OCC race under a tight `poll_interval_secs = 0` test loop). Worth a dedicated design doc; flagging for Scott rather than fixing it inside this phase's scope.
