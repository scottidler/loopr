# Design Document: E2E React-Todo Target

**Author:** Scott A. Idler
**Date:** 2026-04-01
**Status:** Implemented
**Review Passes Completed:** 5/5

## Summary

Add a new E2E target that scaffolds a Vite + React + Tailwind project and has Loopr orchestrate building a todo web app with add/list/done/delete, served from a Docker container. This is a step up from python-todo: more files, a build pipeline, and container verification.

## Problem Statement

### Background

The python-todo E2E validates Loopr's orchestration on a simple CLI project. To build confidence that Loopr handles real-world web projects, we need a frontend target with a build step, multiple source files, and infrastructure (Docker).

### Problem

No E2E target exercises JavaScript/TypeScript project detection, npm-based tooling, or Docker-based verification. The `js_preset()` in detect.rs exists but has never been tested end-to-end.

### Goals

- React-todo E2E completes successfully within 900s
- Implementer agents get JS/TS tools via `package.json` detection (already in `MARKER_ORDER`)
- Docker build succeeds and container serves the app
- Verification confirms the app renders and has todo functionality

### Non-Goals

- Testing SSR/Next.js patterns (we chose Vite SPA deliberately)
- Browser-level interaction testing with Playwright/Puppeteer (curl + DOM checks are sufficient)
- Solving node_modules in worktrees (same pattern as .venv - in .gitignore, not available)
- Hot reload or dev server testing (we test the production build)

## Proposed Solution

### File 1: `bin/e2e-targets/react-todo.sh`

**scaffold()** creates:
- `package.json` with vite, react, react-dom, tailwindcss, postcss, autoprefixer, @vitejs/plugin-react
- `vite.config.ts` - Vite config with React plugin, preview on port 4173
- `tailwind.config.js` - content paths for src/
- `postcss.config.js` - tailwind + autoprefixer
- `index.html` - HTML shell with `<div id="root">`
- `src/main.tsx` - React entry point rendering `<App />`
- `src/index.css` - Tailwind directives (@tailwind base/components/utilities)
- `Dockerfile` - multi-stage: node:20-alpine builds, nginx:alpine serves
- `.dockerignore` - node_modules, dist, .git
- `README.md` - todo app requirements
- `.gitignore` - node_modules/, dist/

**scaffold()** also runs `npm install` so the build tools are available in the main repo (same pattern as python-todo's `pip install pytest`). node_modules is in .gitignore so it won't appear in worktrees - implementers use bare `npm` commands which must be on PATH.

**target_validation_commands()** returns empty (phase-scoped in YAML).

**target_goal()** describes building a todo web app with React components, Tailwind styling, localStorage persistence.

**target_plan()** points to `react-todo.yml`.

**verify()** checks:
1. Key files exist: `src/App.tsx`, `src/main.tsx`, `Dockerfile`
2. `npm run build` succeeds (produces dist/)
3. `docker build -t loopr-e2e-react-todo .` succeeds
4. `docker run -d -p 4173:80 loopr-e2e-react-todo` starts a container
5. `curl http://localhost:4173` returns HTML containing "root" div
6. Container cleanup

**collect_results()** dumps src/App.tsx, src/main.tsx, Dockerfile.

### File 2: `bin/e2e-targets/react-todo.yml`

Two phases:

**Phase 1: Core todo logic and components**
- Work: Create `src/App.tsx` with todo state management and React components
  - TodoItem type: { id, title, done }
  - State: todos array in useState, persisted to localStorage
  - Functions: addTodo, toggleTodo, deleteTodo
  - UI: input + button to add, list of items with toggle/delete
  - resource_tags: ["src/App.tsx"]
- Validation: `npm run build` (confirms JSX compiles)

**Phase 2: Styling, filtering, and Docker**
- Work 1: Add Tailwind styling and filter controls to `src/App.tsx`
  - Filter buttons: All / Active / Done
  - Tailwind classes for layout, colors, hover states
  - resource_tags: ["src/App.tsx"]
  - dependencies: [app-component]
- Work 2: Verify Dockerfile builds and serves
  - No code changes needed - Dockerfile is scaffolded
  - Validation: `docker build -t loopr-e2e-react-todo .`
  - resource_tags: ["Dockerfile"]
  - dependencies: [app-component]
- Validation: `npm run build && docker build -t loopr-e2e-react-todo .`

### Detection

`package.json` is first in `MARKER_ORDER` in detect.rs. When an implementer worktree is created, `detect_project_tools` finds `package.json` and returns `js_preset()`: `npm test`, `npm run lint`, `npm run build`. No changes to detect.rs needed.

### Docker Strategy

The Dockerfile is scaffolded, not generated by the LLM. This keeps the E2E focused on React code generation, not Docker knowledge. The multi-stage build:

```dockerfile
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:alpine
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 80
```

Verification runs `docker build` and `docker run` + `curl` in verify(), not as validation-commands (Docker is infrastructure, not code quality).

### Timeout

1200s (20 minutes). React projects have more files and npm install is slow. The python-todo uses 900s for a simpler project.

## Alternatives Considered

### Alternative 1: LLM generates the Dockerfile
- **Description:** Include Dockerfile as a work item instead of scaffolding it
- **Pros:** Tests more of Loopr's capability
- **Cons:** Docker knowledge is orthogonal to the React test; adds failure modes unrelated to the goal
- **Why not chosen:** Scaffold provides a working container; the test is about React code generation

### Alternative 2: No Docker, just npm run build + serve
- **Description:** Skip Docker, verify with `npx vite preview`
- **Pros:** Simpler, fewer dependencies
- **Cons:** Misses the Docker verification goal; vite preview requires a running process to manage
- **Why not chosen:** Docker is a key part of the test's value proposition

### Alternative 3: Three phases (model, components, styling)
- **Description:** Separate todo logic from React components
- **Pros:** More granular; mirrors python-todo's model/CLI split
- **Cons:** In React, state and components are tightly coupled; splitting them creates artificial boundaries that confuse the LLM
- **Why not chosen:** Two phases (working app, then polish) is more natural for React

### Alternative 4: Include vitest/jest for unit tests
- **Description:** Add a testing phase with vitest
- **Pros:** Mirrors python-todo's pytest phase
- **Cons:** Adds vitest config complexity; React component testing requires jsdom; significantly more scaffold
- **Why not chosen:** Docker build + serve is the verification mechanism for this target. Unit testing can be a follow-up.

## Technical Considerations

### Dependencies

- **Docker** must be installed on the E2E host. scaffold() checks with `command -v docker`.
- **Node.js 20+** must be installed. scaffold() checks with `command -v node`.
- **npm** comes with Node.js.
- No new Rust dependencies.

### Testing Strategy

- `otto ci` verifies no regressions to existing code (no Rust changes in this doc)
- Manual run: `bin/e2e.sh --target react-todo`
- Acceptance: E2E exits 0, verify() passes all checks (files exist, build succeeds, Docker serves, curl returns React root)

### Risks and Mitigations

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| npm install slow in scaffold | Medium | Low | One-time cost; cached after first run |
| node_modules missing in worktrees | High | Medium | Same as .venv - implementers use bare npm; commands must be on PATH |
| Docker not installed on host | Low | High | scaffold() checks and fails fast with actionable error |
| Port 4173 already in use | Low | Low | verify() uses a random high port or cleans up before starting |
| LLM generates JSX that doesn't compile | Medium | Medium | Phase 1 validation runs npm run build; failures retry normally |

## Implementation Plan

4. Run `bin/e2e.sh --target react-todo` and verify completion
