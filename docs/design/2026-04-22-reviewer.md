# Design Document: Stage 8 Reviewer Agent

**Author:** Claude (with Scott)
**Date:** 2026-04-22
**Status:** Implemented
**Review Passes Completed:** 5/5 (self-review) + Architect R1 findings folded + Architect R1 follow-up (Finding 1a OCC-placement interpretation confirmed closed); all 2026-04-22
**Crates touched:** `domain`, `store`, `context`, `agents`, `llm`. Scoped to the agent-side contract; daemon wiring (how a Bundle reaches a Reviewer, how a Verdict triggers the Integrator) is out of scope for this doc and lives in the Stage 8 wiring capstone.

## Summary

The Reviewer is a single-iteration LLM agent that reads an Implementer-produced `Bundle`, renders the Bundle's commit diff plus the Work's acceptance criteria into a prompt via `context::build_for_reviewer`, calls `LlmClient::complete_free` with a parse-retry sub-loop, and returns a typed `Verdict` in `{ Accept, ChangeRequested, Reject }`. On success it updates the Bundle's FSM state (`Triaged -> Reviewed` or `Triaged -> Rejected`) and its `verification` field, with intra-daemon OCC (optimistic concurrency control) preventing silent overwrite. The Verdict itself is a typed enum returned to the caller; the daemon (Stage 8 wiring) decides what to do with it.

Ported from v3/v4's battle-tested reviewer with the same two-layer split (rich Verdict in the function return, coarse `Reviewed` / `Rejected` in the Bundle FSM). v5 simplifies: no `Learning` side-effects, no advisory-race fallback (no Coordinator in first gate), no referenced-signatures extraction (deferred).

## Problem Statement

### Background

Stage 7 ends with a persisted `Bundle` at status `Proposed`: an Implementer has run in a worktree, committed changes on `loopr/wk-<work-id>-<seq>`, and recorded `head_commit` + `paths` + `claims` on the Bundle. Stage 8 starts the review/integration pipeline: the daemon must decide whether each Bundle is fit to merge into the Plan's integration branch.

### Problem

v5 has no Reviewer agent. A Bundle sits forever at `Proposed` with no mechanism to transition it toward `Accepted` (and thence to the Integrator) or `Rejected` (and thence to retry or abort). Without a Reviewer, the Stage 8 exit criterion ("approved Bundle lands on the integration branch and produces a Tick record") is unreachable.

### Goals

- `run_reviewer(bundle, work, deps) -> Result<Verdict, ReviewerError>` runs a single LLM turn (plus parse-retry sub-loop) and returns a typed Verdict.
- `domain::Verdict` enum with three variants: `Accept { summary }`, `ChangeRequested { summary, reasons: Vec<ReviewIssue> }`, `Reject { reason }`.
- `domain::ReviewIssue { severity, file, line, message, suggestion }` and `domain::Severity { Error, Warning, Info }` as the structured-feedback types.
- `BundlesStore::update(&self, bundle, expected_updated_at) -> Result<(), StoreError>` added to the `store` crate, with intra-daemon OCC via an internal `tokio::sync::Mutex` + `updated_at` version check. Returns `StoreError::Stale { expected, actual }` on version mismatch. Parallel to the Stage-7 `WorksStore::update` addition in structure, but OCC-aware (the Stage-7 addition is blind-write; this doc does not retrofit OCC onto WorksStore, only adds it for Bundles where the race matters).
- `context::build_for_reviewer(bundle, work, diff, noop_files) -> Result<AssembledContext, ContextError>` assembles the system prompt plus a user message rendering Plan/Spec/Phase/Work hierarchy, acceptance criteria, Bundle metadata, and either the commit diff OR pre-read file contents for noop bundles. `context` performs no I/O; `agents::reviewer` owns both git-diff extraction and file-content reads.
- `AgentsConfig { implementer: ImplementerConfig, reviewer: ReviewerConfig }` struct in `crates/agents/src/config.rs` (new; `ImplementerConfig` currently stands alone there).
- Bundle FSM transitions (inside `run_reviewer`, via injected `BundleUpdateSink`):
  - `Accept` -> `Triaged -> Reviewed` by `Role::Reviewer`; Bundle.verification set to a one-line summary.
  - `ChangeRequested` -> `Triaged -> Rejected` by `Role::Reviewer`; Bundle.verification records the issues for the next Implementer attempt.
  - `Reject` -> `Triaged -> Rejected` by `Role::Reviewer`; Bundle.verification records the reason.
- Parse-retry sub-loop mirrors the Implementer's: on unparseable JSON, append `(assistant: raw, user: error)` to the local messages vec, re-call the LLM, bounded by `max_requeries` per invocation.

### Non-Goals

Structural (deferred to other docs):

- **Daemon wiring.** How a newly-persisted Bundle reaches a Reviewer task, how a Verdict triggers a retry or an Integrator, how the daemon's `implementer_tasks` JoinSet becomes a `reviewer_tasks` JoinSet: all lives in the Stage 8 wiring capstone doc (`docs/design/2026-04-22-stage-8-wiring.md`, not yet written).
- **Integrator.** Separate design doc (`docs/design/2026-04-XX-integrate.md`, upcoming). The Reviewer's output shape is the Integrator's input shape; defining Verdict correctly is this doc's contribution to that seam.
- **Reviewer-triggered Implementer retry.** The daemon (Stage 8 wiring) decides whether `ChangeRequested` means "spawn a new Implementer with the verdict as context" or "mark Work `Blocked`". The Reviewer just returns the Verdict.
- **Multi-iteration review.** A Reviewer never re-prompts itself across iterations; one LLM turn plus bounded parse-retry is the full loop. Any "try again" behavior is the daemon's call, not the Reviewer's.
- **Cross-process OCC on Bundles.** Loopr's threat model is single-daemon-per-target (vision line 295, `.loopr/daemon.pid` lockfile). The Mutex-based OCC in `BundlesStore::update` is intra-daemon. Multi-daemon or external-writer OCC would require upstream changes to `taskstore-async` (a `update_if_version_matches` primitive); not in first-gate scope.

Feature scope (deferred to a real-run motivation):

- **Referenced-signatures cross-module prompt enrichment.** v4's `extract_referenced_signatures` walks imports to give the LLM cross-module visibility. Useful, but not required by the Stage 8 exit criterion.
- **Reviewer-generated `Learning` records.** v4's reviewer created a Learning per review to feed future Implementer prompts. Defer until learning consumption is also built; v5 first gate has no learning store.
- **Advisory-race fallback.** v4 handled the case where a Coordinator accepted a Bundle directly while a Reviewer was running asynchronously. v5 has no Coordinator agent (vision line 597), so there is no race. If this class of concurrency reappears, it will be solved in wiring, not inside `run_reviewer`.

Data-model (deferred until a query demands it):

- **`Verdict` as a `Record`.** The Verdict flows through the Reviewer return value. Its outcome is encoded in Bundle state (`Reviewed` vs `Rejected`) + Bundle.verification (text summary). No `verdicts.jsonl` in first gate. Earn it when a real run surfaces a "what did the reviewer say six days ago" query.

## Proposed Solution

### Overview

Call-flow in one paragraph. The daemon (Stage 8 wiring, out of scope here) triages the Bundle from `Proposed` to `Triaged` using `Role::Coordinator` as a rubber-stamp role identifier (see Invariants: "Role::Coordinator as identifier"), then hands `run_reviewer` a `&Bundle` at status `Triaged` and the matching `&Work`. The Reviewer (a) asserts `bundle.work_id == work.id`, (b) extracts the diff via `git show` for commit bundles or reads file contents via `std::fs` for noop bundles, all inside `agents::reviewer` (never inside `context`), (c) asks `context::build_for_reviewer` to assemble a system prompt + user message, (d) calls `LlmClient::complete_free` once with a bounded parse-retry sub-loop, (e) parses the result into a `Verdict`, (f) clones the Bundle, writes `verification` and transitions the clone's status, persists via `BundleUpdateSink::update` with OCC on `updated_at`, and (g) returns the Verdict. No outer iteration, no Lifeguard, no force-path fallback: one call, one verdict, mutation-on-clone so the caller's `Bundle` stays untouched.

### Loop contract

```
run_reviewer(bundle, work, deps):
  1. assert bundle.work_id == work.id -> else Err(Mismatch)
  2. (diff, noop_files) = match bundle.head_commit {
       Some(sha) => {
         raw = git_show(&deps.target, sha, &bundle.paths)?
         // strip commit header; detect empty patch body
         body = strip_commit_header(&raw)
         // `body` may be empty on structural corruption; prompt handles it
         (body, None)
       }
       None => {
         // noop bundle: read file contents with aggregate cap
         files = read_file_contents(&deps.target, &bundle.paths)?
         ("", Some(files))
       }
     }
  3. AssembledContext = deps.context.build_for_reviewer(
       bundle, work, &diff, noop_files.as_deref())?
  4. messages = [ChatMessage::user(user_message)]
     requeries = 0
     loop {
       raw = deps.llm.complete_free(&system_prompt, &messages).await?
       match parse_verdict(&raw):
         Ok(v)  => break v
         Err(e) => {
           requeries += 1
           if requeries > deps.config.max_requeries {
             return Err(EscalationNeeded("parse exhausted"))
           }
           messages.push(assistant: raw)
           messages.push(user: "parse failed: {e}. Return one JSON object
             matching the schema in the system prompt.")
         }
     }
  5. let expected_updated_at = bundle.updated_at   // OCC version snapshot
     let mut bundle = bundle.clone()               // mutation-on-clone
     bundle.verification = match verdict {
       Accept { summary }            => format!("Reviewer approved: {summary}")
       ChangeRequested { summary, reasons } =>
         render_issue_summary(&summary, &reasons)  // capped at VERIFICATION_CAP
       Reject { reason }             => format!("Rejected: {reason}")
     }
     let target_status = match verdict {
       Accept { .. }          => BundleStatus::Reviewed
       ChangeRequested { .. } => BundleStatus::Rejected
       Reject { .. }          => BundleStatus::Rejected
     }
     bundle.transition(target_status, Role::Reviewer)
       .map_err(|e| ReviewerError::Transition(e.to_string()))?
  6. deps.store.update(bundle, expected_updated_at).await?
     // StoreError::Stale bubbles up via ReviewerError::Update
  7. return Ok(verdict)
```

No outer iteration loop. No Lifeguard (no repeated-action class to detect: one turn, one verdict). No force-path fallback: if the LLM refuses to produce a parseable verdict after `max_requeries`, that's an escalation; there is nothing analogous to "force-propose a bundle anyway."

### Invariants

- **Parse-retry is per-invocation, not per-Bundle.** `max_requeries` is consumed within the single `run_reviewer` call; on exhaustion the function returns `Err(ReviewerError::EscalationNeeded)`. The daemon decides whether a retry invocation is justified.
- **Bundle status precondition is `Triaged`.** The FSM has `Triaged -> Reviewed` and `Triaged -> Rejected` transitions gated by `Role::Reviewer`. If `run_reviewer` is called on a Bundle in any other status, the FSM rejects the transition and the function returns `Err(ReviewerError::Transition(...))`. The Reviewer does not itself move a Bundle from `Proposed` to `Triaged`; that is the daemon's responsibility (Stage 8 wiring).
- **`Role::Coordinator` is an identifier, not an agent instance.** Vision line 597 forbids a Coordinator *agent* in first gate; it does not forbid the `Role::Coordinator` *enum variant* from being used as a role identifier when the daemon acts as orchestrator. The daemon passes `Role::Coordinator` to `bundle.transition(Triaged, Role::Coordinator)` in the Stage 8 wiring code. The Bundle FSM accepts it because the transition table gates on the role identifier, not on the presence of a Coordinator task. This is a load-bearing distinction: without it, every `Proposed => *` transition in the FSM table (`crates/domain/src/bundle.rs:43-49`) is unreachable in first gate. Future Coordinator-agent design must reconcile with this daemon occupancy of the role identifier.
- **`work.id == bundle.work_id` is checked up front.** A wiring bug that paired a Bundle with the wrong Work would otherwise review the change against someone else's AC and silently approve/reject. Early assertion, typed `ReviewerError::Mismatch`, no LLM call wasted.
- **Verification is written before the transition, not after.** A `Reviewed` Bundle has an approval summary; a `Rejected` Bundle has reasons or a rejection message. The Integrator and any downstream Implementer retry can trust the field without re-consulting the Verdict.
- **Mutation is on a clone, not on the caller's `&Bundle`.** The function signature takes `&Bundle`; the loop clones once, snapshots `updated_at` as the OCC expected-version, mutates the clone, persists via `BundleUpdateSink::update(bundle, expected_updated_at)`. On `Err` (including `Stale`), the caller's Bundle is untouched and re-callable.
- **Intra-daemon OCC via Mutex + `updated_at` version check.** `BundlesStore::update` holds a `tokio::sync::Mutex` (per-collection, in the `BundlesStore` struct) that serializes read-check-write. The method (a) acquires the Mutex, (b) reads the current Bundle by id, (c) compares its `updated_at` against the `expected_updated_at` argument, (d) returns `StoreError::Stale { expected, actual }` on mismatch without writing, (e) writes otherwise, (f) releases the Mutex. This closes the intra-daemon race the advisor and Architect both flagged: two Reviewer tasks in one daemon racing on the same Bundle see the mismatch and the second call returns `Stale` instead of silently clobbering the first call's `verification`. Cross-process OCC is not in scope (see Non-Goals).
- **`ChangeRequested` and `Reject` both land at `Rejected` in the FSM; only the Verdict carries the retry hint.** The FSM is deliberately coarse: approved or not. The Verdict (typed enum, returned value) is the signal the daemon uses to decide between "retry with a new Implementer attempt" (`ChangeRequested`) and "this approach is wrong, mark Work Blocked" (`Reject`). Code outside this module does not re-infer the three-way from Bundle state alone.
- **Diff body emptiness is detected by parsing, not by output length.** `git show --format=medium --no-color --patch <head_commit> -- <paths...>` always emits a commit header (hash, author, date, message) even when `paths` filters out all changes. The `strip_commit_header` helper locates the first `diff --git` marker; everything before it is header, everything from it onward is the patch body. If no `diff --git` marker is present, the body is empty and the prompt is told "diff body empty on non-noop bundle; treat as structural corruption." Raw output length is never used as the emptiness signal.
- **I/O is owned by `agents::reviewer`, never by `context`.** `context::build_for_reviewer` is a pure template renderer: it takes a pre-extracted `diff: &str` and optional pre-read `noop_files: Option<&[(String, String)]>` and produces `AssembledContext`. All `std::process::Command` and `std::fs` calls live in `agents::reviewer` helpers. This preserves `crates/context/CLAUDE.md`'s "pure prompt assembly" rule.
- **`force_proposed: true` is surfaced explicitly to the LLM.** The system prompt carries a note that when `force_proposed` is set, the Bundle represents the Implementer hitting its iteration cap without an explicit `ProposeBundle`. The Reviewer is guided to treat such Bundles with heightened skepticism: prefer `ChangeRequested` over `Accept` unless the diff is self-evidently complete and correct. This mirrors v4's lesson that force-propose output is empirically lower quality.

### Data Model

#### `Verdict` (`crates/domain/src/verdict.rs`) - the headline contract

New file. Not a `Record` (no JSONL persistence, no SQLite index, no FSM). Pure data carrier.

```rust
use serde::{Deserialize, Serialize};

#[derive(Debug, Clone, Serialize, Deserialize)]
#[serde(tag = "kind", rename_all = "snake_case", deny_unknown_fields)]
pub enum Verdict {
    Accept {
        summary: String,
    },
    ChangeRequested {
        summary: String,
        reasons: Vec<ReviewIssue>,
    },
    Reject {
        reason: String,
    },
}

#[derive(Debug, Clone, Serialize, Deserialize)]
#[serde(deny_unknown_fields)]
pub struct ReviewIssue {
    pub severity: Severity,
    pub file: String,
    #[serde(default)]
    pub line: Option<u32>,
    pub message: String,
    #[serde(default)]
    pub suggestion: Option<String>,
}

#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize, Deserialize)]
#[serde(rename_all = "lowercase")]
pub enum Severity {
    Error,
    Warning,
    Info,
}
```

Why `ChangeRequested` carries both `summary: String` AND `reasons: Vec<ReviewIssue>`: the summary is the one-liner written into `Bundle.verification` for quick scanning; the reasons are the structured payload that a future Implementer retry prompt will consume issue-by-issue. Keeping both in the Verdict means the daemon does not reconstruct structure from a rendered string.

Why `Verdict` is not a `Record`: there is no query like "list verdicts for bundle X" that isn't answerable from `Bundle.verification` + `Bundle.status`. Adding a `Verdicts` collection would require a second write per review, a new taskstore JSONL file, new indexes, all for data already on the Bundle. Revisit when a real run surfaces a query this denormalization can't answer.

Why Severity is distinct from Verdict kind: a single review can have `Error` / `Warning` / `Info` issues while verdict is `ChangeRequested` or even `Accept` (approval with non-blocking notes). `loopr-v4/resources/agents/reviewer.pmt` codifies the distinction: blocking issues force `request_changes`, non-blocking issues are advisory. v5 inherits that taxonomy.

#### `ReviewerConfig` and `AgentsConfig` (`crates/agents/src/config.rs`)

`ImplementerConfig` currently stands alone in that file. This doc adds a sibling config and a composing wrapper.

#### `BundlesStore::update` (`crates/store/src/bundles.rs`)

New method with intra-daemon OCC. `BundlesStore` currently has `create`/`get`/`list`/`list_by_work_id`; this doc adds `update` with a version check. The Stage-7 `WorksStore::update` is blind-write (fine for Works, where there is no concurrent writer); Bundles need OCC because multiple Reviewer tasks can race on the same Bundle.

```rust
use tokio::sync::Mutex;

pub struct BundlesStore<'a> {
    inner: &'a AsyncStore,
    // New. Serializes read-check-write inside one daemon.
    update_lock: Mutex<()>,
}

#[derive(Debug, thiserror::Error)]
pub enum StoreError {
    // ... existing variants ...
    #[error("stale bundle: expected updated_at={expected}, actual={actual}")]
    Stale { expected: i64, actual: i64 },
    #[error("bundle not found: {0}")]
    NotFound(String),
}

impl<'a> BundlesStore<'a> {
    pub async fn update(
        &self,
        bundle: Bundle,
        expected_updated_at: i64,
    ) -> Result<(), StoreError> {
        let _guard = self.update_lock.lock().await;
        let current = self
            .inner
            .get::<Bundle>(bundle.id.as_ref())
            .await?
            .ok_or_else(|| StoreError::NotFound(bundle.id.to_string()))?;
        if current.updated_at != expected_updated_at {
            return Err(StoreError::Stale {
                expected: expected_updated_at,
                actual: current.updated_at,
            });
        }
        self.inner.update(bundle).await.map_err(Into::into)
    }
}
```

Prerequisite for Phase 3: without it, the Reviewer cannot persist its FSM transition + verification update, and the Architect-flagged silent-overwrite race cannot be closed. See Invariants: "Intra-daemon OCC via Mutex + `updated_at` version check."

Scope note: cross-process OCC (multi-daemon, or an external writer modifying the JSONL while loopr runs) would require upstream changes to `taskstore-async::AsyncStore::update` (currently documented as "alias for create" at `crates/taskstore-async/src/store.rs:120`). Loopr's threat model is single-daemon-per-target (vision line 295, `.loopr/daemon.pid` lockfile) plus never-push (vision line 515), so the intra-daemon Mutex is sufficient for first gate. See Non-Goals.

#### `ContextBuilder::build_for_reviewer` (`crates/context/src/reviewer.rs`)

New method on the existing `ContextBuilder` trait (additive; no breaking change to `build_for_implementer`).

```rust
pub trait ContextBuilder: Send + Sync {
    fn build_for_implementer(&self, /* unchanged */) -> Result<AssembledContext, ContextError>;

    fn build_for_reviewer(
        &self,
        bundle: &Bundle,
        work: &Work,
        diff: &str,
        noop_files: Option<&[(String, String)]>,
    ) -> Result<AssembledContext, ContextError>;
}
```

Signature choices:

- `diff: &str` is pre-extracted by `agents::reviewer::git_show` with header stripped; empty string denotes "no commit" (noop bundle) OR "body empty on non-noop" (corruption; the prompt handles both explicitly).
- `noop_files: Option<&[(String, String)]>` is pre-read by `agents::reviewer::read_file_contents` with both per-file and aggregate caps applied. `None` means "not a noop bundle; render `Diff` section"; `Some(files)` means "noop bundle; render `File Contents` section from these pairs."
- No `target_path` parameter. All I/O is upstream of `context`; the template renderer gets only text. This is the resolution of the Architect's "contradictory I/O boundary" finding: `agents` owns both git-diff extraction and file-content reads, preserving `context/CLAUDE.md`'s "pure prompt assembly" rule.

System prompt: rewritten for the tagged-Verdict schema. Structurally follows v4's blocking criteria 1-4, non-blocking 5-10, verdict thresholds, but the JSON output-schema block emits the tagged form (`{"kind": "accept", "summary": "..."}` etc.) so the LLM output matches serde's internal-tag deserializer. v4's flat `{"verdict": "approve", ...}` schema is not carried forward; reusing it would produce parseable-but-wrong-schema output that drops into the parse-retry path on every call.

Prompt additions beyond v4:

- `force_proposed` guidance: "When the Bundle metadata shows `force_proposed: true`, the Implementer hit its iteration cap without an explicit propose action. Treat the code with heightened skepticism; prefer `change_requested` unless the diff is self-evidently complete."
- `change_requested` with zero reasons: "`change_requested` MUST include at least one issue in `reasons`. A bare `change_requested` with an empty `reasons` array is invalid."
- Empty-diff on non-noop: "If the `Diff` section says `(empty patch body: structural corruption; see system prompt)`, the Bundle is structurally broken. Emit `change_requested` with a single Error-severity issue describing the inconsistency."
- Truncation awareness: "If the `Diff` section ends with `[... diff truncated; ...]`, you are seeing only part of the change. Do not approve unless the visible portion alone demonstrates the AC are met; otherwise prefer `change_requested` citing the truncation."

#### `ReviewerError`

```rust
#[derive(Debug, thiserror::Error)]
pub enum ReviewerError {
    #[error("work/bundle mismatch: bundle.work_id={0} vs work.id={1}")]
    Mismatch(String, String),
    #[error("escalation needed: {0}")]
    EscalationNeeded(String),
    #[error("llm error: {0}")]
    Llm(#[from] llm::LlmError),
    #[error("context error: {0}")]
    Context(#[from] context::ContextError),
    #[error("bundle update failed: {0}")]
    Update(#[from] BundleUpdateError),
    #[error("fsm transition rejected: {0}")]
    Transition(String),
    #[error("git error: {0}")]
    Git(String),
    #[error("io error: {0}")]
    Io(#[from] std::io::Error),
}

#[derive(Debug, thiserror::Error)]
pub enum BundleUpdateError {
    #[error("bundle update failed: {0}")]
    Update(String),
    /// New. OCC version-check failure from BundlesStore::update.
    #[error("stale bundle: expected updated_at={expected}, actual={actual}")]
    Stale { expected: i64, actual: i64 },
}
```

`Transition(String)` rather than `Transition(#[from] FsmError<BundleStatus>)` because `FsmError` is generic; `#[from]` on a generic breaks the `thiserror` macro pattern. The `.to_string()` at the call site preserves the FsmError Display for diagnostics; structured access isn't needed by the daemon.

`BundleUpdateError::Stale` is a dedicated variant (not folded into `Update(String)`) so the daemon can match on it specifically in the Stage 8 wiring capstone: stale-on-update means another Reviewer task beat us to the punch and the daemon should drop this Verdict silently rather than escalate.

### API

```rust
// crates/agents/src/reviewer.rs

use std::path::PathBuf;
use std::future::Future;

use context::ContextBuilder;
use domain::{Bundle, Role, Verdict, Work};
use llm::{ChatMessage, LlmClient};

use crate::config::ReviewerConfig;

/// Minimal Bundle-update interface for the Reviewer. Mirrors
/// `BundleSink` from the Implementer (single-method trait so per-Work
/// test fakes stay tiny). Passes the OCC `expected_updated_at`
/// snapshot the Reviewer took before mutating.
pub trait BundleUpdateSink: Send + Sync {
    fn update<'a>(&'a self, bundle: Bundle, expected_updated_at: i64)
        -> impl Future<Output = Result<(), BundleUpdateError>> + Send + 'a;
}
```

Signature decisions:

- `&Bundle` + `&Work`, not just `&Bundle`: vision line 165 writes `run_reviewer(bundle: &Bundle, deps: &Deps<...>)` informally. This doc upgrades to include `&Work` because the Reviewer's primary comparison is against the Work's acceptance criteria. Fetching Work from the store inside `run_reviewer` would require a `WorkStore` dep; passing `&Work` pushes that fetch to the daemon (which already has the Work in hand after `handle_plan_create`'s decompose step).
- `ReviewerDeps<L, S, C>`, not `Deps<L, T, S, C>`: no `ToolExecutor`. The Reviewer never invokes Tools; it reads the diff via a private git helper and reads file contents via `std::fs`, both infrastructure, not agent-callable capability. Mirrors the Implementer's shape without `T`.
- Return `Verdict`, not `Bundle`: the Bundle is mutated on a clone and persisted via `deps.store.update(bundle, expected_updated_at)`. The caller (daemon) needs the Verdict for downstream routing; it can re-read the Bundle from the store if it needs the mutated form.
- `BundleUpdateSink::update` now takes `expected_updated_at: i64` as a second parameter. Mirrors `BundlesStore::update`'s OCC signature; the trait is the agent-side view of the store method.
- `target: PathBuf` on `ReviewerDeps` (not on every function call): per-daemon constant. Cheap to clone on `Deps` construction.

### Bundle FSM - transitions consumed

Per `crates/domain/src/bundle.rs:42-58` (already in the tree from Stage 7):

```
Proposed  => Triaged           by (Coordinator)   // daemon uses Role::Coordinator identifier
Triaged   => Reviewed          by (Coordinator, Reviewer)
Triaged   => Rejected          by (Coordinator, Reviewer)
Reviewed  => Rejected          by (Coordinator, Reviewer)  // unused by this doc
```

This doc exercises `Triaged -> Reviewed` and `Triaged -> Rejected`, both via `Role::Reviewer`. The `Proposed -> Triaged` transition is called by the daemon (Stage 8 wiring) using `Role::Coordinator` as an identifier per the "Role::Coordinator as identifier" invariant. The `Reviewed -> Rejected` transition is listed but not exercised by `run_reviewer` (a re-review that downgrades an approval is a wiring-level concern, not this function's contract).

No FSM changes are required. The existing `Bundle::transition(target, role)` method handles the mutation; `run_reviewer` calls it with explicit error conversion.

### Phase 3: Core `run_reviewer` loop
**Model:** opus

Non-mechanical: git diff header-stripping + body-emptiness detection, aggregate noop-file budgeting, parse-retry invariants, mismatch detection, OCC snapshot timing. Needs judgment.

- `crates/agents/src/reviewer.rs`: full `run_reviewer`. Helpers:
  - `git_show(target, head_commit, paths) -> Result<String, ReviewerError>` wraps `tokio::process::Command` on `git -C <target> show --format=medium --no-color --patch <head_commit> -- <paths...>`. On non-zero exit (unreachable commit, permission error), returns `ReviewerError::Git(...)`. Empty `paths` list means "full diff of commit." Returns raw output (header + body).
  - `strip_commit_header(raw: &str) -> &str` finds the first `diff --git ` line; returns the slice from there to end. If absent, returns `""`. Stable, no allocation.
  - `truncate_diff(body: &str, cap: usize) -> String` returns either `body` verbatim if `body.len() <= cap`, or a UTF-8-char-boundary-safe prefix up to `cap` bytes concatenated with `"\n[... diff truncated; original {body.len()} bytes, shown first {cut} bytes]\n"`. Cap comes from `ReviewerConfig::diff_byte_cap`.
  - `read_file_contents(target, paths, cap) -> Result<Vec<(String, String)>, ReviewerError>`: reads each file under `target`, applies a **per-file** cap of `cap / paths.len().max(1)` with a floor of 2048 bytes, and enforces an **aggregate** cap of `cap` bytes across all files. Uses the same `cap_str`-style UTF-8 boundary-safe truncation. Missing files render as `(file not found)`. Cap comes from `ReviewerConfig::noop_files_byte_cap`.
  - `parse_verdict(raw) -> Result<Verdict, ParseError>`: strip markdown fences, try `serde_json::from_str` directly, fall back to first-`{` / last-`}` substring and retry. Returns distinct `ParseError::Unparseable` (not JSON) vs `ParseError::Schema` (JSON but wrong shape) so the re-prompt message can be specific. Also returns `ParseError::Schema` on `change_requested` with an empty `reasons` array (belt-and-suspenders with the prompt).

- Tests (`crates/agents/src/reviewer/tests.rs`):

## Alternatives Considered

### Alternative 1: Verdict as a `Record` in TaskStore

- **Description:** Add `Verdicts` collection, JSONL at `.loopr/taskstore/verdicts.jsonl`, one record per `run_reviewer` completion.
- **Pros:** Full audit trail; a future "list all reviews that said X" query is trivial.
- **Cons:** Doubles the write per Bundle review. Data is already derivable from `Bundle.verification` + `Bundle.status`. New index surface, new FSM-or-not question, new migration risk.
- **Why not chosen:** Defer until a real run asks a query that denormalization can't answer.

### Alternative 2: Single `Reviewed` verdict + `verification` field parsing

- **Description:** Skip the typed `Verdict` enum. Encode the three-way outcome purely in `Bundle.verification` prefix.
- **Pros:** Zero new types in `domain`.
- **Cons:** Downstream consumers re-parse strings to distinguish `ChangeRequested` from `Reject`. Stringly-typed anti-pattern v5 was rewritten to eliminate (vision line 28).
- **Why not chosen:** Typed Verdict is the v5 thesis.

### Alternative 3: Reviewer owns Bundle transition directly, bypassing `BundleUpdateSink`

- **Description:** `run_reviewer` takes `&mut Bundle`. Mutates in-place. Caller handles persistence.
- **Pros:** No `BundleUpdateSink` trait.
- **Cons:** Breaks symmetry with Implementer. Callers who forget to persist lose the transition silently. OCC signature would bleed into the caller.
- **Why not chosen:** Persistence-at-agent-exit is the established pattern.

### Alternative 4: Inject a `GitReader` trait instead of a private `git_show` helper

- **Description:** Define `GitReader` in `agents`. Production impl shells out to git; test fake returns canned diffs.
- **Pros:** Testable without a real git repo.
- **Cons:** Every Reviewer test needs a `FakeGitReader`; noop path needs a `FakeFsReader`. Explodes the fake surface.
- **Why not chosen:** Implementer uses the same private-helper pattern. Consistency.

### Alternative 5: Make Verdict a re-export of `BundleStatus`

- **Description:** Return `BundleStatus` directly with a sidecar `summary`.
- **Cons:** Loses the three-way `Accept` / `ChangeRequested` / `Reject` distinction.
- **Why not chosen:** The rich Verdict is the whole point.

### Alternative 6: Cross-process OCC via upstream `taskstore-async::update_if`

- **Description:** Push a `update_if<T, F>(record, predicate: F)` primitive into `scottidler/taskstore`'s async crate. `BundlesStore::update` dispatches the version check inside the writer thread; true atomic CAS, immune to any number of concurrent writers.
- **Pros:** Protects against multi-daemon, external-editor, and git-merge-driver races.
- **Cons:** Upstream PR + workspace tag bump; none of those races are in loopr's current threat model (single-daemon-per-target, never-push).
- **Why not chosen:** YAGNI. The intra-daemon Mutex closes the race the Architect and advisor both flagged. Promote to Alternative-6 upstream work when the threat model grows (multi-daemon, push-to-remote, etc.).

## Technical Considerations

### Dependencies

No new external crates.

- `agents` (existing deps extended): uses `tokio::process::Command` for `git_show` (already pulled in by the Implementer's helpers); `std::fs` for noop-bundle file reads.
- `context` (existing): adds an inline string template; no new deps; no I/O.
- `domain` (existing): adds a file; serde is already a dep.
- `llm` (unchanged): `ChatMessage` + `complete_free` landed in Stage 7.
- `store` (existing): adds `BundlesStore::update` + `tokio::sync::Mutex` field; tokio is already a dep.

No upstream work needed on `scottidler/taskstore`. Intra-daemon OCC is achievable with the existing `AsyncStore::get` + `AsyncStore::update` primitives held together by a loopr-v5-side Mutex.

### Performance

- One LLM call per `run_reviewer` invocation (plus up to `max_requeries` re-prompts; default 3). Dominated by LLM latency (~10-30s per call).
- `git_show` + `strip_commit_header` + `truncate_diff` is a single subprocess spawn and two string passes. Negligible against LLM latency.
- Diff truncation: enforced at `ReviewerConfig::diff_byte_cap` bytes (default 64 KiB) via `truncate_diff` in `agents::reviewer` before the string hits `context::build_for_reviewer`. No "deferred" truncation; a vendored-dependency-update Bundle does not wedge the Reviewer loop.
- Noop-Bundle file reads: enforced aggregate cap at `ReviewerConfig::noop_files_byte_cap` (default 64 KiB); per-file cap is derived as `noop_files_byte_cap / paths.len().max(1)` floor 2048, so a 30-path noop bundle still fits a bounded prompt.
- `BundlesStore::update` Mutex lock held only for the duration of one read + one write (microseconds on SQLite + JSONL append). Not a contention hotspot; concurrent Reviewer tasks on *different* Bundles do not contend on it only because the Mutex is per-collection. If per-Bundle contention becomes measurable, upgrade to a per-Bundle-id lock map.

### Security

- `git_show`'s arguments are all derived from Bundle fields controlled by the Implementer or the decomposer. `head_commit` is a SHA (no shell metacharacters); `paths` come from the Implementer's `git ls-files --modified`. `tokio::process::Command::arg()` is used per-argument (not `sh -c`).
- `read_file_contents` reads paths relative to `target`; no traversal protection added here because the target is a trusted repo. The `path_deny_patterns` sandbox check applies at tool dispatch time, not here. If an Implementer somehow records a `../../../etc/passwd` path on a Bundle, that is a Stage-7 bug to fix at the source.
- `Bundle.verification` is written on the clone before the FSM transition; if the transition fails (or OCC stale), the caller's original Bundle is untouched (mutation-on-clone invariant).

### Testing Strategy

Per `CLAUDE.md` "Seam tests, not only unit tests":

**Unit (in `reviewer/tests.rs` and `store/bundles/tests.rs`):**
- Each Verdict variant serde round-trip (domain tests).
- `parse_verdict` handles direct JSON, fenced code blocks, prose-wrapped JSON, distinguishes Unparseable vs Schema, rejects empty-reasons change_requested as Schema.
- `render_issue_summary` truncates at `VERIFICATION_CAP`.
- `strip_commit_header` returns empty on header-only output; returns body from `diff --git ` onward.
- `truncate_diff` respects UTF-8 char boundaries and appends the correct marker.
- `read_file_contents` enforces aggregate + per-file caps.
- Each Bundle-status precondition: `Triaged` accepted; others produce `ReviewerError::Transition`.
- `work.id != bundle.work_id` produces `ReviewerError::Mismatch` before any LLM call.
- `BundlesStore::update` OCC: matching expected -> Ok; mismatch -> `StoreError::Stale`; not-found -> `StoreError::NotFound`; concurrent-update serialization -> exactly-one-winner.

**Seam (in `tests/reviewer_seam.rs` and `tests/reviewer_concurrency.rs`):**

**Integration (in `tests/implementer_then_reviewer.rs`):**

**Out of scope:**

## Risks and Mitigations

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Reviewer LLM returns unparseable JSON consistently | Med | Med | Parse-retry sub-loop with `max_requeries=3`; on exhaustion, `EscalationNeeded`; daemon decides retry vs block |
| LLM emits v4-schema (`{"verdict": ...}`) instead of tagged v5 schema | Med | Med | System prompt explicitly shows tagged schema; `parse_verdict` returns `ParseError::Schema` so re-prompt is specific |
| Bundle in wrong status when Reviewer runs (e.g., daemon forgot to triage) | Low | High | FSM rejection surfaces as `ReviewerError::Transition`; Stage 8 wiring capstone integration test asserts `Proposed -> Triaged` before `run_reviewer` |
| `bundle.work_id != work.id` (wiring bug) | Low | High | Up-front mismatch assertion returns `ReviewerError::Mismatch` before any LLM call |
| Diff too large for LLM context window (formatting pass, vendor update, broad rename) | Med | Med | `ReviewerConfig::diff_byte_cap` (64 KiB default) enforced by `truncate_diff` in Phase 3; LLM sees a truncation marker and is prompted to prefer `change_requested` when the visible portion is insufficient. No "deferred" defense |
| `head_commit` unreachable (GC'd, rebased away) | Low | Med | `git show` exits non-zero -> `ReviewerError::Git(...)`; daemon decides block vs re-dispatch |
| Empty patch body on non-noop Bundle (structural corruption) | Low | Med | `strip_commit_header` detects absence of `diff --git` marker; prompt renders the structural-corruption marker; LLM is guided to emit `change_requested` with an Error-severity issue. Never "empty-string equals OK" |
| `force_proposed: true` Bundles approve too readily | Med | Med | System prompt explicitly guides skepticism |
| Noop Bundle approval bypasses real AC check | Low | High | Prompt requires the Reviewer to verify each AC against file contents; Phase 3 test coverage |
| Noop Bundle with many paths overflows the prompt | Med | Med | Aggregate cap at `ReviewerConfig::noop_files_byte_cap` (64 KiB default) + per-file derived cap (floor 2048) in `read_file_contents` |

| `ChangeRequested` issue-summary exceeds verification practical length | Low | Low | `render_issue_summary` caps at `VERIFICATION_CAP`; full issues persist on the Verdict return value |
