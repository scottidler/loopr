## Open follow-ups

Both were deliberately left out of the recovery-chain scope (unrequested scope). Neither blocks anything shipped.

### 1. Two flaky log-capture tests (small edit, involved verification)

- Tests: `llm::metered::pricing_tests::cost_sink_append_unknown_model_warns_once_and_still_ledgers_usage` and `store::bundles::tests::update_non_stale_failure_logs_error`.
- Symptom: intermittently assert 1 log line, get 0. PASS on isolated rerun every time.
- Mechanism (leading hypothesis, wrong-thread theory already ruled out in Phase 2 notes): `tracing`'s process-global per-callsite interest cache. A non-capturing test hits the callsite (`metered.rs:86`, `works.rs:233`, `bundles.rs:201`) first with a no-op subscriber, caches "not interested", and the capturing test then sees nothing. The poisoning comes from the many other `update()` tests, not from the capturing test, so a shared mutex among only the capturing tests does NOT fix it (that is why the `worktree` fix in `13ca64c1` worked there but will not transfer directly).
- Fix candidate: call `tracing_core::callsite::rebuild_interest_cache()` after installing the capturing subscriber, forcing re-evaluation. A few lines each in `crates/llm/src/metered.rs` and `crates/store/src/{works,bundles}/tests.rs`.
- The hard part is proving it. It is an intermittent race, so there is no clean break-to-proven: confidence comes from many repeated full-suite runs, not one red -> green flip. Confirm the mechanism (add a deliberate poisoning test that reproduces the 0-line case, then show `rebuild_interest_cache` fixes it) before committing to the fix.
- Operational note: if root `otto ci` goes red on either test, it is almost certainly this. Rerun before investigating.
