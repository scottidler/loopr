# Design Document: IPC Protocol

**Author:** Scott A. Idler
**Date:** 2026-04-19
**Status:** Implemented
**Review Passes Completed:** 5/5

## Summary

Stand up the `ipc` crate: wire-shape-faithful `DaemonRequest` / `DaemonResponse` / `DaemonEvent` structs per `docs/vision.md` §ipc, a closed typed `RpcError` enum that serializes through the `{code, message}` wire form (vision line 407), a typed `Method` enum for internal dispatch (v4 pattern from `src/ipc/method.rs`), NDJSON framing with a 1 MiB max-line cap, and round-trip tests per variant plus byte-stability and oversize tests. Stage 3 of `docs/roadmap.md`. Wire shape is inherited verbatim from v3/v4; the Rust-side typing is where v5 tightens.

## Problem Statement

### Background

Stage 2 (`docs/design/2026-04-19-telemetry-stage-2.md`) gave v5 a working subscriber and log-query layer. Stage 4 will fork the daemon and bind a Unix socket; the moment that socket accepts a connection, it needs a typed protocol to speak. `crates/ipc/` currently ships as an empty scaffold — one-line `Cargo.toml`, empty `lib.rs`, no types, no framing helpers, no tests.

`docs/vision.md` §ipc pins the wire shape and the error-code table:

- Line 183: `DaemonRequest { id: u64, method: String, params: Value }`, `DaemonResponse { id: u64, result: Option<Value>, error: Option<RpcError> }`, `DaemonEvent { event: String, data: Value }` — JSON-RPC-style envelope, inherited verbatim from v3/v4.
- Line 185: `RpcError { code: i32, message: String }` wire shape with named constants `CODE_METHOD_NOT_FOUND = -32601`, `CODE_INVALID_PARAMS = -32602`, `CODE_INTERNAL = -32603` (JSON-RPC standard) plus loopr-specific `-32000..-32005` (transition-rejected, not-found, stale-bundle, validation-required, pool-exhausted, precondition-failed).
- Line 186: NDJSON via `LinesCodec`, 1 MiB max line.
- Line 407: "Closed Rust enum on the daemon/client sides, serialized to JSON-RPC-compatible `{code, message}` on the wire."

Stage 3 is where those commitments become real Rust types with round-trip tests. The design must not re-argue them; it pins the translation between the wire shape and the Rust shape, the initial method vocabulary, and the rollout path as `domain` records come online in later stages.

### Problem

- No protocol types exist. Stage 4 cannot fork the daemon and speak to a client without them.
- Vision commits to a loose envelope on the wire (`method: String, params: Value`) but also to typed error semantics (closed Rust enum). Stage 3 must ship the bridge: structs on the wire, enum typing in Rust, round-trip tests that assert the translation is lossless at the code+message level.
- Vision does not name a concrete method set. Stage 3 ships an intentionally small starter vocabulary (just `system.handshake` + `system.status`) because `domain` is still empty (no Plan, Spec, Phase, Work, Bundle, Tick records to CRUD). Method taxonomy grows stage by stage as records land.
- The framing test for the exit criterion needs `ipc` to expose an `encode_line(&Msg) -> Vec<u8>` / `decode_line(&[u8]) -> Result<Msg>` surface — pure bytes in, pure bytes out, no async I/O. That surface does not yet exist.
- The 1 MiB max-line cap from vision line 186 needs to be a shared const (consumed by both `ipc`'s decoder and `loopr`'s future `LinesCodec` configuration at Stage 4) — not duplicated.

### Goals

- `crates/ipc/src/` defines the wire-faithful envelope structs: `DaemonRequest { id: u64, method: String, params: Value }`, `DaemonResponse { id: u64, result: Option<Value>, error: Option<RpcError> }`, `DaemonEvent { event: String, data: Value }`, and an `IpcMessage` client-side discriminator that discriminates between `Response` and `Event` by field presence (v4 pattern).
- `RpcError` is a closed Rust enum, serializes to / deserializes from `{code: i32, message: String}` on the wire via `#[serde(into, try_from)]`. Variants cover twelve codes: the five JSON-RPC 2.0 standard codes (`-32700` ParseError, `-32600` InvalidRequest, `-32601` MethodNotFound, `-32602` InvalidParams, `-32603` InternalError) plus the seven loopr-specific codes (`-32000` TransitionRejected, `-32001` NotFound, `-32002` StaleBundle, `-32003` ValidationRequired, `-32004` PoolExhausted, `-32005` PreconditionFailed, `-32006` ProtocolVersionMismatch). Unknown codes on deserialize map to `RpcError::Unknown { code, message }` (forward-compat). Vision line 185 gets a one-line amendment to name the additions (`-32700`, `-32600`, `-32006`).
- `Method` is a typed closed Rust enum separate from the wire. `TryFrom<&DaemonRequest> for Method` parses `req.method` (string-matched against a `strum`-serialized enum) plus `req.params` (typed `serde_json::from_value` into the variant's struct). Adding a new method without a handler is a compile error because `Method` is exhaustive.
- Initial method vocabulary for Stage 3: `system.handshake` and `system.status`. Both are real methods that the Stage 2 CLI's `daemon status` subcommand already wants; the handshake lands the `PROTOCOL_VERSION` advertisement on the wire. Method names follow v4's `scope.verb` dotted style (`plan.create`, `work.get`, etc.) — Stage 3 just ships two methods but in the correct shape for growth.
- `MAX_LINE_BYTES: usize = 1 << 20` is a pub const.
- `PROTOCOL_VERSION: u32 = 1` is a pub const. The `system.handshake` method surfaces it via a typed `HandshakeParams { protocol_version: u32 }` on Request and `HandshakeResult { protocol_version: u32, daemon_version: String }` on Response. Negotiation logic lives in `loopr` (Stage 4); this doc defines the shape.
- `encode_line(&IpcMessage | &DaemonRequest) -> Vec<u8>` appends `\n` and returns the full line bytes. `decode_line(&[u8]) -> Result<IpcMessage, ParseError>` validates size cap, strips trailing `\n`, and discriminates by field presence (`"event"` key → Event, else Response). Encoding is deterministic (same input → same bytes). Oversize input returns `ParseError::LineTooLong { size }`; parse failure returns `ParseError::Decode(serde_err)`.
- Round-trip test per `IpcMessage` variant: Response(ok), Response(err), Event.
- Round-trip test per `Method` variant: Handshake, Status.
- Round-trip test per `RpcError` variant: all nine named codes.
- Byte-stability test: two encodes of the same message produce identical bytes.
- Oversize test: `decode_line(>1 MiB)` returns `LineTooLong { size }`.
- Malformed-input test: `decode_line(b"not json\n")` returns `Decode(serde_err)`.
- Forward-compat test: `RpcError` with `code: -32042` round-trips as `RpcError::Unknown { code, message }`.
- Misrouted-request test: a line carrying `"method"` on the client-inbound stream returns `ParseError::MisroutedRequest`.

### Non-Goals

- **Async I/O, socket acceptance, connection lifecycle.** Per `crates/ipc/CLAUDE.md`: no `tokio`, no `reqwest`. Stage 4's `crates/loopr/docs/design/ipc-transport.md` wires these to the typed protocol.
- **Streaming / chunked responses.** v5's first gate is fire-and-forget RPC. Long-running operations surface state via the independent `Event` stream, not chunked `Response`s.
- **Authentication / authorization / capability tokens.** The socket is bound in the target's `.loopr/` dir with owner-only permissions (Stage 4's concern). No network exposure.
- **Protocol evolution beyond v1.** `PROTOCOL_VERSION` bumps get their own design docs. Stage 3 ships v1 and the mechanism to advertise it.
- **Binary / compact framing.** Vision pins NDJSON. Not revisiting.
- **Full method vocabulary.** v4 had ~80 methods covering `plan.*`, `spec.*`, `phase.*`, `work.*`, `bundle.*`, `tick.*`, `learning.*`, `lock.*`, `worktree.*`, `integrator.*`, `validator.*`, `tool.*`, `doc.*`, `chat.*`, `agent.*`, `director.*`, `decomposer.*`. v5's `domain` is empty; we can't ship methods that CRUD records that don't exist. Stage 3 ships two methods — handshake + status — and the compile-time exhaustive dispatch surface that makes growing the set safe. Methods land as their records land.
- **Record-typed payloads for records `domain` hasn't defined yet.** Stage 3 params structs use `String` placeholders for any id-like field; Stage 5+ migrates them to `domain::PlanId` / `domain::WorkId` / etc. as those records land. The migration is called out in §Rollout.
- **Outer message discriminator (`kind` field on every line).** Vision doesn't ask for one; v4 doesn't have one; adding it would break wire compat with anything that speaks v4's envelope. Field-presence discrimination stays.

### Acceptance Criteria

Each item is an assertable check. The design is Done when every assertion below is true.

- `cargo test -p ipc` passes a round-trip test per `IpcMessage` variant — `Request`, `Response(ok)`, `Response(err)`, `Event`
- `cargo test -p ipc` passes a round-trip test per `Method` variant — `Handshake`, `Status`
- `cargo test -p ipc` passes a round-trip test per `RpcError` variant — all twelve named codes
- `cargo test -p ipc` passes a forward-compat test: `RpcError` round-trips an unknown code as `RpcError::Unknown { code, message }` rather than panicking
- `cargo test -p ipc` passes a byte-stability test: `encode_line(&msg)` produces the same bytes on repeated calls
- `cargo test -p ipc` passes an oversize test: `decode_line(&input)` with `input.len() > MAX_LINE_BYTES` returns `ParseError::LineTooLong { size }` with the observed size
- `cargo test -p ipc` passes a malformed-input test: `decode_line(b"not json\n")` returns `ParseError::Decode`, not a panic
- `cargo test -p ipc` passes a discrimination test: a line with `"event"` key parses as `IpcMessage::Event`; a line with `"id"` + `"result"` parses as `IpcMessage::Response(ok)`; a line with `"id"` + `"error"` parses as `IpcMessage::Response(err)`; a line with `"method"` (misrouted request on client stream) returns `ParseError::MisroutedRequest`
- `cargo test -p ipc` passes a method-dispatch test: `Method::try_from(&DaemonRequest { method: "system.status", params: Value::Null, .. })` returns `Ok(Method::Status)`; `"bogus.method"` returns a parse error the dispatch layer can map to `-32601`
- `MAX_LINE_BYTES` and `PROTOCOL_VERSION` are public consts at the crate root with doc comments pointing at this design doc
- The crate does NOT depend on `tokio`, `tokio_util`, `reqwest`, `ureq`, `hyper`, or any I/O runtime — `cargo tree -p ipc` shows only `serde`, `serde_json`, `thiserror`, `strum`, `domain` (currently empty; added for the path dep declaration that's already present)
- `otto ci` inside `crates/ipc` is green; `otto ci` at the workspace root is green

## Proposed Solution

### Overview

**Mental model:** `ipc` has two parallel type systems connected by `TryFrom` bridges.

- **Wire types** (`envelope.rs`): `DaemonRequest`, `DaemonResponse`, `DaemonEvent`. Plain structs with `serde_json::Value` payloads. Match `docs/vision.md` line 183 verbatim. These are what serializes to / deserializes from NDJSON lines.
- **Rust types** (`method.rs`, `error.rs`): `Method` enum with typed params structs per variant; `RpcError` closed enum. These are what handlers match on — compile-time exhaustive, typo-proof, impossible to construct an invalid variant.
- **Bridges**: `impl TryFrom<&DaemonRequest> for Method` (dispatch), `impl From<RpcError> for RpcErrorWire` + reverse (error serialization).

The wire stays v4-compatible because `ipc` never changes its shape. The Rust surface gets all the type-safety benefits of closed enums because bridges convert at the crate boundary, not in user code.

**Daemon read-path flow:**

```
bytes       decode_request_line     Method::try_from      exhaustive match
  │                │                      │                      │
  ▼                ▼                      ▼                      ▼
b"{...}\n"  ──▶  DaemonRequest   ──▶  Method::Status   ──▶  handle_status()
                  {id, method,          (or RpcError             │
                   params}               on bad method            ▼
                                         or bad params)       DaemonResponse::ok(id, ..)
                                                                  │
                                                                  ▼
                                                             encode_line(&resp)
                                                                  │
                                                                  ▼
                                                             bytes → socket
```

**Layout:** `crates/ipc/src/` gets five single-word module files under the Rust 2018+ style (per `rules/rust.md`): `lib.rs` (pub surface + consts), `envelope.rs` (wire structs), `error.rs` (`RpcError`), `method.rs` (typed `Method` + params/result structs), `frame.rs` (encode/decode + `ParseError`).

The rule-of-thumb separation: **`ipc` owns both sides of the wire↔Rust translation and the round-trip proofs. `loopr` owns the `UnixStream`, the `LinesCodec`, and the handler dispatch table that exhaustively matches on `Method`.**

### Architecture

```
crates/ipc/
├── src/
│   ├── lib.rs       re-exports + MAX_LINE_BYTES + PROTOCOL_VERSION consts
│   ├── envelope.rs  DaemonRequest / DaemonResponse / DaemonEvent / IpcMessage
│   ├── error.rs     RpcError closed enum with custom serde through {code, message}
│   ├── method.rs    Method enum + params/result structs + TryFrom<&DaemonRequest>
│   ├── frame.rs     encode_line, decode_line, ParseError
│   └── tests.rs     submodule tests per rules/rust.md
└── .otto.yml        already exists (scaffold-generated)
```

### Data Model

```rust
// crates/ipc/src/envelope.rs
//
// Wire-faithful structs. These match docs/vision.md §ipc line 183 exactly.
// No #[serde(deny_unknown_fields)] on these types: v4 doesn't use it, and
// JSON-RPC 2.0 doesn't reserve field presence. The typed params/result
// structs INSIDE method.rs can use deny_unknown_fields for typo detection.

use serde::{Deserialize, Serialize};

use crate::error::RpcError;

/// Client -> daemon request. Matches v4's `DaemonRequest` verbatim. The
/// `method` string is parsed into a typed `Method` by `method::Method::
/// try_from(&req)` at the dispatch boundary.
#[derive(Debug, Clone, Serialize, Deserialize, PartialEq)]
pub struct DaemonRequest {
    pub id: u64,
    pub method: String,
    #[serde(default)]
    pub params: serde_json::Value,
}

/// Daemon -> client response. `result` or `error` is set; never both. An
/// invariant check is enforced by `DaemonResponse::ok()` / `::err()`
/// constructors; the wire does not prevent both-set but the sender must
/// never produce it.
#[derive(Debug, Clone, Serialize, Deserialize, PartialEq)]
pub struct DaemonResponse {
    pub id: u64,
    #[serde(skip_serializing_if = "Option::is_none")]
    pub result: Option<serde_json::Value>,
    #[serde(skip_serializing_if = "Option::is_none")]
    pub error: Option<RpcError>,
}

impl DaemonResponse {
    pub fn ok(id: u64, result: serde_json::Value) -> Self {
        Self { id, result: Some(result), error: None }
    }
    pub fn err(id: u64, error: RpcError) -> Self {
        Self { id, result: None, error: Some(error) }
    }
    pub fn is_error(&self) -> bool {
        self.error.is_some()
    }
}

/// Daemon -> client unsolicited push event. Events are NOT correlated to any
/// request; they carry their own scope keys in `data` so clients can filter.
#[derive(Debug, Clone, Serialize, Deserialize, PartialEq)]
pub struct DaemonEvent {
    pub event: String,
    pub data: serde_json::Value,
}

/// Envelope for messages flowing IN to a client. Discriminated by field
/// presence (v4 pattern — `frame::decode_line` does this): a line with an
/// `"event"` key is an `Event`; otherwise it's a `Response`.
///
/// The daemon's inbound stream is exclusively `DaemonRequest` and does not
/// need this enum.
#[derive(Debug, Clone, PartialEq)]
pub enum IpcMessage {
    Response(DaemonResponse),
    Event(DaemonEvent),
}
```

```rust
// crates/ipc/src/error.rs
//
// Typed closed Rust enum per docs/vision.md line 407, serialized as
// {code: i32, message: String} per line 185. Eleven named codes + one
// `Unknown` forward-compat variant.
//
// The named set extends vision line 185 in two ways, both mandated by
// architect design review:
//   - Adds standard JSON-RPC 2.0 codes -32700 ParseError and -32600
//     InvalidRequest (vision listed only -32601/-32602/-32603 as the
//     "JSON-RPC standard" set; this was an omission, not a deliberate
//     exclusion). Stage 4's transport layer uses these at the parse and
//     request-shape boundaries.
//   - Adds loopr-specific -32006 ProtocolVersionMismatch (the open question
//     from a prior draft; pinned here rather than punted to Stage 4 so the
//     protocol-spec crate owns the code assignment it's supposed to own).
// Vision line 185 gets a matching one-line amendment when this design doc
// ships.
//
// `Unknown` is the forward-compat escape hatch: a client compiled against
// protocol v1 receiving an error code the v2 daemon introduced must not
// panic. `Unknown` carries the raw code so a future `if let Some(v2_err) =
// self.downcast_v2()` can recover the structured variant once v2 ships.

use serde::{Deserialize, Serialize};
use thiserror::Error;

// `#[derive(Serialize, Deserialize)]` is REQUIRED for `#[serde(into, try_from)]`
// to activate — the attributes modify how the derive generates the impls, they
// do not generate impls by themselves.
#[derive(Error, Debug, Clone, PartialEq, Eq, Serialize, Deserialize)]
#[serde(into = "RpcErrorWire", try_from = "RpcErrorWire")]
pub enum RpcError {
    // JSON-RPC 2.0 standard codes
    #[error("parse error: {0}")]
    ParseError(String),          // -32700
    #[error("invalid request: {0}")]
    InvalidRequest(String),      // -32600
    #[error("method not found: {0}")]
    MethodNotFound(String),      // -32601
    #[error("invalid params: {0}")]
    InvalidParams(String),       // -32602
    #[error("internal error: {0}")]
    Internal(String),            // -32603

    // loopr-specific codes (vision line 185, extended with -32006)
    #[error("transition rejected: {0}")]
    TransitionRejected(String),  // -32000
    #[error("not found: {0}")]
    NotFound(String),            // -32001
    #[error("stale bundle: {0}")]
    StaleBundle(String),         // -32002
    #[error("validation required: {0}")]
    ValidationRequired(String),  // -32003
    #[error("pool exhausted: {0}")]
    PoolExhausted(String),       // -32004
    #[error("precondition failed: {0}")]
    PreconditionFailed(String),  // -32005
    #[error("protocol version mismatch: {0}")]
    ProtocolVersionMismatch(String),  // -32006

    // Forward-compat: codes the current enum doesn't recognize
    #[error("rpc error {code}: {message}")]
    Unknown { code: i32, message: String },
}

impl RpcError {
    // JSON-RPC 2.0 standard
    pub const CODE_PARSE_ERROR: i32 = -32700;
    pub const CODE_INVALID_REQUEST: i32 = -32600;
    pub const CODE_METHOD_NOT_FOUND: i32 = -32601;
    pub const CODE_INVALID_PARAMS: i32 = -32602;
    pub const CODE_INTERNAL: i32 = -32603;

    // loopr-specific (vision line 185 + -32006)
    pub const CODE_TRANSITION_REJECTED: i32 = -32000;
    pub const CODE_NOT_FOUND: i32 = -32001;
    pub const CODE_STALE_BUNDLE: i32 = -32002;
    pub const CODE_VALIDATION_REQUIRED: i32 = -32003;
    pub const CODE_POOL_EXHAUSTED: i32 = -32004;
    pub const CODE_PRECONDITION_FAILED: i32 = -32005;
    pub const CODE_PROTOCOL_VERSION_MISMATCH: i32 = -32006;

    pub fn code(&self) -> i32 {
        match self {
            RpcError::ParseError(_) => Self::CODE_PARSE_ERROR,
            RpcError::InvalidRequest(_) => Self::CODE_INVALID_REQUEST,
            RpcError::MethodNotFound(_) => Self::CODE_METHOD_NOT_FOUND,
            RpcError::InvalidParams(_) => Self::CODE_INVALID_PARAMS,
            RpcError::Internal(_) => Self::CODE_INTERNAL,
            RpcError::TransitionRejected(_) => Self::CODE_TRANSITION_REJECTED,
            RpcError::NotFound(_) => Self::CODE_NOT_FOUND,
            RpcError::StaleBundle(_) => Self::CODE_STALE_BUNDLE,
            RpcError::ValidationRequired(_) => Self::CODE_VALIDATION_REQUIRED,
            RpcError::PoolExhausted(_) => Self::CODE_POOL_EXHAUSTED,
            RpcError::PreconditionFailed(_) => Self::CODE_PRECONDITION_FAILED,
            RpcError::ProtocolVersionMismatch(_) => Self::CODE_PROTOCOL_VERSION_MISMATCH,
            RpcError::Unknown { code, .. } => *code,
        }
    }

    pub fn message(&self) -> String {
        match self {
            RpcError::ParseError(m)
            | RpcError::InvalidRequest(m)
            | RpcError::MethodNotFound(m)
            | RpcError::InvalidParams(m)
            | RpcError::Internal(m)
            | RpcError::TransitionRejected(m)
            | RpcError::NotFound(m)
            | RpcError::StaleBundle(m)
            | RpcError::ValidationRequired(m)
            | RpcError::PoolExhausted(m)
            | RpcError::PreconditionFailed(m)
            | RpcError::ProtocolVersionMismatch(m) => m.clone(),
            RpcError::Unknown { message, .. } => message.clone(),
        }
    }

    /// Constructor for `ProtocolVersionMismatch` that formats the two
    /// version numbers consistently. Stage 4's handshake handler calls this
    /// rather than constructing the variant directly, so all mismatch
    /// messages have the same shape: `"client=N daemon=M"`.
    pub fn protocol_version_mismatch(client: u32, daemon: u32) -> Self {
        RpcError::ProtocolVersionMismatch(format!("client={client} daemon={daemon}"))
    }
}

/// Wire shape — JSON-RPC-compatible `{code, message}`. `RpcError` serializes
/// INTO this and deserializes FROM this (serde `into`/`try_from` attributes).
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct RpcErrorWire {
    pub code: i32,
    pub message: String,
}

impl From<RpcError> for RpcErrorWire {
    fn from(err: RpcError) -> Self {
        RpcErrorWire { code: err.code(), message: err.message() }
    }
}

impl TryFrom<RpcErrorWire> for RpcError {
    type Error = std::convert::Infallible;  // never fails; unknown codes go to ::Unknown
    fn try_from(w: RpcErrorWire) -> Result<Self, Self::Error> {
        Ok(match w.code {
            RpcError::CODE_PARSE_ERROR => RpcError::ParseError(w.message),
            RpcError::CODE_INVALID_REQUEST => RpcError::InvalidRequest(w.message),
            RpcError::CODE_METHOD_NOT_FOUND => RpcError::MethodNotFound(w.message),
            RpcError::CODE_INVALID_PARAMS => RpcError::InvalidParams(w.message),
            RpcError::CODE_INTERNAL => RpcError::Internal(w.message),
            RpcError::CODE_TRANSITION_REJECTED => RpcError::TransitionRejected(w.message),
            RpcError::CODE_NOT_FOUND => RpcError::NotFound(w.message),
            RpcError::CODE_STALE_BUNDLE => RpcError::StaleBundle(w.message),
            RpcError::CODE_VALIDATION_REQUIRED => RpcError::ValidationRequired(w.message),
            RpcError::CODE_POOL_EXHAUSTED => RpcError::PoolExhausted(w.message),
            RpcError::CODE_PRECONDITION_FAILED => RpcError::PreconditionFailed(w.message),
            RpcError::CODE_PROTOCOL_VERSION_MISMATCH => RpcError::ProtocolVersionMismatch(w.message),
            other => RpcError::Unknown { code: other, message: w.message },
        })
    }
}
```

```rust
// crates/ipc/src/method.rs
//
// Typed internal dispatch vocabulary. The wire still carries `method:
// String`; this enum is what the daemon's dispatch layer matches on.
// Matches v4's `src/ipc/method.rs` pattern (strum-serialized enum) but is
// scoped to Stage 3's two starter methods; more variants land as their
// domain records come online in Stage 5+.

use serde::{Deserialize, Serialize};
use strum::{Display, EnumString, IntoStaticStr};

use crate::envelope::DaemonRequest;
use crate::error::RpcError;

/// Every IPC method the daemon accepts in Stage 3. Add a variant here AND a
/// matching params struct AND a handler arm; compile errors enforce
/// coverage.
///
/// **Case-sensitive on the wire.** `strum`'s `EnumString` derive is
/// case-sensitive by default, matching JSON-RPC 2.0 method-naming convention
/// and v4's wire behavior. `system.Handshake` is NOT valid; only
/// `system.handshake` is.
#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash, Display, EnumString, IntoStaticStr)]
pub enum MethodName {
    #[strum(serialize = "system.handshake")]
    SystemHandshake,
    #[strum(serialize = "system.status")]
    SystemStatus,
}

/// Typed parameters per method. Each variant's struct uses
/// `deny_unknown_fields` so a `{"params": {"protocol_version": 1, "bonus":
/// "evil"}}` request fails at the dispatch boundary with InvalidParams.
#[derive(Debug, Clone, PartialEq, Eq)]
pub enum Method {
    Handshake(HandshakeParams),
    Status,
}

#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize)]
#[serde(deny_unknown_fields)]
pub struct HandshakeParams {
    pub protocol_version: u32,
}

/// Parse `DaemonRequest` into a typed `Method`. Errors map cleanly to wire
/// error codes:
///   - unknown method string -> RpcError::MethodNotFound
///   - params shape mismatch -> RpcError::InvalidParams
impl TryFrom<&DaemonRequest> for Method {
    type Error = RpcError;
    fn try_from(req: &DaemonRequest) -> Result<Self, Self::Error> {
        use std::str::FromStr;
        let name = MethodName::from_str(&req.method)
            .map_err(|_| RpcError::MethodNotFound(req.method.clone()))?;
        match name {
            MethodName::SystemHandshake => {
                let params: HandshakeParams = serde_json::from_value(req.params.clone())
                    .map_err(|e| RpcError::InvalidParams(e.to_string()))?;
                Ok(Method::Handshake(params))
            }
            MethodName::SystemStatus => {
                if !req.params.is_null() && !matches!(&req.params, serde_json::Value::Object(m) if m.is_empty()) {
                    return Err(RpcError::InvalidParams(
                        "system.status takes no params".into(),
                    ));
                }
                Ok(Method::Status)
            }
        }
    }
}

/// Typed results for each method. Serialized into the `result` field of
/// `DaemonResponse` via serde_json::to_value.
#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize)]
#[serde(deny_unknown_fields)]
pub struct HandshakeResult {
    pub protocol_version: u32,
```

```rust
// crates/ipc/src/frame.rs

use thiserror::Error;

use crate::envelope::{DaemonEvent, DaemonRequest, DaemonResponse, IpcMessage};

/// Encode any serializable message as a single NDJSON line (UTF-8, trailing
/// `\n`). Used by both directions: client -> daemon (encodes `DaemonRequest`)
/// and daemon -> client (encodes `DaemonResponse` or `DaemonEvent`).
pub fn encode_line<T: serde::Serialize>(msg: &T) -> Vec<u8> {
    let mut buf = serde_json::to_vec(msg).expect("ipc messages must serialize");
    buf.push(b'\n');
    buf
}

/// Decode a single NDJSON line into an `IpcMessage` (the client-inbound
/// variant). Strips an optional trailing `\n`, rejects oversize lines,
/// discriminates by field presence:
///   - `"event"` key  -> `Event`
///   - `"method"` key -> `MisroutedRequest` error (a request should not
///     arrive on the client-inbound stream; catching it here avoids silent
///     drop-through to `DaemonResponse::deserialize` which would succeed
///     with empty result/error and lose the request payload)
///   - otherwise       -> `Response`
pub fn decode_line(line: &[u8]) -> Result<IpcMessage, ParseError> {
    if line.len() > crate::MAX_LINE_BYTES {
        return Err(ParseError::LineTooLong { size: line.len() });
    }
    let trimmed = line.strip_suffix(b"\n").unwrap_or(line);
    let v: serde_json::Value = serde_json::from_slice(trimmed)?;
    if v.get("event").is_some() {
        let event: DaemonEvent = serde_json::from_value(v)?;
        Ok(IpcMessage::Event(event))
    } else if v.get("method").is_some() {
        Err(ParseError::MisroutedRequest)
    } else {
        let resp: DaemonResponse = serde_json::from_value(v)?;
        Ok(IpcMessage::Response(resp))
    }
}

/// Decode a single NDJSON line as a `DaemonRequest` (daemon-inbound).
/// Separate entry point because the daemon's inbound stream is homogeneous
/// — no discrimination needed; the input must be a request or it's malformed.
pub fn decode_request_line(line: &[u8]) -> Result<DaemonRequest, ParseError> {
    if line.len() > crate::MAX_LINE_BYTES {
        return Err(ParseError::LineTooLong { size: line.len() });
    }
    let trimmed = line.strip_suffix(b"\n").unwrap_or(line);
    Ok(serde_json::from_slice(trimmed)?)
}

#[derive(Error, Debug)]
pub enum ParseError {
    #[error("line exceeds MAX_LINE_BYTES: size={size}")]
    LineTooLong { size: usize },
    #[error("decode failed: {0}")]
    Decode(#[from] serde_json::Error),
    #[error("request received on client-inbound stream (wrong direction)")]
    MisroutedRequest,
}
```

```rust
// crates/ipc/src/lib.rs

//! Typed wire protocol between the loopr daemon and its clients.
//!
//! # Wire shape
//!
//! Per `docs/vision.md` §ipc: JSON-RPC-style envelope inherited verbatim
//! from v3/v4. Request is `{id, method, params}`; response is `{id,
//! result?, error?}`; event is `{event, data}`. See [`DaemonRequest`],
//! [`DaemonResponse`], [`DaemonEvent`]. Framing: NDJSON, one message per
//! line, max [`MAX_LINE_BYTES`] per line.
//!
//! # Rust-side typing
//!
//! The wire is deliberately loose (Value payloads); the Rust surface is
//! typed. [`Method`] is the exhaustive internal dispatch enum; [`RpcError`]
//! is the closed error enum that serializes through the `{code, message}`
//! wire shape. Handlers in `loopr` match on these, and compile errors
//! catch unhandled variants.
//!
//! # I/O discipline
//!
//! This crate is intentionally I/O-free: no tokio, no sockets. Async
//! transport lives in `loopr` per `crates/ipc/CLAUDE.md`.

mod envelope;
mod error;
mod frame;
mod method;

/// Maximum bytes per NDJSON line, enforced by [`decode_line`] /
/// [`decode_request_line`]. Matches v3/v4 and the value wired to
/// `tokio_util::codec::LinesCodec::new_with_max_length` in `loopr`'s
/// transport layer.
pub const MAX_LINE_BYTES: usize = 1 << 20;  // 1 MiB

/// Wire protocol version. Advertised via the `system.handshake` method;
/// negotiated by `loopr` at Stage 4.
pub const PROTOCOL_VERSION: u32 = 1;

pub use envelope::{DaemonEvent, DaemonRequest, DaemonResponse, IpcMessage};
pub use error::{RpcError, RpcErrorWire};
pub use frame::{decode_line, decode_request_line, encode_line, ParseError};
pub use method::{HandshakeParams, HandshakeResult, Method, MethodName, StatusResult};

#[cfg(test)]
mod tests;
```

### API Design

From a caller's perspective (Stage 4's `loopr::transport::`):

```rust
// Client side (short-lived CLI invocation): handshake + status request.
let handshake = ipc::DaemonRequest {
    id: 1,
    method: ipc::MethodName::SystemHandshake.to_string(),
    params: serde_json::to_value(ipc::HandshakeParams {
        protocol_version: ipc::PROTOCOL_VERSION,
    })?,
};
stream.write_all(&ipc::encode_line(&handshake)).await?;
let line = read_until_newline(&mut stream).await?;
match ipc::decode_line(&line)? {
    ipc::IpcMessage::Response(resp) if resp.id == 1 => {
        let result: ipc::HandshakeResult = serde_json::from_value(resp.result.unwrap())?;
        // proceed on version match
    }
    _ => bail!("expected handshake response"),
}

// Daemon side: dispatch a request.
let req = ipc::decode_request_line(&line)?;
let method = ipc::Method::try_from(&req)
    .map_err(|rpc_err| ipc::DaemonResponse::err(req.id, rpc_err))?;
match method {
    ipc::Method::Handshake(params) => handle_handshake(req.id, params),
    ipc::Method::Status => handle_status(req.id),
}
```

### Protocol Contracts (enforced by Stage 4's transport layer)

Stage 3 owns the types and the wire shape. The following operational contracts are part of the protocol specification but are enforced in Stage 4's `loopr::transport` module — `ipc` is I/O-free and cannot enforce anything at runtime itself. They are stated here because this is the protocol-spec crate; Stage 4 is just the implementor.

**Handshake ordering.** The daemon MUST require `system.handshake` as the first method on every new connection. Any other method received before a successful handshake MUST return `RpcError::InvalidRequest("handshake required before: {method}")` and MUST NOT advance the connection to "handshaked" state. This mirrors v4's behavior (`src/tui/run/ipc.rs` lines 215, 401 enforce the same ordering check). Stage 4's `daemon-lifecycle.md` design doc owns the connection-state machine; this doc owns the contract.

**Unparseable input on the daemon's inbound stream.** `decode_request_line` failure (malformed JSON, oversize line, or a non-request payload) means the daemon cannot correlate a response to any `id`. The transport layer MUST NOT synthesize a fake `id` (0 or any other value) to satisfy `DaemonResponse::id: u64` — a synthesized id can collide with a legitimate client request id and corrupt correlation state. Instead the transport layer logs the failure via the telemetry subscriber (Stage 2) and **closes the connection without sending a response**. The client sees the socket close and treats it as a protocol-level failure. Stage 4's `ipc-transport.md` design doc codifies this in the accept loop.

**Unparseable input on the client's inbound stream.** Symmetric to the above: if `decode_line` on the client side fails, the client logs and drops the connection. No response is synthesized because the client has no way to know which outstanding request (if any) the malformed bytes were intended for.

**Forward-compatibility mechanism.** Extensions to the protocol happen via `PROTOCOL_VERSION` bumps, not via silent additive fields. A v2 daemon serving a v1 client sees the v1 client's `system.handshake` advertise `protocol_version: 1`, recognizes the mismatch, and returns `RpcError::protocol_version_mismatch(client=1, daemon=2)`. The v1 client treats that as a hard refusal and exits. Because `deny_unknown_fields` is ON on the typed params structs (`HandshakeParams`, etc.), a v2 client sending `protocol_version: 2, client_capabilities: [...]` to a v1 daemon fails cleanly with `InvalidParams` rather than silently dropping the new field and proceeding half-blind. This is the intended behavior: `deny_unknown_fields` is correct *within a negotiated protocol version*; cross-version extension is the handshake's job.

## Alternatives Considered

### Alternative 1: Tagged Request/Response/Event enums on the wire (original Design B draft)

- **Description:** `#[serde(tag = "method")]` on `Request`, `#[serde(tag = "event")]` on `Event`, outer `#[serde(tag = "kind")]` on `IpcMessage`. Typed end-to-end.
- **Pros:** Every field typed on the wire; no `Value` escape hatches; impossible to construct a request with a typo'd method name in Rust.
- **Cons:** Wire shape diverges from `docs/vision.md` line 183 (which commits to `method: String, params: Value`); v4 clients can't interop; JSON-RPC 2.0 parsers can't interop; adds an outer `kind` discriminator that appears nowhere in vision.
- **Why not chosen:** Vision explicitly inherits v4's wire shape "verbatim" (line 183, reinforced by line 634). The typed-end-to-end benefits can be had in Rust via the `Method` enum without breaking wire compat. This alternative was the original draft's silent scope expansion; rewritten to match spec.

### Alternative 2: Plain `RpcError` struct (v4 literal)

- **Description:** `RpcError { code: i32, message: String }` as a struct with factory methods (`::method_not_found(m)`, `::invalid_params(d)`, etc.). No Rust-side variant discrimination.
- **Pros:** Even simpler serde; no `#[serde(into, try_from)]`; no `Unknown` variant needed.
- **Cons:** Dispatch handlers can't `match` on error kind — they must `if err.code == RpcError::CODE_NOT_FOUND` everywhere. Lost type safety on the daemon side when mapping handler failures to wire errors.
- **Why not chosen:** Vision line 407 explicitly says *"Closed Rust enum on the daemon/client sides"*, which overrides v4's struct-with-factories for v5. The `{code, message}` wire shape is preserved; only the Rust type tightens. Handlers get exhaustive `match` on `RpcError`.

### Alternative 3: No `Method` enum; dispatch by string match

- **Description:** Daemon handler dispatch is `match req.method.as_str() { "system.handshake" => ..., "system.status" => ..., _ => err }`.
- **Pros:** One fewer enum to maintain.
- **Cons:** No compile-time exhaustiveness; a new method string added without a handler routes to the default error arm silently. This is exactly what v4's `method.rs` was introduced to solve.
- **Why not chosen:** v4 added `DaemonMethod` for this reason; v5 inherits that pattern. The enum is cheap; the compile-time guarantee isn't.

### Alternative 4: No handshake; version check on first request

- **Description:** Drop `system.handshake`; the first request's shape implicitly tells the daemon the protocol version.
- **Pros:** One fewer round-trip on connection setup.
- **Cons:** Version mismatch surfaces AFTER the daemon starts parsing a request it may not understand; the error path is less clean. `system.handshake` is already present in v4's method list, so we're not inventing a new pattern.
- **Why not chosen:** The round-trip cost is invisible at v5 scale. An explicit handshake makes Stage 4's version-negotiation design doc write itself.

### Alternative 5: Full v4 method vocabulary (~80 methods) from day 1

- **Description:** Ship all the `plan.*`, `work.*`, `bundle.*`, `tick.*`, etc. methods now.
- **Pros:** Stage 4 can land without new ipc methods being added.
- **Cons:** v5's `domain` is empty. Methods like `plan.create` reference a `Plan` record type that doesn't exist. Shipping stubs that will be rewritten when `domain` lands violates v5's working rule #1 ("one design doc at a time, motivated by a failing run").
- **Why not chosen:** Stage 3 ships the protocol SHAPE (envelope, framing, dispatch discipline). Methods accrete as their records come online. `system.handshake` + `system.status` are the minimum to prove the framing tests and give Stage 4 something non-trivial to dispatch.

## Technical Considerations

### Dependencies

- `serde` (workspace dep, derive feature). Already declared.
- `serde_json` (workspace dep). Already declared.
- `thiserror`. Added per-crate via `cargo add` in Phase 1.
- `strum`. Added per-crate via `cargo add` in Phase 1. v4 used this for `DaemonMethod`'s wire-string attributes; v5 inherits the pattern.

No `tokio`, `reqwest`, or any async/network crate enters `ipc`. Enforced by the Acceptance Criteria `cargo tree -p ipc` check.

### Performance

- **Encode**: `serde_json::to_vec` on the envelope + a Value payload of ~10 fields is ~2 µs on modern x86_64. Appending `\n` is amortized free.
- **Decode**: `serde_json::from_slice` on the same is ~3 µs. At v5's single-digit RPS (humans pressing Enter), framing is nowhere near the hot path.
- **Two-pass decode on `decode_line`**: the function parses input as `serde_json::Value` first, inspects the `"event"` / `"method"` field for discrimination, then re-parses the full Value into the concrete `DaemonResponse` or `DaemonEvent`. This is ~2x the decode cost of a single-pass typed parse. Matches v4's `IpcMessage::from_json`; inherited intentionally for the discrimination-by-field-presence contract. Single-digit RPS makes the 2x trivial.
- **Line cap**: 1 MiB is 2+ orders of magnitude larger than any plausible Stage 3 message. Large validation output in the `data` field of an event could approach this — v4 ran into it only on cargo/clippy output that got embedded verbatim, and the 1 MiB cap accommodates that case.

### Security

- Wire format is JSON-RPC 2.0 compatible; it does not embed credentials by itself. If a downstream method's `params` or an event's `data` carries secrets (e.g. `tools` emits an event with an echoed env var containing `ANTHROPIC_API_KEY`), those land in events.log via the telemetry subscriber. **No scrubbing in `ipc`.** Scrubbing belongs with the producer of the `Value` payload — typically the `tools` crate at Stage 6+.
- Socket bind is Stage 4's concern (owner-only permissions on `.loopr/socket`). `ipc` never touches the filesystem.
- Request correlation ids (`u64`, client-generated) are not globally unique; the daemon MUST scope correlation to the connection that issued the request. Transport-layer invariant, Stage 4.

### Testing Strategy

- **Unit tests** in `crates/ipc/src/tests.rs` covering every enum variant (round-trip), every RpcError code (wire <-> Rust), byte-stability, oversize, malformed, method-not-found, invalid-params, deny_unknown_fields on params structs, `Unknown` RpcError forward-compat.
- **Seam tests** (per v5 working rule #2): the end-to-end "encode a request, decode it, dispatch via `Method::try_from`, build a response, encode it, decode it, assert equal at the `IpcMessage` level" test is the seam test for `ipc`'s surface. If it passes, Stage 4's transport can assume the wire is correct.
- **Fuzz-style edge cases** (manual, not in CI):
    - Empty line → `ParseError::Decode`
    - Only a newline → `ParseError::Decode`
    - Valid JSON but wrong shape (`{"foo": "bar"}`) → `ParseError::Decode` at the Response/Event parse step
    - Deeply-nested Value in params (5+ levels) → round-trips cleanly (serde_json handles this natively)

### Rollout Plan

- Phases land incrementally, each as its own commit on `v5` that passes `otto ci`.
- Bump to `v0.5.5` after Phase 4 (same repo-local override of `rules/git.md` as prior Stage commits).
- **Stage 5 migration (domain records land):** Add `plan.create`, `plan.get`, `plan.list`, `work.*`, etc. as new `MethodName` variants + `Method` variants + typed params structs. Each new method is additive — existing tests keep passing.
- **Stage 4 consumption:** `loopr` adds a `tokio_util::codec::LinesCodec::new_with_max_length(ipc::MAX_LINE_BYTES)` and wires it to `UnixStream`. Handlers match exhaustively on `ipc::Method`.

## Open Questions

- [ ] **`IpcMessage` disposition for `DaemonRequest`.** v4's `IpcMessage::from_json` rejects requests — the client side only expects responses and events. Should `IpcMessage` gain a `Request` variant for bidirectional-stream scenarios (e.g., a long-lived TUI that submits requests AND receives events on the same connection)? Current draft says no; the client's request-sending path uses `encode_line(&daemon_request)` directly, no envelope. Stage 4's transport design may revisit if the connection model requires it.
- [ ] **Method name format: `scope.verb` or `scope-verb` or `scopeVerb`?** v4 uses `scope.verb` (`plan.create`). Stage 3 inherits that. The root `rules/general.md` says identifiers should be hyphenated; this is one of the few places we follow v3/v4 over general naming rules, because JSON-RPC convention is dotted method names.
- [ ] **Should `DaemonEvent` have typed constructor helpers (v4 pattern: `DaemonEvent::transition_completed(...)`)?** Stage 3 ships the plain struct; if agents/integrator crates end up constructing events from dozens of sites and wanting type safety per event type, revisit. v4's pattern works; Stage 3 defers it pending motivating need.
- [ ] **`strum` over `serde` for `MethodName`?** `strum` is used for the string<->enum mapping because method names go on the wire but not as structured JSON (they're single string fields). Could reimplement via serde with `#[serde(rename = "...")]` on a unit-variant enum. Picked `strum` because v4 set that precedent and `MethodName::iter()` (for coverage tests) is free.
- [ ] **`Method::Status` accepting `Value::Object({})` in addition to `Value::Null` for params.** Some clients emit an empty object `{}` when no params are needed rather than `null`. Current draft accepts both. If this causes ambiguity with future methods that legitimately accept an empty-object params, pin `null` as the only acceptable no-params form — a Stage 4 UX decision.
- [ ] **Request `id` type pinned to `u64`.** JSON-RPC 2.0 allows `id: String | Number | Null`. V4 (and this draft) pin `u64` for Rust ergonomics. A strict third-party JSON-RPC client sending `{"id": "req-1"}` or `{"id": null}` would fail to deserialize. Acceptable for v5 because clients are first-party and we control every sender; revisit if a third-party tool ever needs to speak to the daemon.
- [x] **`ProtocolVersionMismatch` error variant.** Vision line 185 names nine error codes; none covers "client and daemon speak different `PROTOCOL_VERSION`s." **Decided (architect design review):** extend `RpcError` with a new variant at code `-32006`, constructed via `RpcError::protocol_version_mismatch(client, daemon)` for consistent message formatting (`"client=N daemon=M"`). Vision line 185 gets a one-line amendment to name the new code alongside the original six loopr-specific codes. Punting to Stage 4 was the wrong call for a protocol-spec crate; the code assignment belongs here.

## Architect Design-Review Findings (acted on + deferred)

Design review surfaced eight findings. Four were acted on in this draft (error-code additions, `ProtocolVersionMismatch` pinning, handshake enforcement contract, parse-error transport contract — all integrated above). Four are deferred with rationale:

### Deferred: double-parse CPU cost in `decode_line`

- **Concern:** `decode_line` parses each NDJSON line twice (once as `serde_json::Value` to inspect discrimination keys, then as the concrete `DaemonResponse` or `DaemonEvent`). In Stage 4's async runtime, a burst of max-sized (~1 MiB) payloads could stall the executor thread with multi-ms synchronous parsing.
- **Why not acting:** v4 ships this exact pattern and has not hit the limit at production scale. Acknowledged in §Technical Considerations > Performance. v5 runs at single-digit RPS (humans pressing Enter); the 2x decode cost is measurable but invisible. If Stage 4 discovers a real bottleneck during the first E2E, `tokio::task::block_in_place` or `spawn_blocking` at the transport layer is the fix — not a change to `ipc`. The discrimination-by-field-presence contract that requires the two-pass parse is inherited from v4 and worth more than the CPU it costs.

### Deferred: stack overflow from deeply-nested JSON input

- **Concern:** A malicious 1 MiB payload composed of `[[[[...]]]]` could overflow the stack during `serde_json::Value` recursion and panic the daemon outside the agent-task `catch_unwind` boundary.
- **Why not acting:** Outdated for current `serde_json`. Modern versions use a recursion-limit check (`RECURSION_LIMIT: 128` by default) and return `Error::RecursionLimitExceeded` as a parse error, not a stack overflow. The failure surfaces as `ParseError::Decode` and the daemon's transport layer closes the connection cleanly per the Unparseable-input contract above. Worth verifying empirically in Stage 4's first E2E hardening run, but not a Stage 3 doc concern.

### Deferred: `deny_unknown_fields` brittleness for forward compat

- **Concern:** Typed params structs (`HandshakeParams`, etc.) use `#[serde(deny_unknown_fields)]`. A v2 client sending an additive field to a v1 daemon fails with `InvalidParams` rather than the daemon silently ignoring the field and proceeding.
- **Why not acting:** This is the correct behavior, not a bug. `PROTOCOL_VERSION` is the forward-compat mechanism — cross-version extensions happen via a version bump that the handshake refuses, not by silently tolerating unknown fields within a negotiated version. Within a given protocol version, every field is expected; `deny_unknown_fields` catches typos and malformed clients early. Documented in the Forward-Compatibility section of Protocol Contracts above. If a future protocol version ever needs mid-version additive extensions without a version bump, revisit; not a foreseeable need.

### Deferred: asymmetric misrouting detection in `decode_request_line`

- **Concern:** `decode_line` detects misrouted requests on the client stream (returns `ParseError::MisroutedRequest` when `"method"` key present). `decode_request_line` does not do the symmetric check — a misrouted `Event` or `Response` arriving on the daemon stream fails with a generic `ParseError::Decode` (missing `id`) rather than a specific `MisroutedResponse` or `MisroutedEvent`.
- **Why not acting:** Low-value. The daemon stream is tightly controlled — only client-side code sends on it, and the only client code that exists is `loopr`'s own transport. A misrouted Event/Response would be a same-codebase bug, not a real-world protocol violation. The existing `ParseError::Decode` error message would identify the misrouted-payload bug during development. If Stage 4's transport design surfaces this as a real debugging problem, adding a `MisroutedResponse`/`MisroutedEvent` pair of variants is trivial. For now, asymmetry is intentional — prioritize protecting the client from a misdirected daemon (potentially a server bug) over protecting the daemon from a misdirected client (definitely a client bug).
