# Design Document: Store Wrapper over taskstore-async (Stage 5, Plans only)

**Author:** Scott A. Idler
**Date:** 2026-04-20
**Status:** Implemented (shipped in v0.5.12)
**Review Passes Completed:** 5/5 + Architect (Rounds 1 + 2)

## Summary

The fourth and final Stage 5 design doc. Defines a thin typed-ID + typed-error adapter over `taskstore_async::AsyncStore` (the async-native sibling crate designed in `~/repos/scottidler/taskstore/docs/design/2026-04-20-taskstore-async.md`, shipped as `taskstore-async v0.1.1` in taskstore workspace v0.4.1). Exposes exactly three Plan operations — `create`, `get`, `list` — through a `store.plans()` accessor handle, plus `Store::close(self).await` for safe shutdown. All concurrency (writer thread, reader-pool, `spawn_blocking`, WAL-mode SQLite) lives inside `taskstore-async`; the `store` crate is pure adaptation. Unlocked Stage 5's exit-criterion readiness: the seam is ready for the daemon to call `store.plans().create(plan).await` and `store.plans().list().await` as soon as the IPC handlers wire through.

## Problem Statement

### Background

Stages 1–4 gave v5 a working binary, a telemetry layer, a wire protocol, and a forking daemon that accepts IPC requests. Stage 5 introduces persistence. The domain-side work landed in v0.5.8 / v0.5.10 / v0.5.11 (`#[derive(Fsm)]`, `#[derive(Record)]`, and the `Plan` record type plus `id_type!` macro). The remaining gap is the bridge between `domain::Plan` and disk: the `store` crate.

`crates/store/` exists as a directory and is included in the workspace, but `src/lib.rs` is empty and `Cargo.toml` lists only `derive` and `taskstore` as dependencies. There are no accessors, no `Store` type, no error type, no tests. The daemon's IPC `plan` handler has nothing to call.

An earlier draft of this doc proposed wrapping the blocking `taskstore::Store` directly, using `Arc<Mutex<...>>` + `tokio::task::spawn_blocking` to adapt to tokio. That design was reviewed by the Architect, who flagged two structural concerns: (1) the daemon spawns a per-connection tokio task (`crates/loopr/src/transport/server.rs:64`), so concurrent IPC traffic would consume blocking-pool slots for nothing but lock waits, risking daemon-wide deadlock; (2) `rusqlite::Connection` is `!Sync`, which makes `RwLock` structurally impossible and leaves only `Mutex` for in-process serialization. In response, the concurrency shell moved upstream: a new `taskstore-async` crate (design doc above) owns a dedicated writer thread, a pooled set of reader connections, and SQLite WAL mode — all the knobs that actually make the persistence layer performant. This doc is what falls out: a ~60-line adapter whose only job is typed-ID and typed-error conversion.

The `taskstore_async::AsyncStore` API surface we consume (verbatim from its design doc §API Design):

```rust
pub async fn open<P: AsRef<Path>>(path: P, opts: OpenOptions) -> Result<Self, ts_async::Error>;
pub async fn create<T: Record>(&self, record: T) -> Result<String, ts_async::Error>;
pub async fn get<T: Record>(&self, id: &str) -> Result<Option<T>, ts_async::Error>;
pub async fn list<T: Record>(&self, filters: &[Filter]) -> Result<Vec<T>, ts_async::Error>;
// (plus: update, delete, delete_by_index, sync, rebuild_indexes, install_git_hooks,
//  is_stale, base_path, close — all out of Stage 5 scope)
```

### Problem

- **No `Store` type exists.** The daemon has a persisted `Plan` struct but no way to write it.
- **Raw `taskstore_async::AsyncStore` leaks its error type (`ts_async::Error`) and the generic `<T: Record>` type parameter to every call site.** Downstream code would write `store.create::<Plan>(plan).await?` with type annotations at each call. A `store.plans().create(plan).await?` accessor both pins the record type and opens the door to record-specific behavior later (filters, validation hooks, secondary indexes) without mass-editing call sites.
- **`ts_async::Error` is not the loopr error taxonomy.** The `store` crate's stated purpose (per `crates/store/CLAUDE.md`) is to be the anti-corruption layer between loopr's domain types and taskstore's persistence engine. That includes owning a loopr-scoped `StoreError` variant set.
- **`AsyncStore::get` returns `Result<Option<T>, Error>`, which forces every call site to handle the `Option`.** In loopr, "asked for a specific id and didn't find it" is almost always an error condition. Collapsing `Ok(None)` into `Err(StoreError::RecordNotFound)` at the wrapper boundary keeps downstream `match` arms consistent across every Stage 6+ accessor.
- **`PlanId` is a typed newtype; `AsyncStore::create` returns `String`.** Callers want a `PlanId` back. Converting once at the seam is better than every consumer calling `PlanId::from_str(&id).unwrap()` inline.

### Goals

- **`store::Store` type** wrapping `taskstore_async::AsyncStore`, opened by `async fn Store::open(target) -> Result<Store, StoreError>` where `target` is the target repo root. `AsyncStore::open` itself appends `.taskstore/`; our wrapper passes the target through unchanged.
- **`store::StoreError`** `thiserror` enum, closed set of variants, covers every error any Stage 5 operation can raise. `rusqlite`, `fs2`, `eyre::Report`, and `ts_async::Error` never appear in the public API.
- **`store.plans() -> PlansStore<'_>`** typed accessor handle. Returns a borrowed handle, lifetime-tied to the `Store`.
- **Three async methods on `PlansStore<'_>`:**
  - `async fn create(&self, plan: Plan) -> Result<PlanId, StoreError>`
  - `async fn get(&self, id: &PlanId) -> Result<Plan, StoreError>` (returns `Plan`, not `Option<Plan>` — missing id is a typed error)
  - `async fn list(&self) -> Result<Vec<Plan>, StoreError>`
- **Seam tests in `crates/store/tests/plans.rs`**: create → get round-trip, create → list sees the record, serde survives the JSONL layer (indirectly via taskstore-async's internal pipeline), `StoreError::RecordNotFound` fires on a missing id, and `create` returns an id that a subsequent `get` can actually resolve (Architect Round 1 Finding 2 fix).
- **One-line `lib.rs` re-exports** of the public items (`Store`, `StoreError`, `PlansStore`).

### Non-Goals

- **Concurrency plumbing.** `Arc<Mutex<...>>`, `tokio::task::spawn_blocking`, connection pools, dedicated writer threads, SQLite WAL mode — all of this is `taskstore-async`'s responsibility. Our wrapper holds a plain `taskstore_async::AsyncStore` by value and calls `.await` on its async methods.
- **Other record types** (`Spec`, `Phase`, `Work`, `Bundle`, `Tick`, `Run`). Each gets its own accessor in the stage that motivates it — `works()` in Stage 6, `bundles()` in Stage 7, `ticks()` in Stage 8. Stage 5 ships `plans()` alone.
- **Filters, queries, pagination.** `list()` returns every plan. When Stage 6 surfaces a consumer that needs `list_by_status(Active)` or `list_since(ts)`, that's a Stage 6 design-doc change to `PlansStore`, not a Stage 5 change.
- **`update`, `delete`, `delete_by_index`, `create_many`.** Stage 5's only write is a daemon receiving a goal string, constructing a `Plan`, and persisting it. No path mutates or removes existing plans; no path writes in bulk. Each becomes a line-item in a future doc when a consumer materializes.
- **Git-hooks install** (`taskstore install-hooks`, or `AsyncStore::install_git_hooks`). `loopr init` does not exist yet; when it does (likely Stage 6 or alongside Stage 9's first-gate hardening), it gets its own design doc and wires through.
- **In-memory hydration cache at the wrapper layer.** `taskstore-async` already has a SQLite cache of the JSONL truth via its reader pool; a second cache here is premature. Defer until a profile shows `list()` as a hot path.
- **`StoreConfig` composition into top-level `Config`.** The CLAUDE.md bullet exists for later; Stage 5 opens against a fixed path (target root) with `OpenOptions::default()`. Earn `StoreConfig` when the first config knob (reader pool size, writer queue capacity, stale-sync threshold) needs to be tunable from the top-level YAML.
- **Integrating the graceful-shutdown path at the daemon layer.** Our `Store` exposes `close(self).await`; the daemon chooses when to call it. Stage 5's scope is providing the method and documenting the contract, not wiring the daemon's signal handler to invoke it.

## Proposed Solution

### Overview

One `Store` struct, one `PlansStore<'_>` handle, one `StoreError` enum, three async methods. The `Store` holds `taskstore_async::AsyncStore` by value. Each public method on `PlansStore` forwards to the corresponding `AsyncStore` method, maps `ts_async::Error` into `StoreError`, collapses `Option<T>` into `RecordNotFound` where appropriate, and converts between `String` ids and `PlanId`. Callers write `store.plans().create(plan).await?` and get typed ids, typed errors, and no concurrency ceremony.

The daemon flow at Stage 5's exit is: IPC handler receives a `plan "x"` request, constructs `Plan::new("x")`, calls `store.plans().create(plan).await?`, returns the `PlanId` to the client. A second request queries `store.plans().list().await?` and streams the two records back.

### Data Model

#### StoreError (`error.rs`)

```rust
use thiserror::Error;

#[derive(Debug, Error)]
pub enum StoreError {
    #[error("I/O error in taskstore: {0}")]
    Io(String),

    #[error("record not found: {collection}/{id}")]
    RecordNotFound { collection: &'static str, id: String },

    #[error("record already exists: {collection}/{id}")]
    AlreadyExists { collection: &'static str, id: String },

    /// Reserved for Stage 6+ schema-version / integrity checks. Not
    /// constructed in Stage 5; upstream I/O failures arrive as Io.
    #[allow(dead_code)]
    #[error("corrupt record in taskstore: {0}")]
    Corruption(String),

    /// Reserved for Stage 6+ custom deserialize paths in the wrapper itself.
    /// Not constructed in Stage 5; upstream serde failures arrive as Io.
    #[allow(dead_code)]
    #[error("serde failure at store boundary: {0}")]
    Serde(String),
}

impl From<taskstore_async::Error> for StoreError {
    fn from(e: taskstore_async::Error) -> Self {
        match e {
            taskstore_async::Error::Serde(inner) => StoreError::Serde(inner.to_string()),
            other => StoreError::Io(other.to_string()),
        }
    }
}
```

Design notes:

- **Five variants total, closed enum.** Four (`Io`, `RecordNotFound`, `AlreadyExists`, `Serde`) are actively constructed in Stage 5. One (`Corruption`) is reserved for Stage 6+ distinctions and carries `#[allow(dead_code)]` with a comment explaining the reservation. `rules/rust.md` inherits `#![deny(dead_code)]`; the local allow is the canonical pattern for "taxonomy pinned now, consumer staged." Pinning the taxonomy costs one `#[allow]` and buys downstream `match` arms that are compile-forward-stable. (`Serde` went active during implementation once taskstore-async's `Error::Serde` variant was confirmed; see §Addendum Round 2 Finding B resolution.)
- **`AlreadyExists` enforces the domain contract of `create`.** A method named `create` promises record creation, not upsert. `AsyncStore::create` inherits SQLite's `INSERT OR REPLACE` semantics (silently overwrites on id collision). Our wrapper enforces the domain expectation by pre-checking existence (`get` then `create`); a pre-existing record produces `AlreadyExists`, not a silent overwrite. If a future use case specifically wants upsert semantics, it earns an explicit `upsert()` or `create_or_update()` method rather than making the common-case `create` ambiguous. Race-condition caveat captured in §Risks.
- **No `LockPoisoned`, no `JoinError`.** These existed in an earlier draft when the wrapper owned `Arc<Mutex<taskstore::Store>>` + `spawn_blocking`. Both concerns moved upstream into `taskstore-async`; the wrapper has no mutex to poison and no `JoinHandle` to await.
- **`From<taskstore_async::Error>` as the only boundary for upstream errors.** Every `AsyncStore` call site in this crate ends in `.map_err(StoreError::from)` or `?` (the latter leverages the `From` impl). No other way to construct `StoreError::Io`.
- **`From` impl is the single extension point for error fidelity.** The Stage 5 impl maps `taskstore_async::Error::Serde` structurally to `StoreError::Serde` and collapses every other upstream variant (`Io`, `Sqlite`, `StoreClosed`, `WalUnsupported`, `Other`) to `StoreError::Io(String)`. Architect Round 2 flagged blanket collapse as lossy; activating the `Serde` mapping is the partial answer. When Stage 6+ needs to distinguish `Sqlite` (e.g., constraint violation) or `WalUnsupported` or `StoreClosed` as separate `StoreError` variants, those `match` arms land here. The `From` impl lives in one place (`error.rs`); callers pattern-match on `StoreError` variants, never on the stringified detail — so the extension is additive, not breaking.
- **`RecordNotFound` and `AlreadyExists` carry `collection + id`.** Lets downstream call sites construct user-facing messages like "no such plan: pl-k7m2p" or "plan pl-k7m2p already exists" without pattern-matching Display output.
- **Detail in `Io` carried as `String`, not as `#[from] taskstore_async::Error`.** Preserving the upstream error type would re-export `taskstore_async` as a public dep of `store` and force every consumer to compile against it. Stringifying at the boundary is cheap (error paths are rare) and keeps the dependency surface narrow.

#### Store (`store.rs`)

```rust
use std::path::Path;

use taskstore_async::{AsyncStore, OpenOptions};

use crate::error::StoreError;
use crate::plans::PlansStore;

pub struct Store {
    inner: AsyncStore,
}

impl Store {
    /// Open the store rooted at the given target directory.
    ///
    /// `taskstore_async::AsyncStore::open` appends `.taskstore/` to its
    /// argument and creates the subdirectory on first call. Pass the target
    /// repo root; do NOT pre-append `.taskstore/` or the subdirectory gets
    /// nested.
    ///
    /// Uses `OpenOptions::default()` — the default reader-pool size and
    /// writer-queue capacity are fine for Stage 5. When tuning becomes
    /// necessary, `StoreConfig` composes into top-level `Config` and
    /// exposes the knobs.
    pub async fn open(target: impl AsRef<Path>) -> Result<Self, StoreError> {
        let inner = AsyncStore::open(target.as_ref(), OpenOptions::default()).await?;
        Ok(Self { inner })
    }

    /// Typed accessor for Plan records. Borrowed handle; zero cost.
    pub fn plans(&self) -> PlansStore<'_> {
        PlansStore::new(&self.inner)
    }

    /// Graceful async shutdown. Drops the writer queue, awaits the writer
    /// thread's drain signal, joins cleanly. Consumes `self` so the wrapper
    /// cannot be used after close.
    ///
    /// **Why this exists:** `AsyncStore::Drop` joins the writer thread
    /// synchronously. If the `Store` is dropped on a tokio executor thread
    /// (normal runtime shutdown, task panic, daemon exit), the sync join
    /// blocks the reactor and can trigger tokio's "Cannot block the current
    /// thread" panic — exactly when you need flush-to-disk to succeed most.
    /// Callers holding the `Store` on a tokio runtime MUST invoke
    /// `close().await` before drop; the daemon's shutdown handler does this
    /// as part of Stage 4's signal-handling path (or whatever stage materializes
    /// the daemon-lifecycle wire-up).
    ///
    /// Drop remains safe as a last-resort fallback (crash-interrupt paths, etc),
    /// but must not be the expected shutdown pattern.
    pub async fn close(self) -> Result<(), StoreError> {
        self.inner.close().await?;
        Ok(())
    }
}
```

Design notes:

- **`open()` is `async`.** Unlike the earlier draft where `Store::open` was sync (because `taskstore::Store::open` was sync), `AsyncStore::open` is async (it initializes the writer thread and reader pool). The daemon calls this once at startup inside its tokio runtime; no change to consumer ergonomics.
- **`inner: AsyncStore` — no `Arc`, no `Mutex`, no `PhantomData`.** The concurrency model is `AsyncStore`'s concern. `AsyncStore` is `Send + Sync` (taskstore-async design doc confirms); `Store` inherits those bounds automatically.
- **`plans()` returns `PlansStore<'_>`** (borrowed, lifetime-tied to `&self`). An owned handle would have no inner state to own (the handle is stateless and borrows the `AsyncStore`), so the lifetime is load-bearing, not cosmetic. Keeps the door open for a future `PlansStore` field that wants a real `&'a AsyncStore` reference.

#### PlansStore (`plans.rs`)

```rust
use std::str::FromStr;

use taskstore_async::AsyncStore;

use domain::{Plan, PlanId};

use crate::error::StoreError;

pub struct PlansStore<'a> {
    inner: &'a AsyncStore,
}

impl<'a> PlansStore<'a> {
    pub(crate) fn new(inner: &'a AsyncStore) -> Self {
        Self { inner }
    }

    pub async fn create(&self, plan: Plan) -> Result<PlanId, StoreError> {
        // Enforce create-semantics at the ACL boundary. AsyncStore inherits
        // SQLite's INSERT OR REPLACE from taskstore, which silently overwrites
        // on id collision. The domain contract of a method named `create` is
        // "make a new record, error on collision" — so we pre-check existence
        // and surface AlreadyExists when the id is taken.
        //
        // Race-condition caveat: the get(..) and create(..) are not inside one
        // transaction, so a concurrent create of the same id between these two
        // calls would still overwrite. See §Risks for scope; Stage 5's single-
        // daemon model with fresh-id minting (Plan::new() → PlanId::new())
        // makes this vanishingly unlikely in practice, and a multi-daemon
        // scenario needs upstream conditional-write support anyway.
        let id_str_ref = plan.id.as_ref().to_string();
        if self.inner.get::<Plan>(&id_str_ref).await?.is_some() {
            return Err(StoreError::AlreadyExists {
                collection: "plans",
                id: id_str_ref,
            });
        }
        let id_str = self.inner.create(plan).await?;
        // AsyncStore returns the id as a String. Round-trip through
        // PlanId::from_str (Infallible) to get the typed form back. This
        // preserves the invariant that whatever id taskstore persisted under
        // is the id we return — any future upstream change that synthesizes
        // server-side ids surfaces here via a subsequent `get(&id)` returning
        // RecordNotFound (pinned by the `create_returns_id_that_resolves` test).
        Ok(PlanId::from_str(&id_str).expect("PlanId::from_str is Infallible"))
    }

    pub async fn get(&self, id: &PlanId) -> Result<Plan, StoreError> {
        match self.inner.get::<Plan>(id.as_ref()).await? {
            Some(plan) => Ok(plan),
            None => Err(StoreError::RecordNotFound {
                collection: "plans",
                id: id.to_string(),
            }),
        }
    }

    pub async fn list(&self) -> Result<Vec<Plan>, StoreError> {
        Ok(self.inner.list::<Plan>(&[]).await?)
    }
}
```

Design notes:

- **`Plan` is consumed, not borrowed.** `AsyncStore::create<T: Record>(&self, record: T)` takes ownership; we pass it through. Matches the typed-domain contract (each record has one canonical location after persistence).
- **`create` returns taskstore's String round-tripped through `PlanId::from_str`, not a pre-move clone of `plan.id`.** Architect Round 1 Finding 2: pre-cloning `plan.id` before the create call would make the `create_returns_id_matching_plan` test tautological (it would compare a hardcoded clone against itself). By round-tripping through `AsyncStore`'s returned String, the test actually proves that the id we give back matches what taskstore-async persisted under. `PlanId::from_str` is `Infallible` (per domain's `id_type!` macro), so the `.expect` is the correct shape, not a papered-over `unwrap()`.
- **`get` collapses `Option` into `RecordNotFound`.** `AsyncStore::get` returns `Result<Option<T>, Error>`; we return `Result<Plan, StoreError>`. Callers almost always want "give me this plan or tell me why not." The `Option` collapse happens once at the wrapper boundary, keeping the one-variant error model consistent across every Stage 6+ accessor. If a future caller needs "exists-without-fetching," add `exists(&PlanId) -> Result<bool, StoreError>` as a separate method rather than leaking the `Option` form.
- **`list` passes an empty filter slice `&[]`.** Returns every plan. `AsyncStore::list` orders by `updated_at DESC` in its reader-pool SELECT; tests assert membership, not ordering (ordering is a taskstore-async invariant, not ours to re-verify).
- **`?` at `.await` sites uses `From<ts_async::Error>`.** The `StoreError::Io` conversion happens via the `From` impl; no explicit `.map_err` needed. Compact and readable.
- **No `spawn_blocking`, no `Arc::clone`, no `Mutex::lock`.** The wrapper is pure adaptation. Any performance or concurrency concern is `taskstore-async`'s owned territory.

### API Design

Public surface exported from `crates/store/src/lib.rs`:

```rust
mod error;
mod plans;
mod store;

pub use error::StoreError;
pub use plans::PlansStore;
pub use store::Store;
```

Three public items. No re-export of `taskstore_async::AsyncStore`, `taskstore_async::Error`, `taskstore::Filter`, or any other upstream type. The crate forms exactly the anti-corruption seam `crates/store/CLAUDE.md` mandates.

Consumer-facing usage from the daemon (illustrative, not Stage 5 code):

```rust
// daemon startup
let store = store::Store::open(target_path).await?;

// IPC plan handler
let plan = domain::Plan::new(goal);
let id = store.plans().create(plan).await?;
respond_with_id(id);

// IPC list handler
let plans = store.plans().list().await?;
respond_with_plans(plans);

// IPC get handler (future)
let plan = store.plans().get(&id).await
    .map_err(|e| match e {
        StoreError::RecordNotFound { .. } => rpc_error_not_found(),
        other => rpc_error_internal(other),
    })?;
```

The daemon holds one `Store` as a long-lived field; `store.plans()` is called per-request and produces a zero-cost handle.

### Implementation Plan

Three phases, each a single-commit milestone. All three are pure adaptation with no novel design decisions once this doc is approved, so the model annotation is `sonnet` throughout.

- Ensure `taskstore-async` has shipped (its own three-crate workspace design doc is implemented and the workspace has cut a compatible release). If not yet shipped, this phase blocks on it; Stage 5 depends on taskstore-async as a prerequisite.

  - Replace `taskstore = { workspace = true }` with `taskstore-async = { workspace = true }` (the Stage 5 wrapper consumes only the async-native API).
  - Add `domain = { path = "../domain" }`.
  - Add `thiserror` (via `cargo add -p store thiserror`, workspace-promote if a second crate adopts).
- Create `crates/store/src/error.rs` with `StoreError` + `From<taskstore_async::Error>` per §Data Model.
- Create `crates/store/src/store.rs` with `Store { inner }` and `async fn open`.
- Rewrite `crates/store/src/lib.rs` to declare `mod error; mod store;` and re-export `Store`, `StoreError`.
- Add a `//! crate doc comment` at the top of `lib.rs` matching the sibling crates' pattern.
- `otto ci` inside `crates/store/` passes (compiles against `domain::Plan` and `taskstore_async::AsyncStore`; no tests yet).

#### Phase 2: `PlansStore` handle with `create` / `get` / `list`

**Model:** sonnet

- Create `crates/store/src/plans.rs` with `PlansStore<'a>` and the three async methods per §Data Model.
- Edit `crates/store/src/lib.rs` to add `mod plans;` and `pub use plans::PlansStore;`.
- Edit `crates/store/src/store.rs` to add the `plans()` accessor.
- Create `crates/store/tests/plans.rs` with `#[tokio::test]` seam tests:
  - `create_returns_id_that_resolves` — Architect Round 1 Finding 2 fix. `create(plan).await` returns an id; immediately `get(&id).await` returns `Ok(plan_eq)`. This proves the returned id is the id taskstore-async actually persisted under, not a hardcoded echo. Supersedes the earlier (tautological) `create_returns_id_matching_plan` framing.
  - `create_then_get_roundtrip` — serde-equivalence across the store boundary. `create(p).await → get(&id).await` yields a `Plan` equal in all five fields to the original.
  - `create_then_list_sees_record` — after one `create`, `list()` returns a single-element `Vec` containing the created plan.
  - `create_two_then_list_returns_both` — idempotence / ordering sanity; assert both ids present. Order not pinned — `AsyncStore::list` orders by `updated_at DESC`, sufficient for seam coverage.
  - `get_missing_returns_record_not_found` — `get(&PlanId::new())` on a fresh store returns `Err(StoreError::RecordNotFound { collection: "plans", .. })`. Pattern-matches the variant structurally, not the stringified Display.
  - `empty_store_list_returns_empty_vec` — `list()` on a freshly-opened store returns `Ok(vec![])`. Pins that zero records is not an error condition.
  - `create_same_id_twice_returns_already_exists` — Architect Round 2 Finding 3 fix. The first `create(p)` succeeds; a second `create` with the same `plan.id` returns `Err(StoreError::AlreadyExists { collection: "plans", .. })`. Pattern-matches the variant structurally. Asserts `list()` returns a single record (proving the second create did not overwrite). Pins the ACL's enforcement of `create` semantics — if the pre-check ever regresses, this test fails.
  - `close_returns_ok_on_fresh_store` — `Store::open(...).await?.close().await?` succeeds. Pins that graceful shutdown works end-to-end and that `close` is callable without any prior operations.
  - `serde_roundtrip_survives_jsonl` — Plan with unusual (but valid) content (`goal` with unicode characters, empty `goal`, each `PlanStatus` variant), create, list, assert deep equality. Pins the JSONL truth layer round-trips through the same serde path `domain`'s own tests cover.
  - `plans_store_is_send_sync` — compile-time assertion via `fn assert_send_sync<T: Send + Sync>() {}` called with `Store` and `PlansStore<'static>`. Pins the tokio-task compatibility at the type level. `'static` is the worst-case lifetime; if it passes, any shorter lifetime passes too. (`Store: Send + Sync` follows from `AsyncStore: Send + Sync`; this test fences regressions if the struct ever gains a non-Send field.)

## Alternatives Considered

### Alternative 1: Wrap blocking `taskstore::Store` in-crate with `Arc<Mutex<...>>` + `spawn_blocking`

- **Description:** Earlier draft of this doc. `Store` owns `Arc<Mutex<taskstore::Store>>`, each public async method clones the Arc, hands it to `tokio::task::spawn_blocking`, acquires the lock inside the closure, calls into the blocking `taskstore::Store`, maps errors.
- **Pros:** No upstream change to taskstore. One crate to modify (`store`). All concurrency design local.
- **Cons (Architect Round 1):** (1) `crates/loopr/src/transport/server.rs:64` spawns a per-connection tokio task, so concurrent IPC clients all call the wrapper concurrently. Each `spawn_blocking` consumes a tokio blocking-pool slot (default 512); N concurrent requests all parked on `.lock()` consume N slots for nothing, risking daemon-wide starvation. (2) `rusqlite::Connection` is `!Sync`, which makes `RwLock` structurally impossible — only `Mutex` works, and we inherit its serialization. (3) `PoisonError` creates a recovery surface our wrapper has no path to handle. The earlier draft's `StoreError::LockPoisoned` existed precisely because this alternative has no better answer.
- **Why not chosen:** The performance and correctness concerns are real and structural. Pushing the concurrency shell upstream into `taskstore-async` gives us a connection pool (real concurrent reads), a dedicated writer thread (zero blocking-pool pressure), and WAL mode (SQLite-level reader/writer isolation) — all properties the in-crate alternative cannot provide. This doc's entire `§Data Model` shrinks once the alternative moves upstream.

### Alternative 2: Async-only `taskstore` (drop the sync API entirely)

- **Description:** Rather than a `taskstore-async` sibling crate, make the existing `taskstore` crate async-native (breaking change for sync consumers).
- **Pros:** Simplest mental model. One crate, one API, one version. No "which import?" decision.
- **Cons:** Breaks three concrete sync consumers (identified in the taskstore-async design doc §Problem): the `taskstore` CLI binary, the `taskstore-merge` git merge driver (must stay sync — git invokes it with no tokio runtime), and any external libraries that consume `taskstore` blocking.
- **Why not chosen:** the `taskstore-merge` constraint is load-bearing. The merge driver runs inside `git merge` with no tokio runtime available; making it async would force `taskstore` to ship two binaries with different runtime behavior or drop the merge driver entirely (and the merge driver is what makes `.taskstore/*.jsonl` safe under concurrent edits). Keeping `taskstore` sync and adding `taskstore-async` as a sibling preserves all three consumers without compromise.

### Alternative 3: `taskstore` feature flag (`taskstore = { features = ["async"] }`)

- **Description:** One crate, opt-in async API behind a Cargo feature. Sync consumers keep the default; async consumers opt in.
- **Pros:** One crate to publish, one version to track. Ecosystem-common pattern (reqwest, serde).
- **Cons:** Feature flags on a persistence library mean every downstream consumer that enables `async` also compiles the sync `Store` (Cargo features are additive). The merge-driver CLI still needs to not-depend-on-tokio, which a feature flag can enable but doesn't enforce; build-matrix testing grows. Also, taskstore already has the two-crate discipline (`taskstore-traits` + `taskstore`) — adding the async path as a third crate is the consistent move.
- **Why not chosen:** the three-crate workspace matches the project's existing split-by-scope discipline. Feature-flag archaeology ("why is tokio compiled here?") is harder to debug than three clearly-named crates with clean dep graphs.

### Alternative 4: Loopr-v5 owns the concurrency shell, taskstore stays entirely untouched

- **Description:** Keep `taskstore` as it is today. Our `store` crate builds the dedicated-thread + connection-pool pattern internally, wrapping blocking `taskstore::Store`. Essentially Alternative 1 with a different internal shape.
- **Pros:** Zero upstream change. Full control over concurrency semantics.
- **Cons:** Duplicates work that belongs upstream. Every future taskstore consumer that wants async rebuilds the same shell. Increases our crate's code surface from ~60 lines to ~300+. Moves the WAL-mode knob out of the library that owns SQLite semantics. Keeps the in-crate alternative's Architect findings live (just relocated one layer down).
- **Why not chosen:** taskstore-async is a reusable upstream piece; loopr is the first consumer, not the last. Owning the concurrency shell at the library layer serves every future consumer; owning it in loopr serves only loopr and forks the ecosystem.

### Alternative 5: Streaming `list()` (returns `impl Stream<Item = Plan>`)

- **Description:** For scalability, `list` yields a stream of records instead of a fully-materialized `Vec`.
- **Pros:** Bounded memory footprint if a future repo has 100k plans.
- **Cons:** `AsyncStore::list` returns `Vec<T>` (materializes internally). Streaming at our wrapper would buffer the Vec and replay it — same memory cost with more code. Stage 5 expects O(dozens) of plans per target repo.
- **Why not chosen:** premature. Solve the problem that exists. If a target ever hits 100k plans, streaming earns its way in with a design change both at `taskstore-async` (incremental SQLite SELECT) and here.

## Technical Considerations

### Dependencies

- `taskstore-async` (workspace, git dep alongside the existing `taskstore` and `taskstore-traits` entries). Stage 5 prerequisite; must ship before Phase 1 can start.
- `domain` as a path dep. Consumed for `Plan`, `PlanId`. `crates/store/CLAUDE.md` anticipates this.
- `thiserror` for `StoreError`. Workspace-consistent with `domain` + `derive`.
- `tempfile` as a dev-dep for tests.
- `tokio` with `rt` + `macros` as a dev-dep (tests use `#[tokio::test]`).

Note: **no direct `tokio` dep in the library.** `AsyncStore` is async-native; our wrapper calls `.await` on its methods and uses `From` for error conversion. No `spawn_blocking`, no `Arc`, no `Mutex`, no `tokio::task` imports. The tokio runtime comes in through `AsyncStore`'s transitive dep; our library's Cargo.toml names only taskstore-async and domain for the persistence-facing wiring.

Note: **no direct `taskstore` dep in Stage 5.** We consume `taskstore-async` exclusively. `taskstore` is present transitively (taskstore-async depends on it for the sync core), but our crate does not import anything from it. If a future stage needs sync-only access (e.g., a `loopr init` CLI path that must run without a tokio runtime), that wires `taskstore = { workspace = true }` back in as a direct dep then.

### Performance

- `create`: one async call into `AsyncStore::create` → one writer-queue enqueue → one fsync at the SQLite layer. Dominant cost is fsync (~1-5ms local SSD). Human-filed plans are nowhere near a hot path.
- `get`: one async call into `AsyncStore::get` → one reader-pool acquire → one SQLite SELECT by primary key → one deserialize. Concurrent reads multiplex across the reader pool (WAL mode allows genuine parallelism). ~100μs order per call, scales with pool size for concurrent clients.
- `list`: one async call into `AsyncStore::list` with empty filter → one reader-pool acquire → one SQLite SELECT all → N deserializes. Concurrent `list()` from multiple IPC clients also multiplex.
- Adapter overhead (our wrapper): one `From` error conversion per error path (error paths are rare), one `PlanId::from_str` per `create` success (microseconds), one `Option`→`RecordNotFound` collapse per `get`. Negligible relative to the SQLite + fsync path.
- Daemon concurrency: every `store.plans().create(plan).await` awaits the writer-queue; writes are serialized by design (SQLite constraint). Multiple `store.plans().get(...).await` calls from different IPC connections run in parallel against the reader pool.

### Security

No new security surface. `tempfile::TempDir` for tests isolates fixture state into `/tmp`. The wrapper introduces no new parse surfaces: JSONL deserialization happens inside `taskstore-async`, already covered by its threat model.

### Testing Strategy

Per v5 working rule #2 ("every crate boundary has at least one round-trip serde test and one integration test that crosses the seam with real types"), tests live at `crates/store/tests/plans.rs` and exercise the public API against a real `taskstore_async::AsyncStore` via `tempfile::TempDir`-backed storage. No mocks, no fakes at this layer — taskstore-async is the thing we're wrapping; faking it defeats the seam.

- **No unit tests inside `src/`.** The wrapper is thin enough that unit coverage would duplicate what the integration tests prove. If `StoreError` variant-mapping ever grows logic (Stage 6+ distinguishing Corruption vs Io upstream), unit tests on the pure `From` impl land at that point.
- **`#[tokio::test]`** for all tests; default flavor (current_thread) is sufficient.
- **Per-test `TempDir`.** Each test opens its own `.taskstore/` under a fresh tempdir. No shared fixtures; no test-order coupling.
- **Plan construction uses `domain::Plan::new(...)`.** Couples test surface to domain's public constructor API; evolves together.
- **`assert_send_sync`** compile-time test fences regressions if Store or PlansStore ever gain a non-Send field.

### Rollout Plan

Three commits on the `v5` branch, one `bump` at the end.

- Commit 1: Phase 1 (Cargo wiring + `StoreError` + `Store::open`).
- Commit 2: Phase 2 (`PlansStore` + three async methods + seam tests).
- Commit 3: Phase 3 (roadmap + doc status flip + `bump` patch).

No coexistence. v4's TaskStore handling is not imported. The daemon's Stage 5 exit-criterion integration (wiring `Store::open` into daemon startup and plumbing `store.plans()` into the IPC handlers) is a separate follow-up design under `crates/loopr/docs/design/`.

**Prerequisite:** `taskstore-async` must ship its v0.4.x (or whatever version-bump scheme the taskstore workspace lands on) release before Phase 1 can start. Stage 5 work on `store` blocks on that upstream release.

|------|------------|--------|------------|
| `AsyncStore::create` synthesizes a server-side id that doesn't match `plan.id` (surfaces as `RecordNotFound` on immediate `get`) | Low | High | Phase 2 test `create_returns_id_that_resolves` pins the invariant: `create(plan).await` returns id; `get(&id).await` returns `Ok(plan_eq)`. If taskstore-async ever changes this behavior, the test fails loudly in CI. |
| Two daemons opening the same `.taskstore/` race on the advisory lock | Low | Medium | taskstore-async inherits taskstore's advisory-lock behavior; the second opener fails. Our wrapper surfaces that as `StoreError::Io`. Stage 5's daemon enforces single-instance via `.loopr/daemon.pid` (Stage 4 feature), so two-daemon collision on the same target is already prevented one layer above. |
| `create(plan)` races with a concurrent `create` of the same id, bypassing the pre-check | Vanishingly low | Medium | The pre-check (`get` then `create`) is NOT transactional — a concurrent `create` between the two upstream calls could overwrite. Stage 5's single-daemon model with `Plan::new()` minting fresh random ids makes collision ~0. Upstream (taskstore-async) does not currently expose a conditional-write primitive; when Stage 6+ introduces a multi-daemon scenario or a Stage 7 parallel-writer path, extend `AsyncStore` with `create_if_absent` (or equivalent) and replace our pre-check with the atomic upstream primitive. Documented, bounded, not-blocking-Stage-5. |
| Dropping `Store` on a tokio executor thread triggers "Cannot block the current thread" panic or deadlocks the reactor | Medium if daemon shutdown flow ignores close() | High | `AsyncStore::Drop` synchronously joins the writer thread. Safe when dropped from outside the executor (main thread after runtime shutdown); unsafe when dropped from inside a tokio task or during runtime termination. The daemon's shutdown handler MUST invoke `store.close().await` before the runtime terminates; `Drop` is a last-resort fallback only (power loss, `abort()`, etc). Our `close()` method exists specifically to make the safe path callable from Stage 5 onward. When Stage 4 or a follow-up doc wires the daemon's signal handler to `close().await`, the hazard is fully contained. |
| `StoreError::Io(String)` is too coarse — callers want to distinguish "disk full" from "schema mismatch" from "permission denied" | Low | Low | `Io` is a Stage 5 catch-all. Future Stage-N design docs earn their own variants when a caller actually needs to distinguish. The `From<taskstore_async::Error>` impl is the single place to add variant-mapping logic, contained and unit-testable. |
| `taskstore-async` fails to ship on the schedule our Stage 5 plan assumes | Medium | Medium | Stage 5's three-phase plan blocks on the upstream release. Mitigation-in-depth: rev-pin in the root workspace if the first break occurs. |
| `AsyncStore::close` is never called in Stage 5 (we rely on `Drop`) | Low | Low | taskstore-async's `Drop` impl joins the writer thread synchronously and waits for in-flight writes; no data loss on process exit. ## Addendum: Architect Review (Round 1)

After converging at 5/5 Rule-of-Five passes, an earlier draft of this doc went to an Architect consultation (Gemini via `~/.claude/skills/architect/script.sh`). Three findings surfaced; two were accepted into this design's shape, and one prompted upstream refactoring.

### Finding 1: Blocking-pool exhaustion under concurrent IPC (resolved upstream)

- **Architect critique:** the earlier draft claimed "daemon IPC serializes requests through one event loop, contention is zero." Verification against `crates/loopr/src/transport/server.rs:64` showed `tokio::spawn(handle_client(stream, ctx).instrument(span))` — per-connection concurrent tasks. With `Arc<Mutex<TaskStore>>` + `spawn_blocking` inside each method, N concurrent IPC requests would consume N blocking-pool slots just to wait on `.lock()`. Under load (default blocking pool = 512 threads), the daemon would starve its blocking pool on mutex contention and deadlock daemon-wide operations.
- **Resolution:** the concurrency shell moved upstream into a new `taskstore-async` sibling crate. This doc now consumes `AsyncStore`, which owns a dedicated writer thread + pooled reader connections + WAL mode. Our wrapper has no mutex, no `spawn_blocking`, and no blocking-pool pressure. The entire class of failures the Architect flagged is structurally eliminated at our layer.

### Finding 2: ID verification tautology (fixed by design change)

- **Architect critique:** an earlier Pass-2 optimization had `create` return a clone of `plan.id` before taking ownership of `plan`, discarding the `String` id that taskstore's underlying `create` returns. The proposed test `create_returns_id_matching_plan` would have been tautological — comparing a hardcoded clone against itself, proving nothing even if taskstore-async began synthesizing server-side ids.
- **Resolution:** this doc's `create` returns `AsyncStore`'s returned String parsed via `PlanId::from_str` (`Infallible`, so the `expect` is the correct shape, not a papered-over `unwrap`). The Phase 2 test `create_returns_id_that_resolves` performs `create(plan).await` → `get(&id).await` and asserts the record resolves, proving that the id returned is the id taskstore-async persisted under. If the upstream behavior ever diverges, the test fails in CI rather than producing silent `RecordNotFound`s in production.

### Finding 3: RwLock reconsideration (moot given upstream shift)

- **Architect critique:** the earlier draft rejected `RwLock` citing "`taskstore::Store` requires `&mut self` for writes." The Architect observed that `get` and `list` take `&self` (taskstore `store.rs:208, 352`) and suggested reconsidering `RwLock` for read concurrency.
- **Resolution:** the Architect's observation about method signatures was correct, but verification against `rusqlite::Connection` showed `Send + !Sync` — which makes `Arc<RwLock<TaskStore>>` structurally unable to compile (`RwLock<T>: Sync` requires `T: Send + Sync`, which `taskstore::Store` is not). The earlier draft's rejection rationale named the wrong constraint; the real one was `!Sync`. Either way, the upstream shift to `taskstore-async`'s connection-pool design (multiple independent reader `Connection`s, each used from the blocking pool via isolated `spawn_blocking` invocations) provides real read concurrency — which `RwLock` on a single Connection could never have delivered. Finding 3's suggestion was moot once Finding 1's upstream resolution landed.

### Net design diff vs. pre-review 5/5 draft (Round 1 resolutions)

- §Data Model: dropped `Arc<Mutex<TaskStore>>`, `PhantomData`, `StoreError::LockPoisoned`, `StoreError::JoinError`, and all `spawn_blocking` plumbing. Replaced with a direct `AsyncStore` value and a `From<taskstore_async::Error>` impl.
- §Proposed Solution: `Store::open` becomes `async fn`. No concurrency plumbing in the wrapper.
- §API Design: public surface preserves the same three methods (`create`, `get`, `list`). The upstream shift is invisible at the seam.
- §Alternatives Considered: five alternatives, collapsing the earlier sync/thread/tokio-rusqlite options and adding the taskstore-async workspace alternatives (async-only, feature flag).
- §Technical Considerations: no direct `tokio` or `taskstore` deps in our library Cargo.toml. taskstore-async is the only persistence-facing dep.
- §Risks: trimmed to boundary-local concerns. Upstream concurrency risks moved to taskstore-async's own risk table.

## Addendum: Architect Review (Round 2)

After the Round 1 resolutions landed, the revised doc went back to the Architect. Three new findings surfaced, all accepted.

### Finding A: Drop-in-async-context hazard (critical)

- **Architect critique:** `AsyncStore::Drop` performs a synchronous thread join. If the `Store` is dropped from a tokio executor thread (runtime shutdown, task panic, daemon exit), the sync join blocks the reactor and can trigger tokio's "Cannot block the current thread" panic — precisely when flush-to-disk needs to succeed most. Deferring `close().await` to Stage 6 leaves the hazard live through Stage 5.
- **Resolution:** `Store::close(self) -> Result<(), StoreError>` added as part of Stage 5's API. Documentation on both `Store::close` and the §Risks table explicitly states that `close().await` is the required shutdown path on tokio, and `Drop` is a last-resort fallback for crash-interrupt scenarios only. New test `close_returns_ok_on_fresh_store` exercises the happy path. The daemon wire-up (invoking `close().await` in the signal handler) is a Stage 4 / follow-up doc concern; exposing the safe method now is Stage 5's responsibility and is done.

### Finding B: Error fidelity loss (accepted with scoped deferral)

- **Architect critique:** collapsing every `ts_async::Error` variant into `StoreError::Io(String)` destroys structural fidelity. Downstream code cannot programmatically distinguish disk-full from schema-corrupt from constraint-violation without fragile string-matching on Display.
- **Resolution (partial, intentional for Stage 5):** the `From<taskstore_async::Error>` impl is the single extension point — Stage 5 collapses to `Io(String)` with the stringified detail; Stage 6+ earns specific mappings (`ts_async::Error::NotFound` → `StoreError::RecordNotFound`, `ts_async::Error::Serde(_)` → `StoreError::Serde(_)`, etc.) when callers actually need to branch on them. The reserved `Corruption` / `Serde` variants in the enum exist for exactly this expansion; they carry `#[allow(dead_code)]` until the mapping earns them. The deferral is explicit, localized to one file, and additive (no existing caller breaks when variants expand). Documented in §Data Model design notes and as an open question for the `ts_async::Error` variant list (below).

### Finding C: Adapter too thin — `create` semantics leak

- **Architect critique:** taskstore-async's `create` inherits SQLite `INSERT OR REPLACE` semantics, silently overwriting on id collision. The earlier draft documented this passively ("documents what actually happens") rather than enforcing the domain contract of a method named `create`. That's a leaky abstraction — an anti-corruption layer enforces, it doesn't transcribe.
- **Resolution:** `PlansStore::create` now pre-checks existence (`get` before `create`) and returns `StoreError::AlreadyExists { collection, id }` on collision. The test `create_same_id_twice_overwrites` was replaced with `create_same_id_twice_returns_already_exists`, which pattern-matches the variant and also asserts `list()` still returns a single record. The race-condition caveat (the pre-check is not transactional) is bounded and captured as a §Risks row; Stage 5's single-daemon fresh-id-minting model makes it vanishingly unlikely in practice, and the upstream fix (conditional-write primitive in `AsyncStore`) is identified for when Stage 6+ introduces contention.

### Open question raised by Round 2

- **Which `taskstore_async::Error` variants exist, and which of our `StoreError` variants do they map to?** Currently unknown — the taskstore-async design doc is authored; the Error enum's exact shape lands when its Phase 1 ships. The `From` impl must be revisited once the upstream enum is concrete. Stage 5 consumers rely on the `Io` catch-all; Stage 6+ consumers revisit the mapping as their needs surface.

### Net design diff vs. Round 1 draft

- §Data Model: `StoreError` grows from four to five variants (adds `AlreadyExists`). Design notes updated to explain the `From` impl as the single extension point for Stage 6+ fidelity.
- §Proposed Solution: `PlansStore::create` now does a pre-check-get before create to enforce no-overwrite. `Store::close(self).await` added as a public method.
- §API Design: one new method (`close`). Existing three method signatures unchanged.
- §Non-Goals: "Integrating the graceful-shutdown path at the daemon layer" replaced the old "Exposing AsyncStore::close through our wrapper" (inverted — we DO expose it; the daemon-side wire-up is what's deferred).
- §Implementation Plan: Phase 2 test list gains `create_same_id_twice_returns_already_exists` (replacing the `overwrites` variant) and `close_returns_ok_on_fresh_store`.
- §Risks: added Drop-on-executor row (Medium/High, with the mitigation pointing at `close()`); replaced the old `create` silent-overwrite row with the pre-check race-condition row.
- §Open Questions: added the `ts_async::Error` variant-mapping question (blocks the `From` impl refinement in Stage 6+, not Stage 5).
